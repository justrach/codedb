## Ranked hot paths and opportunities

### 1. Initial indexing: parallel workers feed a serial commit/merge bottleneck

**References**

- `src/benchmark.zig:304-311`, `main`: times one complete `watcher.initialScan(..., false)`.
- `src/watcher.zig:699-852`, `initialScanWithWorkerCount`.
- `src/watcher.zig:784-801`: static contiguous partitioning and thread creation.
- `src/watcher.zig:803-812`: main thread serially consumes and commits parsed files.
- `src/watcher.zig:821-828`: word-index shards are merged serially under `Explorer.mu`.
- `src/watcher.zig:606-663`, `parseInitialScanEntry` / `parseInitialScanWorkerEntry`: per-file read, parse, arena-backed persistence/copying.

**Why hot**

Parsing and file reads are parallel, but `commitParsedFileAdoptOutline` remains a single ordered consumer. Static file-count partitioning ignores file-size/parser-cost variance, so one slow chunk can determine wall time. Final shard merging is also serial and performs substantial hash-table insertion/allocation.

**Optimization opportunities**

- Schedule files dynamically or partition by cumulative byte size rather than count.
- Batch commits so lock acquisition, hash-map growth, and generation/cache invalidation occur once per batch.
- Pre-reserve destination outline/content/dependency maps from `entries.items.len`.
- Reuse worker parser/scratch arenas across files instead of constructing per-file allocator state.
- Separate I/O and CPU stages only if profiling shows read stalls; otherwise avoid extra queues/copies.
- Parallelize shard reduction as a tree, then publish the completed index once.

**Benchmark method**

```sh
zig build -Doptimize=ReleaseFast benchmark -- --root <fixed-repo> --iterations 200 --json
CODEDB_BENCH_CALLOC=1 CODEDB_INDEX_PROFILE=1 CODEDB_INDEX_WORKERS={1,2,4,8} \
  zig build -Doptimize=ReleaseFast benchmark -- --root <fixed-repo> --json
```

Report files/s, indexed MiB/s, total `index_ms`, and profile phases `collect`, `parse_commit`, `join`, and `merge_free`. Use ≥10 fresh processes per worker count; report median and p95. Add `perf stat` counters for cycles, instructions, context switches, cache misses, and major/minor faults.

### 2. Trigram construction: generic hash lookup at nearly every input byte

**References**

- `src/watcher.zig:854-890`, `extractTrigramMasks`.
- `src/watcher.zig:895-920`, `readAndBuildTrigramShardWorker`.
- `src/watcher.zig:928-944`, `cachedTrigramBuildWorker`.
- `src/index.zig:1448-1461`, `TrigramIndex.insertBulkMapNew`.
- `src/watcher.zig:1077-1078`, `initialScanWithTrigrams`: capped at eight workers.
- `src/watcher.zig:1126-1150`: parallel read/build followed by serial shard merge.

**Why hot**

`extractTrigramMasks` advances one byte per iteration and performs normalization, twelve whitespace comparisons, packing, and `AutoHashMap.getOrPut` for every non-whitespace trigram. Workers reserve only 4,096 local entries (`src/watcher.zig:903-905`, `930-932`), then `insertBulkMapNew` performs another global hash lookup and append per unique trigram.

**Optimization opportunities**

1. Highest expected CPU win: replace the generic per-file `AutoHashMap(u24, PostingMask)` with specialized open addressing using inline 24-bit keys and masks.
2. Size local tables from content length or retained high-water mark; avoid rehashing above 4,096 unique trigrams.
3. Use a 256-byte normalization/whitespace LUT and maintain a rolling normalized window.
4. SIMD-normalize/classify 16–32 bytes at a time with `@Vector`; retain scalar hash insertion. SIMD packing alone is unlikely to matter while hashing dominates.
5. Pre-reserve shard/global index capacity before `insertBulkMapNew`.
6. Compare hash accumulation against radix-sort/unique of packed 24-bit trigrams for large files.
7. Replace serial shard merging with pairwise parallel reduction if merge profiling is material.

**Benchmark method**

Create a focused harness around `extractTrigramMasks` plus `insertBulkMapNew`, using fixed 4 KiB, 64 KiB, and 1 MiB source buffers. Measure:

- input GiB/s;
- ns/input byte;
- unique trigrams/s;
- allocations and bytes allocated/file;
- branch misses and L1/LLC misses.

For end-to-end validation, use `initialScanWithTrigrams` on warm-cache and cold-cache runs at 1/2/4/8 workers. Verify generated posting masks and search results byte-for-byte against baseline before accepting SIMD or custom-table changes.

### 3. Exact-word lookup allocates and copies the complete posting list on every query

**References**

- `src/benchmark.zig:100-110`, `benchWord`: allocation occurs inside the timed interval.
- `src/explore.zig:5369-5389`, `Explorer.searchWord`.
- `src/index.zig:525-560`, `WordIndex.searchDeduped`.
- `src/index.zig:526-528`: full-size result allocation.
- `src/index.zig:546,559`: shrinking `realloc`.
- `src/index.zig:548-558`: fallback hash-table allocation and second full pass.

**Why hot**

Every exact-word query allocates `hits.len` results, copies hits, and then reallocates to shrink. If posting order is violated, it additionally allocates and pre-sizes a hash table and hashes every hit. The benchmark deliberately repeats this work for `request`, `response`, `config`, and `error`.

**Optimization opportunities**

- Enforce and document the posting invariant `(doc_id, line_num)` sorted with adjacent duplicates; then deduplicate linearly.
- Return the original posting slice directly when already unique if API ownership can be represented as borrowed.
- Otherwise count unique adjacent hits first, allocate the exact result size, and copy once—avoiding shrink `realloc`.
- For callers needing only bounded results, add a capped API rather than materializing the complete list.
- Keep the hash fallback only for mutable/reused-ID states where ordering cannot be guaranteed.

**Benchmark method**

Use the built-in word rows with `CODEDB_BENCH_CALLOC=1`, but stratify fixtures by posting-list length: 0, 1, 10, 1,000, and 100,000 hits. Record p50/p95 ns/query, hits/s, allocations/query, and bytes/query. Compare sorted-unique, sorted-duplicate, and deliberately unsorted lists to ensure the fallback is not accidentally removed.

### 4. Symbol lookup performs repeated outline scans and multiple heap allocations per hit

**References**

- `src/benchmark.zig:113-123`, `benchSymbol`.
- `src/explore.zig:2825-2890`, `Explorer.findAllSymbols`.
- `src/explore.zig:2835-2843`: for every indexed location, linearly rescans that file’s symbols to recover detail.
- `src/explore.zig:2840,2845-2853`: duplicates detail, path, and query name separately for every result.
- `src/explore.zig:2863-2888`: incomplete-index fallback scans all files and symbols.

**Why hot**

For each location, lookup is effectively `O(symbols in containing outline)` before allocation. A common symbol such as `init` or `main` causes many small allocations. The benchmark times construction but at `src/benchmark.zig:121` only frees the outer result slice, so nested strings are not reclaimed during the run; that also biases later iterations through allocator growth/leak behavior.

**Optimization opportunities**

- Store a direct symbol ordinal or immutable detail reference in `SymbolLocation`; avoid rescanning the outline.
- Return borrowed interned names/paths/details where lifetime permits.
- Store compact result records and clone only at serialization/API ownership boundaries.
- Reserve `result_list` to `indexed_locs.len`.
- Ensure the symbol index is complete before timed iterations so the full-corpus safety scan is not mixed into steady-state latency.
- Correct the benchmark cleanup to free nested owned fields before using it for allocation comparisons.

**Benchmark method**

Benchmark symbols with 0, 1, 100, and 10,000 locations. Separate complete-index and forced-incomplete-index cases. Measure ns/location, allocations/location, bytes/location, p50/p95 latency, and resident-memory growth over 10,000 repetitions. Validate exact result ordering and ownership behavior.

### 5. Search measurement and result materialization can hide the actual candidate-scan cost

**References**

- `src/benchmark.zig:80-98`, `benchSearch`.
- `src/benchmark.zig:313-327`, `main`: disables whole-query caching for five rows.
- `src/explore.zig:3403-3420`, `Explorer.searchContent`: cached versus uncached dispatch.
- `src/benchmark.zig:85-89`: timing includes result and line-text allocation, while frees occur after the timer read.
- `src/benchmark.zig:91-95`: optional tier/candidate/rerank breakdown.
- `src/explore.zig:8754`, `fuzzyScoreBatch`: existing SIMD-across-files scorer.
- `src/explore.zig:5525-5547`: batched fuzzy scoring path.

**Why hot**

Uncached search is the primary latency path, but its reported average combines candidate selection, content access, matching, reranking, and result allocation. It excludes frees. That asymmetry makes allocation-reduction changes look better or worse depending on allocator behavior and obscures whether SIMD scoring is still material versus I/O/cache misses.

**Optimization opportunities**

- Extend the existing breakdown with candidate-content load time, scan time, scoring time, result-copy time, bytes read, cache-hit count, and allocations.
- Avoid cloning `line_text` until the final top-N set is known.
- Keep candidate IDs and scores in compact arrays; resolve paths/content only after pruning.
- Reuse per-query scratch buffers or an arena for transient candidates.
- Increase `fuzzyScoreBatch` lane width only after checking generated code on AVX2/AVX-512/NEON; benchmark scalar tails and short paths separately.
- Parallel search is only likely beneficial for large candidate sets; use a threshold and persistent pool to avoid thread-spawn overhead on microsecond queries.

**Benchmark method**

Use the built-in five uncached queries with:

```sh
CODEDB_BENCH_CALLOC=1 CODEDB_BENCH_BREAKDOWN=1 \
  zig build -Doptimize=ReleaseFast benchmark -- \
  --root <fixed-repo> --iterations 1000 --json
```

Report p50/p95/p99 rather than only mean, candidates/s, scanned MiB/s, allocations/query, and each tier’s share. Add controlled queries producing tiny, medium, and very large candidate sets. Compare one thread versus a persistent 2/4/8-thread pool; reject threading unless it improves p95 after scheduling overhead.
