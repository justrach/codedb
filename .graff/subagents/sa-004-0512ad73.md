1. `TrigramIndex.indexFile` changed from amortized append to sorted binary-search insertion.

# Ranked findings

## 1. Verified likely regression: incremental trigram indexing now pays sorted insertion costs

**Location:** `src/index.zig`, around `TrigramIndex.indexFile`, current lines approximately 1396–1410.

### Change

Old:

```zig
try idx_gop.value_ptr.items.append(self.allocator, .{
    .doc_id = doc_id,
    .next_mask = mask.next_mask,
    .loc_mask = mask.loc_mask,
});
```

New:

```zig
const posting =
    try idx_gop.value_ptr.getOrAddPosting(self.allocator, doc_id);
posting.next_mask = mask.next_mask;
posting.loc_mask = mask.loc_mask;
```

`getOrAddPosting` binary-searches a posting list and inserts at the correct position. Insertion may shift the tail of the `ArrayList`.

### Why this can regress

For every unique trigram in an incrementally indexed file:

- Old path: append, normally O(1) amortized.
- New path: O(log N) comparisons.
- If the doc ID belongs before existing entries: O(N) movement for the list tail.

The worst case is specifically enabled by free-ID reuse:

1. Remove an older, low-numbered document.
2. Reuse that low doc ID for a new file.
3. Insert it into many established posting lists.
4. Shift substantial portions of those lists.

This is on the watcher/update path through `Explorer.commitParsedFileAdoptOutline`. It can affect re-index latency, watcher catch-up, and interactive edits even if cold-build benchmarks are unchanged.

### Important context

This change appears **correctness-motivated**, not accidental. The old append could violate the posting-list sortedness invariant after doc-ID reuse, breaking binary search and persisted/mmap ordering.

Therefore “restore append” is not a valid optimization unless document IDs are made monotonic or unsorted delta postings are handled separately.

### Verdict

**Verified likely source-level regression**, especially for update/re-index workloads. It is not evidence of worse Zig 0.17 codegen.

### Targeted experiment

Construct a large index, remove low doc IDs, then repeatedly index files containing common trigrams. Measure separately:

- New highest doc ID, where insertion is effectively at the end
- Reused low doc ID, where tail movement is maximal
- Time in `getOrAddPosting`
- Bytes moved by insertion
- Allocations/reallocations

A benchmark that merely cycles ten files may not expose the worst case unless those files reuse low IDs and contain trigrams with long posting lists.

## 2. Likely regression or variance source: persistence now writes two files concurrently and delays both renames

**Location:** `src/index.zig`, `TrigramIndex.writeToDisk`.

### Change

HEAD wrote:

1. Postings temporary file
2. Flushed/closed it
3. Renamed postings into place
4. Created and wrote lookup temporary file
5. Renamed lookup into place

Dirty tree:

1. Opens postings and lookup temporary files together
2. Streams postings and lookup batches during the same traversal
3. Flushes both
4. Renames postings
5. Renames lookup

This removes the heap-resident `lookup_entries` array, which is a good RSS/allocation improvement. But it changes I/O behavior:

- Two buffered writers and two open files are active simultaneously.
- Writes alternate between postings and lookup every 4096 lookup entries.
- The lookup stream may disturb otherwise sequential postings writeback.
- Postings publication is delayed until lookup generation completes.
- There are now two random suffix generations before serialization.
- The stack frame gains roughly:
  - 256 KiB postings writer buffer
  - 64 KiB lookup writer buffer
  - ~32 KiB posting batch, depending on `DiskPosting`
  - ~48 KiB lookup batch
  - plus ordinary frame state

The prior code already held the compact lookup table in memory and wrote it as one contiguous block. On a fast SSD, eliminating that allocation may win; on some APFS/cache states, interleaving two output streams can lose slightly.

### Countervailing improvement

This is not an obvious net regression. It eliminates:

- `lookup_entries` growth reallocations
- Copies during `ArrayList` growth
- A later full lookup-table write from heap memory
- Memory proportional to trigram cardinality

It is likely a memory win and could be a speed win for large indexes. But it is a plausible explanation if the measured slowdown is specifically persistence completion.

### Correctness concern affecting benchmark comparability

The two final renames are still not an atomic pair. A failure after the postings rename but before the lookup rename exposes mismatched files. The old version had a similar mismatch window, but the changed ordering and timing alter its duration.

### Verdict

**Plausible workload-dependent source effect; not verified as slower.** Profile the persistence phase before blaming codegen.

### Targeted experiments

Compare:

- Wall time for posting construction
- Time spent in `write`
- Time spent in `flush`
- Rename latency
- Peak RSS and allocation bytes
- Cold versus warm APFS cache

Use a corpus with enough distinct trigrams for the removed lookup allocation to matter. Small repositories will mostly measure noise and filesystem scheduling.

## 3. Verified non-regression: local `mcp_json.zig` does not change the MCP hot path currently used

The migration removes the `mcp-zig` dependency and adds untracked `src/mcp_json.zig`. This initially looks suspicious because the old dependency contains several zero-allocation JSON scanners and a reusable line-buffer API that the local file omits.

However, comparing call sites in `src/mcp.zig` at HEAD and in the dirty tree shows the same used interface:

- `readLineBuf`
- `getStr`
- `getInt`
- `getBool`
- `eql`
- `writeEscaped`

Those implementations are materially the same as the cached old dependency. The omitted functions—`scanJsonRpc`, `scanStr`, `scanObj`, `readLineInto`, and related helpers—were not used by the current `mcp.zig` request loop at HEAD.

The request loop already performed:

```zig
std.json.parseFromSlice(std.json.Value, alloc, input, .{})
```

for each message, and `readLineBuf` already allocated a fresh `ArrayList`/owned slice per request.

### Verdict

**Refuted as an explanation for the current A/B slowdown.** Removing unused dependency code may reduce binary size or compile time, but does not explain request-time regression by itself.

### Still a high-value future optimization

The old dependency exposes exactly the optimization the server is not using:

- Reuse one line buffer with `clearRetainingCapacity`
- Scan JSON-RPC method/id/params without building a full `std.json.Value` tree
- Fully parse only requests whose handlers need decoded nested arguments

That is one of the strongest opportunities to beat the 0.16 binary on MCP-heavy workloads.

Also, `src/mcp_json.zig` is untracked. A benchmark of the current working tree is not reproducible from the patch alone until it is included in the compared source set.

## 4. No native arm64 regression expected from `@splat` migrations

Changes such as:

```zig
[_]bool{false} ** 256
```

to:

```zig
@as([256]bool, @splat(false))
```

occur in:

- Fuzzy search scratch arrays
- Pair-frequency tables
- Cache/test data
- Event queues and fixed-size rings
- Snapshot headers

These express the same initialization. For native arm64, LLVM should lower large zero initializations to stores or `memset` as appropriate.

Potential codegen differences should still be checked in the fuzzy batch path because some arrays are initialized on every call, but there is no source-level reason that `@splat` should add allocations, hashing, synchronization, or I/O.

### Verdict

**No identified regression.** It would be broken only if generated assembly showed lost vectorization or redundant stack initialization.

# Benchmark methodology problems

## The current CI JSON runner does not request a release optimization mode

`scripts/run-bench-json.py` invokes:

```text
zig build bench -- --json
```

It does not pass:

```text
-Doptimize=ReleaseFast
```

The build uses `b.standardOptimizeOption`, so absent an external default this measures a Debug benchmark executable, not the release binary. Debug results are particularly sensitive to safety checks and compiler implementation changes and should not be used to claim release-runtime parity.

The GitHub benchmark workflow shown in the diff calls that script unchanged.

### Consequence

A small regression reported by this benchmark may reflect:

- Debug codegen
- Safety/bounds-check implementation
- Build cache state
- Different source changes
- Filesystem cache
- CPU frequency/thermal state

It does not establish that the shipped `ReleaseFast` 0.17 binary is slower.

## The benchmark is also a mixed workload

The repo benchmark reports indexing, ranked searches, cached search, word lookup, symbol lookup, and re-index behavior. A single aggregate statement such as “slightly slower” hides whether the loss is in:

- Cold parse/index construction
- Trigram insertion
- Persistence
- Query candidate generation
- Rendering/JSON
- Process startup
- I/O

The source changes affect these phases differently.

# How to isolate compiler codegen from source effects

Use a four-cell experiment rather than old binary versus dirty binary:

| Source semantics | Zig 0.16 | Zig 0.17 |
|---|---:|---:|
| HEAD behavior | A | B |
| Dirty behavior | C | D |

Direct compilation may be impossible because the standard-library APIs changed. The useful comparisons are:

1. **A vs B:** same HEAD algorithms, minimal compatibility-only port to 0.17  
   This isolates compiler/std codegen as closely as practical.

2. **B vs D:** both built with Zig 0.17  
   This isolates dirty source changes.

3. **A vs C:** both built with Zig 0.16, if dirty algorithms can be backported  
   This confirms source effects independently.

4. **A vs D:** current end-to-end product comparison  
   Useful for users, but not causal diagnosis.

A compatibility port should preserve:

- The old append behavior for the diagnostic build, even if it retains the known correctness defect
- Old persistence staging
- Same dependency source revisions
- Same target triple and CPU model
- Same optimization mode
- Same strip/LTO/unwind settings
- Same benchmark corpus and query sequence

Do not use the behavior-preserving diagnostic build in production; it exists to isolate causality.

## Build controls

For every binary, record:

# Recommended macOS arm64 experiments and profilers

## 1. Stable statistical A/B

Use `hyperfine` if installed, or a small runner that:

- Alternates A/B/B/A order
- Performs warmups
- Runs at least 30–50 samples
- Reports median, p90, MAD, and confidence intervals
- Pins identical input snapshots
- Separates cold and warm filesystem-cache tests

Avoid running from `zig build`; execute already-built artifacts directly so compilation and build-runner overhead cannot leak into timing.

For sub-millisecond query benchmarks, benchmark many operations per process. Process startup noise otherwise dominates.

## 2. Instruments / `xctrace`

Available through Xcode Command Line Tools/Xcode:

- **Time Profiler:** CPU samples and call-tree deltas
- **Allocations:** allocation count, allocated bytes, persistent bytes
- **System Trace:** scheduling, blocking, syscalls, file I/O
- **File Activity:** persistence and snapshot behavior
- **Points of Interest / signposts:** useful if phase markers are later added

For this tree, first inspect:

- `TrigramIndex.getOrAddPosting`
- Array insertion/memmove
- `TrigramIndex.writeToDisk`
- `std.json.parseFromSlice`
- JSON response construction
- Hash-map lookup and growth
- Mutex/rwlock wait time
- `read`/`write` syscall frequency

Run:

```text
xcrun xctrace list templates
```

to see exact template names on the installed Xcode version.

## 3. Built-in sampling and memory tools

Useful low-friction tools:

- `sample <pid> <seconds> -file out.txt`
- `spindump`
- `vmmap <pid>`
- `heap <pid>`
- `leaks <pid>`
- `/usr/bin/time -l <command>`
- `fs_usage` for filesystem call patterns

`/usr/bin/time -l` is useful for:

- Peak resident set size
- Page faults
- Context switches
- Filesystem input/output counts

`fs_usage` can validate whether the new dual-file persistence path changes write/flush/rename behavior. It normally requires elevated privileges.

## 4. Allocation interception

Instruments Allocations is the preferred first choice. For focused tests, wrap the benchmark allocator with counters and report:

- Allocation count
- Resize count
- Free count
- Requested bytes
- Peak live bytes

Count allocator events around each phase rather than around the whole process. This will directly validate the expected lookup-table allocation reduction.

## 5. Assembly and LLVM IR comparison

Build small, stable benchmark roots around specific hot functions and emit:

- Assembly
- LLVM IR
- Object files

Compare:

- Bounds-check branches
- Vectorized loops
- Calls to `memcpy`/`memmove`/`memset`
- Inlining of integer hash functions
- Atomic instruction sequences
- Stack-frame size
- Indirect I/O dispatch

Whole-binary symbol comparison is less useful because Zig monomorphization and symbol naming can shift substantially between versions. Function-sized benchmark roots produce cleaner evidence.

On Apple silicon, inspect with:

```text
otool -tvV binary
nm -nm binary
size binary
```

Release stripping may remove useful symbols, so retain a profiling build with release optimization but debug symbols.

# Optimizations most likely to beat the 0.16 binary

## 1. Add a fast MCP dispatch path and reuse the input buffer

**Highest likely win for MCP request throughput.**

The current loop:

- Allocates an owned line for every request
- Parses the complete request into `std.json.Value`
- Builds object maps and decoded strings even to discover `method` and `id`

The removed dependency already had prototypes for:

- `readLineInto` with retained capacity
- `scanJsonRpc`
- `scanStr`
- `scanInt`
- `scanObj`
- `scanBool`

A robust local equivalent could:

1. Reuse one request buffer.
2. Zero-allocation scan method/id/params boundaries.
3. Dispatch `ping`, notifications, and simple calls without a full tree.
4. Parse only the `arguments` object when required.
5. Preserve proper JSON string unescaping and validation where handlers need decoded strings.

This should reduce both allocation traffic and hash-map construction. Validate correctness carefully: naive raw scanners often mishandle escapes, nested arrays/objects, duplicate keys, and braces inside strings.

## 2. Preserve sorted posting correctness without repeated middle insertion

For incremental trigram updates, consider one of:

- **Monotonic doc IDs:** do not reuse IDs; compact only during rebuild/persistence.
- **Main sorted postings plus small unsorted delta:** search both, periodically merge.
- **Per-file collection followed by batched merge:** sort new `(trigram, doc_id)` records and merge posting lists once.
- **Tombstones:** avoid immediate deletion/reinsertion movement and compact later.

The simplest likely speed win is monotonic IDs plus tombstones, provided memory growth is bounded and persistence remaps live documents. It restores append behavior while maintaining sorted order.

A delta structure is more complex but may give the best interactive update latency.

## 3. Make persistence writes sequential again without restoring unbounded lookup memory

The dirty implementation’s bounded memory is desirable. Possible refinements:

- Generate lookup entries into a bounded temporary/mmap file while writing postings sequentially.
- Avoid alternating output streams in the inner trigram loop.
- Increase lookup batches enough to reduce interleaving while retaining a strict memory cap.
- Measure whether 4096 entries is the correct batch size on APFS.
- Close/flush temporaries explicitly before rename and publish through a generation/manifest file if pair consistency matters.

Do not optimize this until File Activity/System Trace shows the dual-stream schedule matters.

## 4. Pre-size hot maps and result buffers from known counts

Likely targets include:

- Search aggregation maps
- Dedup maps in word/prefix searches
- Trigram/symbol result buffers
- JSON response arrays
- Per-file local trigram maps

Where an upper bound or prior candidate count is available, use capacity reservation once rather than growth. Confirm with allocator counters; speculative over-reservation can increase RSS and cache misses.

## 5. Reduce copies in result rendering

Search results commonly duplicate paths and line text and then serialize them. Potential wins:

- Borrow stable path slices while the explorer read lock is held.
- Write JSON directly into the transport writer where protocol framing permits.
- Reserve from estimated result size.
- Avoid constructing an intermediate escaped string and then copying it again.

This is especially promising for MCP calls returning large search/read payloads.

## 6. Separate benchmarkable cold-build and incremental-update paths

The code already has lean bulk insertion. Ensure cold scans always select it and never fall through the correctness-heavy incremental path.

Instrument counts of calls to:

- `bulkInsert`
- `indexFile`
- `getOrAddPosting`
- `ArrayList.insert`

If cold build unexpectedly invokes `indexFile` frequently, fixing dispatch would likely exceed any compiler-level gain.

## 7. Verify fuzzy-search vector codegen before source tuning

The fuzzy batch path uses vectors but constructs transposed scratch arrays and performs lane-filling loops. Compare 0.16/0.17 assembly for:

- Vector loads/stores
- Scalarized comparisons
- Stack spills
- Repeated bounds checks
- Initialization of `lo`, `orig`, and `wbf`

Only act if assembly or Time Profiler points there. The migration syntax itself is not evidence of a regression.

## Final skeptical verdict

- **“The 0.17 compiler is slightly slower” — refuted by confounding source changes and inadequate isolation.**
- **“The dirty tree can be slower” — survives.** The strongest concrete counterexample is incremental trigram indexing after low doc-ID reuse, where append became binary-search insertion with possible O(N) tail movement per trigram.
- **Most likely route to beat 0.16:** eliminate MCP full-tree parsing/per-request line allocation and redesign incremental postings so correctness does not require repeated middle insertion.
