## Findings

### High — “Response parity” does not hash the actual MCP response  
**`src/mcp.zig:547`, response assembled at `src/mcp.zig:552-587`**

`response_hash` is computed from `out.items` immediately after `dispatch`, before the client-visible MCP response is assembled. The actual response additionally contains:

- generated summary text,
- guidance,
- JSON escaping,
- content-item framing,
- `isError`.

Concrete failure sequence:

1. A candidate changes `mcpGenerateSummary`, `mcpGenerateGuidance`, `mcpj.writeEscaped`, response framing, or `isError` construction.
2. `dispatch` still produces identical `out.items`.
3. Line 547 produces the same hash for base and candidate.
4. The paired comparator reports output parity `PASS`.
5. Production clients receive different—or potentially malformed—MCP responses.

This defeats the stated response-parity guarantee. Hashing the full response requires excluding or canonicalizing only the genuinely nondeterministic duration field; hashing the pre-response dispatch buffer is not response parity.

### Medium — Only the final iteration participates in parity checking  
**`src/bench.zig:183-197`, especially `src/bench.zig:191`**

Every iteration overwrites `response_hash`; only the final invocation is emitted.

Concrete failure sequence:

1. Base and candidate differ on cold-cache behavior, an early state transition, or iterations 1–99 of a 100-iteration case.
2. By the final invocation, both produce the same output.
3. Line 191 overwrites all earlier hashes with the final matching hash.
4. The benchmark reports parity `PASS`, despite measuring timings that included behaviorally non-equivalent calls.

This is particularly relevant because one `BenchContext`, `Store`, and `Explorer` are reused across iterations and cases. A rolling hash of every iteration, or an immediate per-iteration equality check in the paired protocol, is needed to substantiate parity over the measured workload.
