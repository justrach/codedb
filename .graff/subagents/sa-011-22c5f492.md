## Release blockers

### 1. `--require-parity` still permits tools to opt out of parity entirely

**References**

- `scripts/compare-bench-paired.py`, `compare()`, approximately lines 105–129
- `scripts/test_compare_bench_paired.py`, `test_parity_opt_out_is_explicit`
- `src/bench.zig`, `Case.parity` and the `codedb_status` / `codedb_snapshot` cases

The comparator defines parity as enabled only when every sample on both sides says `parity: true`:

```python
parity_enabled = all(
    bool(base[tool].get("parity", False))
    and bool(head[tool].get("parity", False))
    for base, head in mapped
)
```

With `--require-parity`, a tool for which both sides report `parity: false` is marked `SKIP` and causes no failure. The unit test explicitly locks in this behavior:

```python
self.assertIn("SKIP", report)
self.assertEqual([], failures)
```

That means “require parity” does **not** require parity for every benchmark case. A shared harness change, or a newly introduced case disabled on both revisions, can bypass output checking while retaining an overall successful comparator exit.

The current report uses this exemption for:

- `codedb_status`
- `codedb_snapshot`

Their raw hashes happen to match in the inspected samples, but the gate does not enforce that. The claimed exceptions are justified only by comments and mutable benchmark metadata; there is no comparator-owned allowlist of approved exemptions.

**Counterexample:** one can set `parity: false` for a tool in both inputs, give base and head different `response_hash` values, run with `--require-parity`, and receive no failure. The repository’s own test demonstrates exactly this.

**Required before release:** make parity exemptions an explicit comparator/CI allowlist, reject all other opt-outs, and preferably enforce the hashes for these two cases after normalizing the known nondeterministic fields.

### 2. The persisted 20-pair evidence contains no provenance or order data

**References**

- `zig-out/bench-ab-release-0.2.5830/base-01.json` through `base-20.json`
- `zig-out/bench-ab-release-0.2.5830/head-01.json` through `head-20.json`
- `scripts/compare-bench-paired.py`, `paired_files()` and report header
- `zig-out/bench-ab-release-0.2.5830/report.md`, “counterbalanced by the runner”

Each raw JSON sample records:

- `repo_root`
- temporary `corpus_root`
- corpus hash/count/bytes
- tool results

It does **not** record:

- source commit SHA;
- whether the sample is baseline or candidate;
- compiler version/hash;
- build mode;
- invocation timestamp;
- pair number inside the payload;
- execution sequence/order;
- production baseline SHA versus harness SHA.

Consequently, the files themselves cannot prove they were generated by `24e89c7` and `33ea66c`, using the stated compiler, or in AB/BA order. Filenames can be renamed or populated from arbitrary builds.

Worse, the comparator prints:

```text
Pairs: 20 (counterbalanced by the runner)
```

without inspecting any order metadata. `paired_files()` merely matches `base-NN.json` and `head-NN.json`. Twenty base-then-head runs, twenty head-then-base runs, or duplicated samples all receive the same “counterbalanced” statement.

**Counterexample:** copy any valid base/head payloads into correctly named files in arbitrary execution order. The comparator reports them as counterbalanced and returns success.

This blocks the documentation claims in:

- `CHANGELOG.md`: “The release gate ran 20 counterbalanced AB/BA pairs…”
- `docs/performance-0.2.5830.md`: “Twenty AB/BA-counterbalanced pairs passed”
- `docs/bench-0.2.5830-paired-report.md`: pinned baseline/candidate/compiler/order metadata

Those statements may describe how the run was performed, but the persisted evidence cannot verify them.

**Required before release:** emit and validate immutable provenance in every sample—commit SHA, compiler, corpus-source SHA/hash, side, pair ID, and sequence/order—and reject samples inconsistent with the expected manifest.

### 4. “Exact `dd36e94` corpus” overstates what the fingerprint proves

**References**

- `src/bench.zig`, `corpus_files`
- `src/bench.zig`, `copyCorpus()`
- `src/bench.zig`, `hashCorpus()`
- `docs/performance-0.2.5830.md`, paired release gate
- `docs/bench-0.2.5830-paired-report.md`, Corpus field

The paired benchmark does not copy or hash the complete `dd36e94` worktree. It hashes a fixed allowlist of 21 files, copies those files, and then creates `src/bench_target.zig`, producing the reported 22-file corpus.

Thus the shared hash `13647708728832762745` proves parity for that selected synthetic benchmark corpus—not the complete production-baseline repository. Unlisted files, ignored files, symlinks, executable bits, repository metadata, and other corpus state do not participate.

The wording:

> “the exact `dd36e94` corpus”

and:

> “immutable production-baseline worktree shared by both binaries”

is too broad. The worktree is the **source used to construct an allowlisted 21-file corpus**, not the corpus itself.

**Required before release:** either describe it accurately as the fixed 21-file benchmark corpus copied from `dd36e94`, or fingerprint/copy the complete intended corpus.

### Rolling iteration parity is implemented

`src/bench.zig`, `runCase()`, folds every iteration’s `response_hash` into a rolling Wyhash. Therefore the final hash is not merely the last response.

The underlying hash is built from a duration-normalized MCP content envelope wrapped in a JSON-RPC result envelope. This supports parity for the synthesized response bytes. It is not an independent capture of actual stdio traffic, but it does cover every measured in-process iteration for parity-enabled cases.

### Comparator arithmetic matches its documented policy

The comparator uses:

- per-pair percentage deltas;
- median paired percentage;
- median absolute paired delta;
- deterministic bootstrap median CI;
- conjunctive regression threshold:
  - percentage above threshold **and**
  - absolute delta above threshold.

No single-run minimum is used.
