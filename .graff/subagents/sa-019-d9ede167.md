### Verified path

1. `mainImpl` creates the shared threaded I/O object, allocator, `Store`, and `Explorer`; its normal bootstrap call site is `bootstrap.coldLoadOrScan` at `src/main.zig:448`. However, `coldLoadOrScan` immediately returns for `cmd == "mcp"`, so it is **not** the actual MCP cold-indexing path. [src/main.zig:L130-L140; src/main.zig:L417-L421; src/main.zig:L448; src/bootstrap.zig:L387]

2. `commands.runMcp` is the MCP bootstrap owner. For an explicit root it:
   - gets Git HEAD;
   - synchronously attempts `loadBestSnapshot`;
   - starts `background.scanBg` if no valid snapshot loads;
   - starts `watcher.incrementalLoop`;
   - enters `mcp_server.run`.  
   [src/commands.zig:L453-L468; src/commands.zig:L488-L489]

   For an implicit-CWD root, it defers the root decision until the MCP roots handshake; `triggerScanFromRoots` then performs the same snapshot-or-`scanBg` decision. [src/commands.zig:L434-L451; src/background.zig:L203-L225]

3. Snapshot eligibility is Git-HEAD based. `loadBestSnapshot` tries `<root>/codedb.snapshot`, then the central snapshot; each candidate first reads its 44-byte-ish header/HEAD and only deserializes if it matches the current HEAD. [src/bootstrap.zig:L37-L53; src/bootstrap.zig:L56-L75; src/snapshot.zig:L503-L523]

4. On a cold MCP start, `scanBg`:
   - checks the on-disk trigram header/HEAD;
   - sets `word_index.skip_file_words = true`;
   - calls `watcher.initialScan(..., skip_trigram=true)`;
   - persists the word index;
   - either loads a matching trigram index or builds trigrams from `Explorer.contents`, writes them, and mmaps them;
   - sets `scan_done` and MCP scan state to `ready`;
   - **then** emits a snapshot and may release cache/index memory.  
   [src/background.zig:L35-L58; src/background.zig:L73-L98; src/background.zig:L130-L186; src/background.zig:L190-L201]

5. `initialScan` uses up to `min(cpu_count, 8)` workers unless `CODEDB_SCAN_WORKERS` overrides it. Its initial collector serially walks/filter paths, duplicates every path, then runs a separate stat-and-`Store.recordSnapshot` phase. [src/watcher.zig:L527-L599; src/watcher.zig:L1179-L1189]

6. The scan workers parse files concurrently, but the main thread commits their results to shared `Explorer` structures serially and in static worker/chunk order. Each commit acquires `Explorer.mu`, updates outlines/content/dependencies/symbol index, and duplicates content into `ContentCache`. [src/watcher.zig:L762-L824; src/watcher.zig:L663-L688; src/explore.zig:L1511-L1615; src/hot_cache.zig:L151-L231]

7. Cold search-dependent MCP tools wait for `ready` using a 25 ms polling loop (up to the configured timeout); therefore initial-scan, word persistence, trigram build/write/mmap are directly on the cold-search critical path. Snapshot writing is not, because readiness is published first. [src/mcp.zig:L808-L815; src/mcp.zig:L1436-L1444; src/background.zig:L185-L195]

## Ranked candidate changes

Impact rankings are hypotheses, not measured results. The suggested benchmarks should be run on both a many-small-file repository and a byte-skewed repository, with a deleted project cache/snapshot for each cold trial.

### 1. Stream trigram persistence instead of materializing the complete postings blob
**Expected impact: High peak-RSS reduction; medium-to-high cold-ready latency improvement on large trigram indexes.**

**Evidence.** `TrigramIndex.writeToDisk` first creates:
- a complete file table plus a path→disk-ID hash map;
- a `doc_to_disk` array;
- sorted trigram keys;
- a complete `postings_buf`;
- a complete `lookup_entries` buffer.  
Only after fully building `postings_buf` does it write the postings file. [src/index.zig:L1721-L1800] The MCP scan cannot publish `ready` until `writeToDisk` completes and the written index is remapped/adopted. [src/background.zig:L154-L186]

**Concrete change.** In `TrigramIndex.writeToDisk` (`src/index.zig:L1721-L1879`), retain sorted trigram keys and the small lookup table, but write each posting list directly into the temporary postings writer while tracking a running `u32` posting offset. This removes `ArrayList(DiskPosting) postings_buf`; the lookup record can be appended per trigram. If lookup entries are also material at very large cardinalities, write a temporary lookup stream or pre-size/write it after counts are known.

**Correctness risks.**
- Preserve exactly the existing sorted-trigram order and every posting-list order.
- Validate `u32` posting offsets/counts before serialization.
- Keep the two-file atomicity failure semantics: the current code atomically renames postings and lookup independently, so changing write order needs compatibility validation with the mmap loader.
- Do not mutate heap posting lists while serializing.

**Minimal benchmark.**
1. Cold-start MCP with no snapshot and no trigram disk files.
2. Record time from MCP initialization to the first index-dependent `codedb_search` response; capture peak RSS.
3. Compare `trigram write` time and total ready time using existing `CODEDB_INDEX_PROFILE`; the build already exposes distinct trigram-build/write/mmap phases in the CLI profile path. [src/bootstrap.zig:L549-L568; src/bootstrap.zig:L612-L622]
4. Verify identical search candidate/result sets and successful mmap reload on the next process.

### 2. Eliminate the scan pipeline’s full-content copy and long-lived worker arenas
**Expected impact: High peak-RSS reduction and medium scan CPU/allocation reduction.**

**Evidence.** Every scan worker reads content into its persistent result arena, parses it, then copies its outline into a libc-owned packed outline before publishing. [src/watcher.zig:L629-L660] The main-thread commit calls `ContentCache.put`; `put` duplicates both a new key and, for owned content, the complete content value. [src/explore.zig:L1608-L1611; src/hot_cache.zig:L219-L230] Worker result arenas are deinitialized only after the ordered commit and shard merge stage, rather than after each individual file is consumed. [src/watcher.zig:L750-L759; src/watcher.zig:L807-L824]

**Concrete change.**
- Add an ownership-transfer path to `ContentCache` (for example, `putOwned`) and a scan result representation whose content allocation can be handed directly to the cache.
- Allocate scan content in individually freeable blocks from the cache/Explorer allocator rather than from a worker-wide arena. On cache refusal/eviction, free that block immediately.
- Similarly, parse outlines directly into an adoptable packed representation, avoiding `cloneOutlinePackedBorrowingPath`’s size pass, allocation, and string copies. That helper explicitly totals all symbol/import bytes, allocates storage, then copies each string. [src/explore.zig:L2592-L2647]

**Correctness risks.**
- `ContentCache` has a byte budget and an entry-size cap; the transfer path must free rejected/evicted owned allocations exactly once. [src/hot_cache.zig:L151-L158; src/hot_cache.zig:L209-L230]
- `Explorer.commitParsedFileAdoptOutline` assumes ownership of the adopted outline, whereas the current cache copies content. Define ownership at all error exits before changing either behavior. [src/explore.zig:L1511-L1516; src/explore.zig:L1608-L1615]
- Do not accidentally retain content for files intentionally too large for the cache.

**Minimal benchmark.**
1. Cold MCP scan on a repository whose indexed contents exceed the content-cache byte budget.
2. Measure ready latency, allocator bytes/allocations, and peak RSS.
3. Assert scan file count, content cache hit/miss behavior, outline/symbol counts, word results, and substring results match baseline.
4. Repeat under forced parse/commit error injection if a suitable existing test seam exists.

### 3. Replace static file-count chunking and ordered worker draining with size-aware scheduling
**Expected impact: High on repositories with generated/minified/large-file skew; low on uniformly sized source trees.**

**Evidence.** The collector records file size before scanning. [src/watcher.zig:L515-L524] But scan worker chunks are equal **numbers of files**, not bytes or estimated parse cost. [src/watcher.zig:L776-L793] Trigram-cache build and frequency counting use the same equal-file static partitioning. [src/watcher.zig:L997-L1011; src/index.zig:L3305-L3316] The scan consumer drains every result from worker 0 before worker 1, etc.; an early slow chunk can therefore delay commits even when later workers already have ready results. [src/watcher.zig:L795-L809]

**Concrete change.**
- Sort or bin `InitialScanEntry` work by `size` into balanced byte-cost chunks, preserving a separately assigned discovery ordinal.
- Use a bounded shared work queue or per-worker work stealing for parse/trigram/frequency stages.
- Commit available files in original ordinal order only if that ordering is semantically required; otherwise drain globally ready results. A reorder buffer keyed by ordinal retains deterministic commit order while avoiding coarse static chunk imbalance.

**Correctness risks.**
- Existing comments explicitly preserve chunk order for symbol precedence, cache eviction, dependency output, persistence, and doc-ID assignment. The replacement must either retain discovery-order commit/merge semantics or deliberately version/test any ordering-dependent output. [src/watcher.zig:L795-L797; src/watcher.zig:L669-L674]
- Word-index shard document IDs and trigram shard merge offsets depend on stable chunk/order handling. [src/index.zig:L1455-L1488]
- A queue must not allow unbounded parsed-content buffering when the single commit spine is slower than parsing.

**Minimal benchmark.**
1. Build a fixture with 90–95% tiny files and a handful of files near the 1–2 MB indexing limits.
2. Compare workers=1, baseline workers=8, and size-aware workers=8.
3. Measure time to `ready`, worker idle time, p95 per-worker completion, and result equivalence against workers=1.
4. Repeat separately for `buildTrigramsFromCache` and `buildFrequencyTableFromMapParallel`.

### 4. Remove per-file root-directory opens in parallel parse/trigram workers
**Expected impact: Medium on high-file-count repositories and metadata-latent filesystems; likely small on warm local SSDs.**

**Evidence.** `parseInitialScanEntry` opens and closes the root directory for every file before reading it. [src/watcher.zig:L602-L612] The trigram-only cold-search worker does the same within its per-file loop. [src/watcher.zig:L849-L860] These paths already partition files by worker, so each worker can safely own a directory handle rather than opening the same root thousands of times.

**Concrete change.**
- Open one root directory per scan worker in `initialScanWorker`; pass `*Dir` to a parse helper.
- Do the same in `readAndBuildTrigramShardWorker`.
- Retain the current per-worker ownership rather than sharing a `Dir` handle across worker threads.

**Correctness risks.**
- Confirm Zig’s directory iterator/file-open semantics and symlink behavior remain unchanged when a handle lives for a whole worker.
- Maintain the current behavior if a directory becomes unavailable during a scan: individual file failures are currently skipped.
- Avoid extending a directory-handle lifetime past worker join.

**Minimal benchmark.**
1. Cold-scan a fixture with 50k+ small eligible files, with word indexing disabled/enabled separately.
2. Measure root `openDir` syscall count and scan time; compare local disk and a network/container-mounted workspace if available.
3. Verify symlink-focused existing initial-scan tests still pass; the repository already has sequential symlink scan coverage. [callers of `initialScanWithWorkerCount`: src/test_explore.zig:L1868-L1968]

### 5. Batch `Store.recordSnapshot` during the parallel stat pass
**Expected impact: Medium-to-high for very many files; depends on mutex contention and allocator cost.**

**Evidence.** The collector parallelizes `statFile`, but each stat worker immediately calls `store.recordSnapshot`. [src/watcher.zig:L515-L524; src/watcher.zig:L546-L590] `recordSnapshot` reaches `Store.appendVersion`, which takes the single `Store.mu`, increments the global sequence, inserts/duplicates the path, appends a version, and may compact the log. [src/store.zig:L79-L144] Thus the stat phase’s state updates serialize even though filesystem stats fan out.

**Concrete change.**
- Have each stat worker fill a worker-local `(path, size)` result slice.
- After joins, batch-insert them under either one lock acquisition or a dedicated `Store.recordSnapshotsBulk` that reserves/preallocates map/version capacity and applies entries in discovery order.
- Keep file stats parallel; only the state publication is batched.

**Correctness risks.**
- Current sequence ordering across stat worker chunks is scheduling-dependent; changing it to discovery order may be observable through `changesSince`. That is likely an improvement, but it must be treated as behavior and tested.
- Preserve error handling: current workers stop after a shared `build_err` is set. [src/watcher.zig:L515-L523]
- Ensure no concurrent MCP mutation can observe a partially published startup baseline.

**Minimal benchmark.**
1. Use a many-small-file cold start; run workers=1 and workers=8.
2. Instrument/measure lock wait and total collector phase time (`scan` profiling already separates collection from parse/commit). [src/watcher.zig:L832-L842]
3. Verify `Store.currentSeq`, file count, and per-file latest snapshot size after the scan.

### 6. Make word-index shard merge a measured next target; avoid premature redesign
**Expected impact: Medium to high if profile shows merge dominance; otherwise low.**

**Evidence.** Worker-local word shards remove tokenization from the serial commit path, but all shards are merged under one exclusive `Explorer.mu` section after worker join. [src/watcher.zig:L762-L770; src/watcher.zig:L813-L820] `WordIndex.mergeShard` duplicates each path and each new term, remaps every posting’s document ID, and appends postings to global lists. [src/index.zig:L391-L439] This is necessarily serial in the current representation and occurs before `scanBg` can persist the word index and proceed to trigram readiness. [src/background.zig:L73-L75]

**Concrete change.**
- First split profiling into word-shard build vs merge; current profile combines merge and worker-result cleanup into `merge_free`. [src/watcher.zig:L825-L842]
- If merge is material, partition the final word index by stable term-hash range so shard merges for disjoint ranges can run in parallel, or merge one shard at a time with pre-reserved destination capacity and bulk posting transfers where ownership permits.
- A smaller, lower-risk first step is to precompute/reserve global document and term capacities before taking `Explorer.mu`.

**Correctness risks.**
- Search expects one global index and stable doc IDs; partitioning requires a query fan-out/merge layer or an internal partition abstraction.
- Existing `mergeShard` uses allocator ownership and duplicates path/term keys deliberately; transferring memory without matching allocators would create invalid frees. [src/index.zig:L391-L439]
- Do not expose a partially merged index to readers; the current exclusive lock gives that guarantee. [src/watcher.zig:L813-L819]

**Minimal benchmark.**
1. Enable `CODEDB_INDEX_PROFILE` on a vocabulary-heavy repository.
2. Compare scan time with word index enabled vs disabled, and workers 1/4/8.
3. Add separate timings for shard tokenization, global merge, and `writeToDisk`.
4. Require identical word postings/results and on-disk mmap reloads.

### 7. Avoid the watcher’s immediate second full walk/stat after a cold scan
**Expected impact: Low for readiness, medium for post-ready I/O contention and startup work.**

**Evidence.** `incrementalLoop` waits for `scan_done`, then creates its known-file snapshot by walking every file and calling `statFile` again. [src/watcher.zig:L1206-L1237] `scanBg` sets `scan_done`/MCP `ready` before snapshot persistence, so this second walk is not part of the nominal ready transition, but it starts immediately while users can issue searches. [src/background.zig:L185-L195]

**Concrete change.**
- Return or publish the initial scan’s `(path, mtime, size)` records to `incrementalLoop` and use them to initialize `known`.
- After seeding, perform one reconciliation pass for files modified/created/deleted during the scan window, rather than blindly restatting every file.

**Correctness risks.**
- The current second walk is a simple correctness boundary against changes occurring during initial indexing. A handoff design must define an event/watermark ordering and reconcile changes that occur before the watcher becomes active.
- Preserve ignored-path, symlink, and branch-switch behavior from `FilteredWalker`.

**Minimal benchmark.**
1. Cold start on a 50k-file workspace and measure filesystem stats/walk count until 10 seconds after readiness.
2. Concurrently modify/create/delete files during scanning; verify the final `known` map and Explorer converge to a full post-scan walk.
3. Measure first-query latency under concurrent watcher initialization.

## Verified observations vs. hypotheses

### Verified
- MCP’s cold path is snapshot load → background `initialScan` → word persistence → trigram build/write/mmap → `ready`; snapshot writing follows `ready`. [src/commands.zig:L453-L468; src/background.zig:L73-L201]
- The scan has parallel parsing but a serial `Explorer` commit spine, static equal-file chunks, and ordered per-worker draining. [src/watcher.zig:L762-L824]
- Scan results currently copy outline data and duplicate cached content; worker arenas retain parsed data until late cleanup. [src/watcher.zig:L629-L660; src/explore.zig:L1608-L1611; src/hot_cache.zig:L219-L230]
- Trigram persistence materializes the complete disk postings representation in RAM before writing it. [src/index.zig:L1773-L1846]
- The initial stat pass serializes `Store` mutations behind `Store.mu`, despite parallel stats. [src/watcher.zig:L515-L590; src/store.zig:L79-L144]
- The watcher repeats a full walk/stat after cold scan completion. [src/watcher.zig:L1206-L1237]

### Hypotheses requiring measurement
- The trigram postings buffer and scan-result copy path are likely the largest remaining RSS/allocation wins, but their actual contribution depends on repository size, trigram cardinality, and cache-budget eviction.
- Size-aware scheduling should materially help skewed repositories, but may not help uniform source trees.
- `Store.mu` contention may be minor if `statFile` dominates; lock-wait profiling should decide whether batching is worthwhile.
- Word-shard merge may be a significant serial bottleneck, but existing instrumentation does not isolate it sufficiently.

## 3 most load-bearing facts

1. **MCP readiness is blocked by scan, word-index persistence, trigram build/write/mmap—not snapshot writing.** [src/background.zig:L73-L195; src/mcp.zig:L1436-L1444]  
2. **The parallel initial scan still funnels every parsed file through serial, locked Explorer commit work and ordered static chunks.** [src/watcher.zig:L776-L824; src/explore.zig:L1511-L1615]  
3. **Trigram disk persistence constructs a whole in-memory postings blob before writing, directly before readiness.** [src/index.zig:L1773-L1846; src/background.zig:L154-L186]
