## Ranked concrete changes

### 1. Avoid creating and joining a new OS thread for every ordinary CLI invocation

**Symbols:** `mainTrampoline`, `mainInner`  
**Location:** `src/main.zig:73-76`, `src/main.zig:110-115`  
**HEAD comparison:** identical at `git show HEAD:src/main.zig:73-76,110-115`

Current startup always:

1. allocates an 8 MiB stack in release builds,
2. creates an OS thread,
3. runs all real work there,
4. joins it immediately.

```zig
const thread = try std.Thread.spawn(.{ .stack_size = stack_size }, mainInner, .{});
thread.join();
```

The only invocations exempted are the no-argument/version fast paths handled before `mainTrampoline` (`src/main.zig:58-62,84-107`).

**Concrete change:** Run `mainImpl` on the initial thread for ordinary CLI/query commands. Retain the large-stack worker only for commands demonstrably needing it—likely indexing, daemon/server, MCP, or specific deeply recursive parsing paths. A conservative first version could parse only enough raw argv to choose between direct CLI execution and the large-stack path.

**Why it should measurably help:** Thread creation/join, stack reservation, TLS setup, and scheduler interaction are fixed process-startup costs. They are unusually large relative to a short cold CLI search and directly match both reported regressions. This is the strongest candidate for recovering most or all of the ~3% startup delta.

**Behavior risks:**

- The trampoline likely exists to protect against stack exhaustion in parsing/indexing. Running all commands on the initial stack without auditing stack use is not low risk.
- Command dispatch before full parsing must preserve root/command ambiguity and global-option behavior.
- Error reporting currently differs between `mainTrampoline` and `mainInner` (`src/main.zig:62-69,110-114`).

**Risk-controlled implementation shape:** Keep the worker for `index`, `snapshot`, `serve`, `mcp`, and `cli-daemon`; initially bypass it only for read-only query commands with a known snapshot-backed path. Validate with a deliberately small process stack and the largest supported files.

### 2. Stop duplicating every argv string after argv has already been materialized

**Symbols:** `bootstrapArgs`, `argsAlloc`, `main`, `mainImpl`  
**Locations:** `src/cio.zig:482-490,494-517`; `src/main.zig:58-60,148-149,156-189`  
**HEAD comparison:** identical at `git show HEAD:src/cio.zig:452-487`

Startup first obtains a process-lifetime argv vector:

```zig
const argv = cio.bootstrapArgs(init.args);
cio.setProcessArgs(argv);
```

Then `mainImpl` allocates a new argv slice and separately allocates/copies every string:

```zig
const raw_args = try cio.argsAlloc(allocator);
```

`argsAlloc` performs one allocation for the slice and one allocation plus memcpy per argument (`src/cio.zig:499-515`). The global-option filter then builds another pointer list and converts it to an owned slice (`src/main.zig:156-189`).

On Windows, `bootstrapArgs` itself already calls `args.toSlice(page_allocator)` and allocates another pointer array that intentionally lives for the process lifetime (`src/cio.zig:483-489`).

**Concrete change:** Pass the bootstrap argv slice into the real entry point and parse borrowed `[]const u8` spans directly. Allocate only the filtered pointer array when global options actually need removal—or use a small stack-backed array for normal argument counts.

**Why it should measurably help:** This removes `argc + 1` heap allocations, per-argument memcpy, corresponding frees, and one avoidable pointer-array allocation from every non-fast invocation. It is a small absolute cost but is exactly the kind of fixed allocator work that can explain a low-single-digit startup shift.

**Behavior risks:**

- Borrowed argv lifetime must remain valid until command completion. On POSIX it is runtime-owned; Windows currently intentionally leaks the bootstrap representation for process lifetime (`src/cio.zig:482-490`).
- Some downstream code may implicitly depend on writable or sentinel-terminated argument slices, even though the visible parser APIs accept `[]const []const u8` (`src/cli_args.zig:46,167`).
- macOS currently obtains argv independently through `_NSGetArgv` in `argsAlloc` (`src/cio.zig:495-510`), so the borrowed representation should be tested there.

## 1. Verified likely regression: incremental trigram indexing now pays sorted insertion costs

**Location:** `src/index.zig`, around `TrigramIndex.indexFile`, current lines approximately 1396–1410.

### Change

Old:

```zig
try idx_gop.value_ptr.items.append(self.allocator, .{
    .doc_id = doc_id,
    .next_mask = mask.next_mask,
    .loc_mask = mask.loc_mask,
});
```

New:

```zig
const posting =
    try idx_gop.value_ptr.getOrAddPosting(self.allocator, doc_id);
posting.next_mask = mask.next_mask;
posting.loc_mask = mask.loc_mask;
```

`getOrAddPosting` binary-searches a posting list and inserts at the correct position. Insertion may shift the tail of the `ArrayList`.

### Why this can regress

For every unique trigram in an incrementally indexed file:

- Old path: append, normally O(1) amortized.
- New path: O(log N) comparisons.
- If the doc ID belongs before existing entries: O(N) movement for the list tail.

The worst case is specifically enabled by free-ID reuse:

1. Remove an older, low-numbered document.
2. Reuse that low doc ID for a new file.
3. Insert it into many established posting lists.
4. Shift substantial portions of those lists.

This is on the watcher/update path through `Explorer.commitParsedFileAdoptOutline`. It can affect re-index latency, watcher catch-up, and interactive edits even if cold-build benchmarks are unchanged.

### Important context

This change appears **correctness-motivated**, not accidental. The old append could violate the posting-list sortedness invariant after doc-ID reuse, breaking binary search and persisted/mmap ordering.

Therefore “restore append” is not a valid optimization unless document IDs are made monotonic or unsorted delta postings are handled separately.

### Verdict

**Verified likely source-level regression**, especially for update/re-index workloads. It is not evidence of worse Zig 0.17 codegen.

### Targeted experiment

Construct a large index, remove low doc IDs, then repeatedly index files containing common trigrams. Measure separately:

- New highest doc ID, where insertion is effectively at the end
- Reused low doc ID, where tail movement is maximal
- Time in `getOrAddPosting`
- Bytes moved by insertion
- Allocations/reallocations

A benchmark that merely cycles ten files may not expose the worst case unless those files reuse low IDs and contain trigrams with long posting lists.

**Expected payoff/confidence:** Medium-high / medium; strongest fixed-cost CLI startup candidate.

**Files/functions**

- `src/main.zig:110-115` — `mainInner`
- Command dispatch/parsing around `src/main.zig:148-189`

**Minimal edit**

Run snapshot-backed, read-only commands on the process’s initial thread. Preserve the 8 MiB/64 MiB spawned-thread path for commands with uncertain stack requirements, initially:

- `index`
- `snapshot`
- `serve`
- `mcp`
- `cli-daemon`

Do not implement an approximate raw-argv parser that could misclassify options or root paths. Parse command selection through the existing CLI semantics, then choose direct execution versus the trampoline. Centralize error reporting so both paths behave identically.

**Focused correctness tests**

- Query path under an intentionally small process stack.

- one-hit search;
- no-hit search;
- word and symbol queries;
- representative snapshot-backed CLI search.

## Explicitly rejected for now

- **Reverting `TrigramIndex.insertExtracted` to unconditional append:** incorrect after lower document-ID reuse; it can violate sorted postings. Its safe append fast path is unlikely to affect the supplied cold-scan/query benchmarks materially.
- **Changing `TrigramIndex.writeToDisk` buffering/interleaving:** reports conflict on whether the new streaming implementation helps or hurts. Profile persistence separately before editing it.
- **Per-file directory-handle or parser-context reuse:** plausible, but no phase profile establishes which setup cost dominates `initialScan`; implementation also risks lifetime and concurrency bugs.
- **Attributing the delta to Zig 0.17 code generation:** unsupported without a same-source compiler matrix and confounded by source changes.
- **Tier-0 and exact-word changes without invariant tests:** both depend on posting properties that must hold after shard merge, mmap load, removal, and ID reuse.

## Measurement protocol for every experiment

- Preserve the dirty tree and user changes; create one temporary worktree/branch per single edit.
- Build `ReleaseFast`; record source hash, binary hash, Zig version, corpus hash, environment, and flags.
- Pin `CODEDB_SCAN_WORKERS` and `CODEDB_TRIGRAM_CAP`.
- Use 3–5 warmups followed by at least 30 randomized alternating A/B pairs.
- Report paired median, MAD or p25/p75, and bootstrap 95% CI.
- Compare each experiment first against its dirty Zig-0.17 parent to identify mechanism, then compare the stacked winner against clean `428d8df` built with Zig 0.16.0.
- Final acceptance requires identical canonical outputs and at least a 3% representative end-to-end improvement over clean HEAD; for indexing, also require at least a 2 ms absolute gain. Use a 2×2 source/compiler matrix only for attribution, not as a substitute for the final same-machine gate.
