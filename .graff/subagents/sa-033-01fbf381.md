## Audit scope and conclusion

I inspected the benchmark entry points and the main word-, trigram-, sparse-ngram-, mmap-, and parallel-indexing paths. The repository is explicitly pinned to Zig `0.17.0-dev.813+2153f8143` (`build.zig.zon:5`), and the installed compiler reports that exact version.

**Bottom line:** I found three plausible Zig 0.17-era optimization experiments, but **no repository-wide “turn on this new 0.17 feature for an automatic large win.”** The strongest opportunities are narrowly targeted:

1. apply `@branchHint` to measured, strongly biased rejection/termination branches;
2. test `@prefetch` in the mmap posting-list intersection path;
3. test explicit vectors for byte normalization and whitespace classification during indexing.

Of those, **mmap posting prefetch is the most specifically relevant to 0.17’s current compiler/toolchain behavior**, while explicit vectorization has the largest possible indexing upside. None should be merged without architecture-specific benchmarks: these paths are dominated by hash tables, allocations, and irregular memory access, where hints can easily regress performance.

I did not modify anything.

## 2. Candidate A: `@branchHint` in hot rejection and early-exit branches

### Concrete symbols

#### `TrigramIndex.indexFile`

Every byte window evaluates a pure-whitespace rejection branch:

```zig
if ((c0 == ... ) and (c1 == ...) and (c2 == ...)) continue;
```

The code itself says these are approximately 12% of occurrences, implying an 88/12 bias toward the normal indexing path (`src/index.zig:1264-1278`). This is a credible site for:

```zig
@branchHint(.unlikely);
```

inside the whitespace-only branch.

Other possible branches in the same loop are:

- new versus existing local trigram entry (`src/index.zig:1279-1282`);
- whether a following byte exists (`src/index.zig:1283-1286`).

The latter is false only at the final trigram and is therefore especially biased, although a modern optimizer may already infer it from loop bounds.

#### `TrigramIndex.candidates`

The sorted intersection has two early-rejection/termination paths:

- candidate present versus absent in a posting list (`src/index.zig:1555-1569`);
- intersection becoming empty (`src/index.zig:1569-1570`).

Bloom refinement rejects candidates through two mask checks (`src/index.zig:1595-1605`). Depending on query selectivity, these may be strongly biased toward rejection and are reasonable measured sites for `.likely`/`.unlikely`.

#### `MmapTrigramIndex.candidates`

The mmap implementation repeatedly:

- advances through encoded postings (`src/index.zig:2359-2375`);
- exits when an intersection is empty (`src/index.zig:2377-2378`);
- rejects via Bloom masks (`src/index.zig:2386-2408`).

These branches run directly in search latency’s candidate-filtering path and are more attractive than hints in administrative or error handling code.

#### `WordIndex.indexFile`

The tokenizer excludes short words and detects whether identifier splitting is needed:

- short-token rejection (`src/index.zig:302-307`);
- stack-buffer versus arena normalization (`src/index.zig:311-327`);
- underscore/uppercase detection (`src/index.zig:332-347`).

The 256-byte stack path is almost certainly dominant for source identifiers, making the long-token branch a plausible cold/unlikely branch. However, that condition is obvious enough that a hint may have little effect.

### Why this is relevant to the current 0.17 toolchain

The installed 0.17 standard library actively uses `@branchHint` in hot compression and cryptographic code. In particular, its flate implementation documents cases where a hint corrects LLVM 21’s chosen branch probability (`lib/std/compress/flate/Compress.zig:231`, `:248`, `:1136`). That verifies both that the builtin is supported by this pinned toolchain and that LLVM 21 can make undesirable branch-layout decisions without explicit guidance.

### Expected impact

**Expected:** low single-digit improvement in the affected loop if the branch is genuinely biased and currently laid out poorly; likely negligible repository-wide unless profiles show branch misses in these exact loops.

**Most likely winner:** pure-whitespace rejection in `TrigramIndex.indexFile`, because it is executed once per content byte and the source comment supplies an approximate 12% probability (`src/index.zig:1264-1272`).

### Risks

- Static hints based on one corpus can regress another.
- Search selectivity varies drastically by query, so Bloom-rejection hints may be wrong for common trigrams.
- LLVM may already infer loop-bound branches, producing no gain.
- Incorrect hints can worsen instruction layout and branch prediction.

### Tests

1. Run the benchmark in `ReleaseFast` with a representative multi-language repository and compare initial-index time (`src/benchmark.zig:279-336`).
2. Disable search caching via `CODEDB_NO_SEARCH_CACHE` so candidate intersection is measured (`src/explore.zig:3411-3417`).
3. Add focused benchmark cases for:
   - minified/no-whitespace input;
   - normal source;
   - documentation with long whitespace runs;
   - common versus rare trigrams.
4. Run existing candidate correctness tests, especially the search-content leak/empty/short-query regressions (`src/test_index.zig:814-862`, `:1054-1061`) and adversarial intersection tests (`src/adversarial_tests.zig:86-147`).

**Recommendation:** benchmark first; only annotate branches with measured probability and branch-miss evidence.

## 3. Candidate B: `@prefetch` for mmap posting-list intersections

### Concrete symbol

`MmapTrigramIndex.candidates` intersects sorted posting ranges by repeatedly decoding postings from the mmap representation (`src/index.zig:2350-2378`). It then performs additional range lookup and posting-mask searches for every surviving file and every consecutive trigram pair (`src/index.zig:2381-2408`).

This is the best candidate for a 0.17-era prefetch experiment because:

- the backing index is mmap-based rather than a compact in-cache `ArrayList`;
- accesses are sequential during merge, but subsequent Bloom verification performs repeated range and binary-search accesses;
- search latency depends directly on these reads.

A conservative experiment would prefetch one or a few postings ahead during the linear intersection, not attempt to prefetch every binary-search target. The installed 0.17 standard library demonstrates supported syntax such as:

```zig
@prefetch(ptr, .{ .rw = .write, .locality = 2 });
```

in `lib/std/crypto/ml_dsa.zig:636`.

### Rationale

Hardware prefetchers should already handle the simplest sequential range scan. The possible benefit is at transitions between posting ranges or during repeated mask lookup, where mmap pages or cache lines may not yet be resident.

This is more likely to help:

- large indexes;
- warm process but cold LLC;
- queries containing several moderately selective trigrams;
- x86 machines with higher memory latency.

It is less likely to help tiny benchmark repositories or fully hot indexes.

### Expected impact

**Expected:** zero to modest improvement for ordinary warm searches; potentially material tail-latency reduction for large mmap indexes with cold cache lines. The upper bound is workload- and architecture-dependent.

The heap implementation is a weaker target because its `PostingList` items are ordinary contiguous arrays and the sorted merge is already linear (`src/index.zig:1545-1570`).

### Risks

- Prefetching can increase memory traffic and evict useful lines.
- Query posting lists may be short enough that prefetch overhead dominates.
- Prefetch distance differs across ARM64 and x86-64.
- Prefetching beyond validated mmap ranges must be avoided even where the generated instruction is nominally non-faulting.
- It may hide no latency if `readPosting` decoding, rather than memory access, dominates.

### Tests

1. Benchmark both heap and mmap indexes separately.
2. Test hot-cache and intentionally cold-cache runs.
3. Use short, medium, and very long posting lists.
4. Report median, p95, and p99—not only mean query latency.
5. Run mmap candidate equivalence tests and the existing parallel/index serialization tests; candidate output must remain byte-identical.
6. Compare ARM64 and x86-64 before accepting any prefetch distance.

**Recommendation:** worthwhile as an isolated experiment, but not a default assumption. Start with the linear `readPosting(range.offset + si)` loop at `src/index.zig:2363-2375`.

## 4. Candidate C: explicit `@Vector` classification/normalization in byte-scanning loops

### Concrete symbols

#### `TrigramIndex.indexFile`

The loop performs three byte loads, four whitespace comparisons per byte, three calls to `normalizeChar`, trigram packing, and hash-table insertion for every content position (`src/index.zig:1264-1286`).

The classification and normalization portion is SIMD-friendly. Zig vectors could classify or normalize a block of bytes before the scalar hash-table insertion stage. A practical design would normalize a block into stack storage, then retain the current scalar sliding-trigram/hash loop.

#### `WordIndex.indexFile`

Every accepted word is copied and normalized byte by byte:

```zig
for (word, 0..) |c, j| stack_buf[j] = normalizeChar(c);
```

for normal-size words, with the same scalar loop on the long-word fallback (`src/index.zig:311-327`). It then scans the original word again for `_` or uppercase characters (`src/index.zig:332-343`).

A vector pass could combine ASCII normalization and “needs split” detection for medium/large identifiers.

#### Frequency-table construction

`buildFrequencyTableFromMapParallel` already distributes content among threads, then serially merges per-worker `[256][256]u64` tables (`src/index.zig:3286-3341`). Explicit vectorization is unlikely to help the table updates because they are data-dependent scatter increments, but vectors may help front-end byte loading/classification. The 65,536-counter merge is regular and potentially vectorizable, though it is only once per worker and probably not dominant (`src/index.zig:3332-3339`).

### Why this could improve over 0.16

The opportunity is to rely on the pinned 0.17 compiler’s current vector lowering and LLVM 21 backend rather than scalar source loops. This is a compiler-sensitive opportunity, not proof that vectors were unavailable in 0.16. I verified the repository/compiler pin, but not a language-level claim that `@Vector` itself is new in 0.17.

### Expected impact

**Potentially medium for initial indexing** if normalization/classification is a meaningful CPU fraction after hash-table and allocator costs. The trigram path scans every byte, so it offers the largest exposure.

However, vectorizing only whitespace checks while retaining one hash lookup per byte may yield little overall benefit. The hash map at `src/index.zig:1279-1285` is likely a larger bottleneck than the comparisons.

### Risks

- Tail handling and overlapping trigram windows are error-prone.
- Most identifiers are short; vector setup can make word normalization slower.
- ASCII normalization must preserve current behavior exactly.
- Explicit vector widths may produce poor code on ARM64 or targets lacking the assumed SIMD width.
- Bounds-safety and alignment assumptions require careful validation.
- The compiler may already auto-vectorize simple normalization loops.

### Tests

1. Differential-test vector and scalar normalization over all 256 byte values and random byte strings.
2. Verify index equivalence for binary/non-UTF-8 content, mixed case, CRLF, tabs, and very long identifiers.
3. Compare initial-index throughput on:
   - ordinary source;
   - generated/minified code;
   - large ASCII documentation;
   - high-entropy binary-like input.
4. Inspect optimized assembly to ensure actual SIMD generation.
5. Run existing sharded-versus-sequential equality tests (`src/test_index.zig:585-699`) and the parallel trigram result-identity test (`src/test_search.zig:2739-2788`).

**Recommendation:** prototype normalization as a self-contained helper with scalar fallback. Do not vectorize hash-table updates.

## 5. 0.17 `std.Io` should not automatically replace the existing CPU worker model

The codebase already uses the new 0.17-style `std.Io` interface for benchmark filesystem operations, including threaded I/O initialization (`src/benchmark.zig:279-289`) and `std.Io.Dir` reads/stats during reindexing (`src/benchmark.zig:148-158`).

CPU-heavy frequency-table construction explicitly spawns workers, partitions files into contiguous chunks, and joins them (`src/index.zig:3306-3330`). Parallel initial indexing similarly has dedicated worker/shard machinery; the repository documents that per-worker word-index shards are merged after parallel construction (`src/watcher.zig:771-773`).

### Assessment

I found no evidence that routing the CPU indexing work through `std.Io` would inherently outperform these long-lived, coarse-grained threads. The current design already avoids fine-grained task overhead and false sharing by giving each worker a private count table (`src/index.zig:3309-3338`).

`std.Io` remains useful for overlapping file reads/stats, but replacing the established CPU worker path merely because it is a 0.17 API is **not recommended without evidence**.

### Risk and test

The risk is scheduler overhead, changed stack/memory behavior, and nested parallelism with the threaded I/O backend. Any experiment must compare:

- one worker;
- current `std.Thread.spawn`;
- equivalent `std.Io` scheduling;
- small and very large repositories;
- indexing throughput and peak RSS.

# Inferences and confidence limits

1. **Likely dominant costs.** The source strongly suggests hash-table probes, posting-list memory traffic, and allocation dominate many loops: trigram indexing performs `local.getOrPut` per byte (`src/index.zig:1279-1285`), candidate construction allocates/hash-deduplicates query trigrams (`src/index.zig:1508-1532`, `:2311-2337`), and sparse candidates build a `StringHashMap` union (`src/index.zig:3624-3654`). This is an inference from structure; I did not collect hardware counters.

2. **Hints need profiles.** The whitespace comment supplies one useful probability—about 12% (`src/index.zig:1266-1272`)—but no branch statistics exist for candidate intersections. Any recommendation there is conditional.

3. **Version exclusivity is limited.** `@branchHint`, `@prefetch`, and explicit vectors are verified as usable in the installed 0.17 toolchain, but I did not verify that each was absent from every 0.16 release. The reliable version-specific statement is that this repository is pinned to 0.17 dev and its LLVM 21-era standard library actively uses these facilities (`build.zig.zon:5`; `lib/std/compress/flate/Compress.zig:231`; `lib/std/crypto/ml_dsa.zig:636`).

4. **No safe compiler-only win was identified.** I found no source evidence for a 0.17-only container, allocator, or I/O primitive that can replace the present implementation and predictably improve benchmark runtime without algorithm or data-layout changes.

## Three most load-bearing facts

1. **The hottest indexing loop performs one trigram hash-map probe per content byte**, after scalar classification and normalization (`src/index.zig:1264-1285`); SIMD or hints can only optimize the front end unless the data structure changes.

2. **The search-critical mmap path repeatedly decodes and intersects posting ranges, then performs per-candidate posting-mask searches** (`src/index.zig:2350-2408`), making it the strongest prefetch/cache-latency target.

3. **The repository already parallelizes major indexing work with coarse per-worker shards/private tables** (`src/index.zig:3306-3341`; `src/watcher.zig:771-773`), so adopting 0.17 `std.Io` for CPU work is not an automatic performance improvement.
