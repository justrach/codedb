## report

## Audit verdict: **Refuted**

The migration is buildable on the current machine and the pinned archives exist, but the documentation and CI changes are not fully reproducible or internally consistent.

### High severity

#### 1. CI downloads the compiler without integrity verification
**Files:**  
- `.github/workflows/bench-regression.yml:20`
- `.github/workflows/release-binaries.yml:60`

Both workflows download an executable toolchain with `curl` and immediately extract/run it. Neither uses `curl --fail` nor verifies the archive against a pinned SHA-256 digest.

Consequences:

- A proxy/server error body can reach `tar`, producing an opaque extraction failure.
- The build trusts mutable remote content at a URL without independently pinning its bytes.
- Release binaries cannot be reproduced from repository metadata alone because the expected compiler archive digest is not recorded.

The full-version URL is better than `master`, but URL pinning alone is not sufficient integrity pinning. Add platform-specific SHA-256 values and verify them before extraction; use at least `curl --fail --location --retry`.

**Counterexample:** if `ziglang.org/builds/...tar.xz` returns changed or compromised bytes under the same path, CI accepts and executes them.

---

#### 2. The release workflow’s compiler is not tied to the checked-out release tag
**File:** `.github/workflows/release-binaries.yml:15,50–61`

The workflow is launched from one revision, sets a global current compiler:

```yaml
ZIG_VERSION: 0.17.0-dev.813+2153f8143
```

but then checks out an arbitrary user-supplied existing tag:

```yaml
ref: ${{ env.RELEASE_TAG }}
```

That tag may contain a different `build.zig.zon` minimum or source written for Zig 0.16/0.15. The toolchain therefore describes the workflow revision, not necessarily the release source being rebuilt.

**Concrete counterexample:** dispatch this workflow with an older 0.16-era release tag. The job checks out that old source but still compiles it with the pinned 0.17 development snapshot. It may fail, or worse, produce binaries different from the original release while uploading them with `--clobber`.

For reproducible rebuilding of an existing tag, the compiler must come from metadata in that tag, or the workflow must reject tags not pinned to the expected compiler. Using `--clobber` makes this especially risky because mismatched rebuilds overwrite existing assets.

### Medium severity

#### 3. The documented zigup procedure does not install zigup or pin a zigup implementation/version
**File:** `docs/zig-0.17-migration.md:26–39`  
**Referenced by:** `README.md:458`

The section is called “Install and select the compiler with zigup,” but starts directly with:

```sh
zigup fetch ...
```

There is no zigup installation command, supported implementation/version, binary checksum, or PATH setup. The README calls this a “reproducible zigup setup,” which it is not for a clean machine.

The listed subcommands are valid for the installed `marler8997/zigup` implementation:

- `zigup fetch VERSION`
- `zigup default VERSION`
- `zigup keep VERSION`
- `zigup default`

However, the guide should identify and install that implementation. Its upstream README now recommends `anyzig`, so the generic name “zigup” is insufficient future-proofing.

Also, `keep` is not needed for selecting or using the exact version; it only protects it from later cleanup. Presenting it as part of installation without explaining that distinction is misleading.

---

#### 4. README simultaneously claims an exact tested compiler and permits unspecified moving snapshots
**File:** `README.md:458`

The requirement says:

> Zig `0.17.0-dev.813+2153f8143` or newer compatible 0.17 development build

That weakens the repository’s otherwise exact pin. Development snapshots have no stable API compatibility guarantee, and the migration guide itself says they are “moving targets” and should be upgraded deliberately.

A user following “or newer” currently gets a later `0.17.0-dev` snapshot, not the tested compiler. The present upstream master is already newer than the repository pin. Such a build may fail even though README says it satisfies the requirement.

For reproducibility, source-build instructions should require the exact snapshot. If newer snapshots are merely allowed opportunistically, state that they are unsupported/unverified rather than part of the requirement.

---

#### 5. `ZIG_VERSION` is not actually used to construct release archive names
**File:** `.github/workflows/release-binaries.yml:15,25–44,60`

`ZIG_VERSION` is declared globally, but every archive and extraction directory repeats the complete version literal. The download command only uses `matrix.zig_archive`, not `ZIG_VERSION`.

This creates five independent pins:

- `env.ZIG_VERSION`
- x86_64 macOS archive/directory
- aarch64 macOS archive/directory
- x86_64 Linux archive/directory
- Linux cross-build archive/directory

Changing only `ZIG_VERSION` has no effect on what gets downloaded. That is a concrete maintenance trap and makes the apparent central pin misleading. Construct archive/directory names from `ZIG_VERSION`, or remove the unused variable.

---

#### 6. CI does not verify that the downloaded compiler is the expected compiler
**Files:** both changed workflows

Neither install step runs:

```sh
zig version
test "$(zig version)" = "$EXPECTED_VERSION"
```

A malformed archive layout, stale PATH entry, runner-preinstalled Zig, or future archive naming change can cause subsequent steps to invoke a different `zig`. Recording `zig version` would also make build logs auditable.

This is especially relevant because the release workflow declares `ZIG_VERSION` but never checks it.

---

#### 7. Benchmark CI cannot consistently compare a migrated head against an old-version base
**File:** `.github/workflows/bench-regression.yml:25–38`

The workflow installs only Zig 0.17, then uses it for both the PR head and the checked-out base worktree. If the base branch still requires Zig 0.16, the base benchmark fails and the workflow silently changes into a bootstrap/no-comparison report:

```sh
if python3 ...; then
  have_base_json=true
else
  have_base_json=false
fi
```

Thus, during exactly the migration where regression comparison matters, compiler incompatibility is treated the same as “base lacks JSON support,” and no regression comparison occurs.

The workflow should distinguish:

- base script absent,
- base compilation failed,
- benchmark failed,
- machine-readable output absent.

Ideally, each worktree should use the compiler pinned by that revision, or migration PRs should explicitly document that cross-version benchmark comparison is unavailable.

`website/build.zig.zon` still has `.minimum_zig_version = "0.15.0"`, but that may be intentional if the website is a distinct package. It should either be explicitly documented as separately pinned or migrated/tested independently; it should not be changed merely by global search-and-replace.

#### 9. The migration guide’s old-version search misses important file types and wording
**File:** `docs/zig-0.17-migration.md:261–263`

The suggested command searches only:

```sh
--include='*.zig' --include='*.zon' --include='*.md'
```

It misses `.yml`/`.yaml`, which are precisely where the changed CI pins live. It also searches only `0\.16`, missing materially stale `0.15+` requirements such as `docs/cli.md`.

A useful audit needs at least YAML and all supported old versions, while excluding historical results and dependency/cache directories deliberately.

---

#### 10. CI runner selection is not fully pinned
**File:** `.github/workflows/bench-regression.yml:14`

`ubuntu-latest` is moving. Benchmark regression results are sensitive to runner image and hardware changes, so this weakens reproducibility and can create false regressions. The release workflow uses `ubuntu-24.04`, which is more consistent. Bench CI should likewise use an explicit runner image, though GitHub-hosted hardware still cannot be perfectly pinned.

## Checks that survived attack

- The three pinned Zig archive URLs tested—x86_64 Linux, x86_64 macOS, and aarch64 macOS—currently return HTTP 200.
- The archive naming convention and `/builds/` location are correct for this development snapshot.
- The Linux arm64 release entry intentionally downloads the x86_64 Linux **host compiler** and cross-compiles with `-Dtarget=aarch64-linux`; this is not an archive-selection bug.
- The documented zigup `fetch`, `default`, and `keep` forms match the installed `marler8997/zigup` CLI.
- The main project successfully completed `zig build --summary all` with `0.17.0-dev.813+2153f8143`.
- The reviewed 0.17 recipes—`addPassthruArgs`, `@splat`, `bufPrintSentinel`, `std.Io.Writer.Allocating`, emitted-artifact lazy paths, and public stream reads—are consistent with the pinned compiler and migrated code.
- The vendored `nanoregex` package also declares the same minimum Zig snapshot.

## Final verdict

**Refuted.** The code builds with the stated snapshot and the URLs are live, but the claimed reproducibility is broken by unverified compiler downloads, a release compiler that is independent of the checked-out tag, an incomplete zigup bootstrap, moving-version language in README, duplicated/unused CI pins, and several active old-version requirements.
