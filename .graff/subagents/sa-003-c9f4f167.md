## Evidence-backed candidates

### 1. Remove redundant hash deduplication from exact-word lookup

**Priority:** highest-confidence broad word-path win  
**Exact symbols:** `WordIndex.searchDeduped`, `WordIndex.indexOneToken`, `Explorer.searchWord`

#### Evidence

`Explorer.searchWord` sends every single-token query through `WordIndex.searchDeduped`. [src/explore.zig:5349-5365]

For any result list longer than one hit, `searchDeduped` currently:

1. allocates and pre-sizes an `AutoHashMap({doc_id,line_num}, void)`;
2. allocates a second result array at full hit-list capacity;
3. hashes every hit;
4. copies every unique hit into the second array.  
[src/index.zig:522-548]

The producer already suppresses duplicate `(doc_id,line_num)` entries for a word by comparing each insertion with the last posting and returning without appending when both fields match. [src/index.zig:236-269]

The exact-word benchmark then frees the returned slice after every iteration, so this allocation/hash/copy work is fully inside the timed region. [src/benchmark.zig:100-110]

#### Candidate

Make the posting-list uniqueness invariant explicit and return a straight owned copy of `self.search(word)` rather than rebuilding a hash set per query. A conservative first version can retain a debug/test-only invariant check that adjacent postings do not repeat `(doc_id,line_num)`.

This preserves the existing ownership contract while reducing the hot operation to one allocation plus one bulk copy.

#### Expected magnitude

- **Estimated 25–60% for exact-word rows with several hits**, because the current 5.6–12 µs benchmark rows include hash-table allocation, initialization, per-hit hashing, and an independently grown result list.
- **Likely several-percent improvement to the combined word geometric mean**, rather than a sub-percent compiler-only shift.
- Greatest benefit should occur for common words; misses and one-hit words already take fast paths. [src/index.zig:523-529]

#### Risks

- The insertion-time check only removes an immediately repeated hit. The optimization is safe only if all construction, shard merge, disk load, removal, and reused-document-ID paths preserve “at most one posting per `(word,doc,line)`.”
- Legacy or malformed persisted indexes could contain non-adjacent duplicates. Removing query-time dedup would expose them and change output cardinality.
- Multi-word queries use `searchWordTokensLocked`, not this exact path. [src/explore.zig:5360-5365]

#### Benchmark cases

Primary existing cases:

- `word/request`
- `word/response`
- `word/config`
- `word/error` — probably the most discriminating common-word case. [src/benchmark.zig:324-325]

Add correctness/performance fixtures for:

- repeated same token, with mixed casing, many times on one line;
- the same token on many lines and files;
- remove/reindex with reuse of a lower document ID;
- mmap reload followed by exact lookup;
- malformed/legacy duplicate postings if compatibility requires query-time repair.

### 2. Eliminate Tier-0’s per-query document map by relying on posting uniqueness

**Priority:** best uncached search candidate, but dependent on proving the same invariant as candidate 1  
**Exact symbol:** `Explorer.searchContentUncached`, Tier 0

#### Evidence

Tier 0 obtains exact-word postings from `word_index.search(query)`, groups adjacent hits into document runs, and explicitly states that a file’s postings are contiguous. [src/explore.zig:3472-3486; src/explore.zig:3516-3527]

Despite grouping run-at-a-time, it still builds one of two document-to-candidate structures on every uncached search:

- an allocated and fully initialized direct-address `[]u32`, or
- an allocated `AutoHashMap(u32,u32)`.  
[src/explore.zig:3491-3514]

Every run probes that structure, later stores the candidate index, then looks the candidate up again to update count and `hits_end`. [src/explore.zig:3522-3586]

If each document occurs at most once in a word posting list, a run can append exactly one `Tier0File` directly. Neither `slots` nor `idx_by_doc` is then needed. `count` is simply `run_end - run_start`, and `first_seen`/`hits_end` are known immediately.

The existing producer suppresses same-word same-line duplicate insertions. [src/index.zig:256-269]

Recent performance commits have already optimized this same region through direct-address slots, run grouping, a single outline fetch, and packed sort keys; the remaining map now exists primarily as defensive deduplication. [src/explore.zig:3491-3521; src/explore.zig:3589-3609; commit `38325f0`; commit `6b17e4e`; commit `f97286e`]

#### Candidate

After proving the posting invariant across persisted and incremental states:

- append one `Tier0File` per document run;
- set `count` from run length;
- remove `slots`, `idx_by_doc`, `SLOT_NONE`, `SLOT_INVALID`, and candidate-index probing;
- continue skipping empty `hitPath` entries exactly as today.

No ranking formula or candidate order needs to change: candidates remain in first-posting order, and the packed sort key already uses that append order as its final tie-break. [src/explore.zig:3589-3605]

#### Expected magnitude

- **Estimated 5–20% on Tier-0-heavy searches**, especially common identifiers with hundreds of postings.
- **Estimated 2–8% across the five uncached search rows** if Tier 0 is a material share.
- The existing `authentication` result—approximately 0.85 ms on baseline versus 0.76 ms migrated—shows that high-work search cases can expose roughly 0.1 ms changes, unlike the ~23–98 µs mostly-flat cases. It should be the lead validation case, but its observed Zig migration gain does not prove this candidate’s magnitude.

#### Risks

- Highest risk is non-contiguous or duplicate document runs after remove/reindex and document-ID reuse.
- Dirty `TrigramIndex.addFile` was changed specifically because reused lower IDs can violate append-sorted posting invariants; that is direct warning not to assume analogous word-index ordering without tests. [src/index.zig:1401-1412]
- Candidate order must remain byte-for-byte equivalent because later ranking uses first-seen order as a tie-break. [src/explore.zig:3589-3605]

#### Benchmark cases

Existing uncached search rows:

- `authentication` — high-work lead case;
- `webhook`;
- `error`;
- `database`;
- `middleware`. [src/benchmark.zig:313-321]

Required adversarial cases:

- one identifier repeated on many lines in one file;
- one identifier spread across many files;
- remove/reindex causing low document-ID reuse;
- heap-built versus mmap-loaded word index;
- assert identical result paths, lines, scores, and ordering.

Use `CODEDB_BENCH_BREAKDOWN` to verify that the improvement lands in `tier0_ns`, not in unrelated reranking noise. [src/benchmark.zig:91-95]

### 3. Pre-reserve `findAllSymbols`’ exact result capacity

**Priority:** very low-risk symbol-path improvement  
**Exact symbol:** `Explorer.findAllSymbols`

#### Evidence

`findAllSymbols` obtains the complete indexed location slice before constructing results. [src/explore.zig:2825-2834]

It starts an empty `ArrayList(SymbolResult)` but never reserves `indexed_locs.len`; every hit is then appended while also allocating owned path, name, and optional detail strings. [src/explore.zig:2830-2855]

After `ensureSymbolIndex`, the fallback outline scan runs only when `symbol_index_complete` is false. In the normal complete-index warm path, `indexed_locs.len` is therefore the exact output count. [src/explore.zig:2826-2828; src/explore.zig:2857-2863]

The benchmark invokes and frees the outer result slice on every iteration, so repeated `ArrayList` growth is timed. [src/benchmark.zig:113-123]

#### Candidate

Before the indexed-location loop, call `ensureTotalCapacity(allocator, indexed_locs.len)`. If the incomplete-index fallback is active, retain normal growth for any extra safety-scan results.

This changes neither matching nor order.

#### Expected magnitude

- **Estimated 3–10% for symbols with many locations**, such as `init` and `main`.
- **Near zero for misses or one-hit names**, such as the observed ~30 ns `handleRequest` miss.
- Likely **1–4% on the four-row symbol geometric mean**, enough to reverse the current ~0.8–1.2% regressions if allocator growth is material.

#### Risks

- Minimal: one earlier allocation can increase peak temporary capacity on an error path, but the function already must return that many results.
- Existing error cleanup must still release partially constructed nested strings; capacity reservation itself does not alter ownership.

#### Benchmark cases

- Existing: `symbol/init`, `symbol/main`, `symbol/render`, `symbol/handleRequest`. [src/benchmark.zig:326-327]
- Add synthetic symbols with 1, 8, 64, and 1,000 locations.
- Test both `symbol_index_complete=true` and the incomplete-index fallback.

### 4. Store direct symbol-detail identity in `SymbolLocation`

**Priority:** larger potential symbol win, moderate structural risk  
**Exact symbols:** `SymbolLocation`, symbol-index construction/update functions, `findSymbol`, `findAllSymbols`, `renderSymbols`, `searchSymbols`

#### Evidence

A symbol-index location stores path, kind, and line range, but callers still have to recover `detail` by:

1. hashing the path into `outlines`;
2. linearly scanning that file’s symbols;
3. comparing both `line_start` and symbol name.  
This occurs once per returned location in `findAllSymbols`. [src/explore.zig:556-561; src/explore.zig:2833-2843]

The same recovery scan is repeated in:

- `findSymbol`; [src/explore.zig:2771-2788]
- `renderSymbols`; [src/explore.zig:3375-3384]
- both fuzzy and non-fuzzy `searchSymbols` result materialization. [src/explore.zig:3090-3100; src/explore.zig:3117-3127]

Thus the supposedly O(1) symbol-name index still pays an outline hash lookup and per-file symbol scan for every hit.

#### Candidate

Extend `SymbolLocation` with stable detail identity, preferably a symbol ordinal within the owning outline rather than a raw pointer. Consumers can then index directly into `outline.symbols.items[ordinal]` and validate line/name in debug builds.

A raw borrowed detail slice would be faster but carries more lifetime risk across outline replacement and snapshot adoption; ordinal identity is the safer design.

#### Expected magnitude

- **Estimated 10–30% for common exact symbols** with many locations or files containing large outlines.
- **Estimated 5–15% for broad/fuzzy symbol search after candidate matching**, where each accepted location currently repeats the outline scan.
- Little benefit for misses.

#### Risks

- Symbol ordinals must be rebuilt whenever an outline is replaced or removed.
- Snapshot-restored outlines and lazy symbol-index rebuilding must produce identical ordinals.
- Any sorting/filtering between outline parsing and index insertion could make ordinal identity stale.
- This changes internal structure size and may affect memory/cache behavior; it should not be persisted without a format/version decision.

#### Benchmark cases

- Existing `init`, `main`, and `render`.
- A file with hundreds of symbols where the matching symbol is last.
- One symbol appearing in hundreds of files.
- Snapshot restore, incremental file replacement, and removal.
- Exact byte comparison of rendered symbol output.

### 5. Replace linear candidate dedup in `searchSymbols` for broad/fuzzy searches

**Priority:** targeted high-payoff improvement; not expected to affect exact `findAllSymbols` benchmark rows  
**Exact symbol:** `Explorer.searchSymbols`, nested `Dedup.contains` and `appendOne`

#### Evidence

`searchSymbols` keeps only up to `max_results` candidates, but every attempted append first linearly scans the retained candidate list for the same `(path,line_start)`. [src/explore.zig:2954-2964; src/explore.zig:3019-3030]

Accepted insertion then performs a binary search followed by an array insertion/move. [src/explore.zig:3041-3060]

Recent commits already reduced fuzzy scoring with SIMD slabs and replaced repeated full sorts with bounded binary insertion, leaving linear dedup as the remaining O(K) comparison step per candidate. [src/explore.zig:3064-3110; commit `5b93924`; commit `21e8fcd`]

#### Candidate

For broad `prefix`, `pattern`, or fuzzy searches, maintain a compact hash set keyed by stable `(path identity,line_start)` alongside the bounded candidate array. Because eviction removes the current worst candidate, the set must remove the evicted key before insertion.

Do not use only a path hash without collision verification.

#### Expected magnitude

- **Estimated 15–40% for fuzzy/pattern searches with many matching symbol locations and `max_results` around 50**.
- Negligible for exact symbol lookup and very small result sets.
- This is a production symbol-search opportunity, not a likely explanation for the current four `findAllSymbols` benchmark rows.

#### Risks

- More allocation and hashing can regress small queries; gate it behind a candidate-attempt or `max_results` threshold.
- Eviction/set synchronization errors could suppress valid results or admit duplicates.
- Ranking and total-order behavior must remain identical. [src/explore.zig:2966-2979]

#### Benchmark cases

- Fuzzy `"render"`, `"handleReq"`, and short high-recall patterns such as `"get"`.
- `max_results` values 10, 50, and 200.
- Many overloads in one path and same-name symbols across many paths.
- Assert identical score, order, and deduplication.

- **Trigram persistence, parallel shard build, frequency-table, or watcher work:** recent commits `42a436d`, `be52eef`, `428d8df`, `832749e`, and the dirty streaming persistence changes target indexing/cold readiness, not these warm query loops.
- **Further sort rewrites without profiles:** recent commits already introduced packed-key sorts, run grouping, direct-address slots, SIMD fuzzy scoring, and bounded symbol insertion. The remaining candidates above are narrower and tied to visible repeated allocation/hash/scan work. ## Verified vs. inferred

### Verified

- The dirty migration does not introduce a native warm-query algorithmic optimization in these paths. [src/explore.zig:16; src/explore.zig:1354]
- Exact word lookup always performs query-time hash dedup for lists longer than one hit. [src/index.zig:522-548; src/explore.zig:5360-5365]
- Word insertion suppresses immediately repeated same-word, same-document, same-line postings. [src/index.zig:256-269]
- Search Tier 0 groups postings by document run but still allocates/probes a document map. [src/explore.zig:3491-3586]
- Exact symbol result construction does not reserve its already-known indexed result count and repeatedly scans outlines to recover detail. [src/explore.zig:2830-2855]
- Broad/fuzzy symbol search linearly deduplicates against its retained candidate array. [src/explore.zig:2957-2964; src/explore.zig:3028-3030]

### Inferred

- Candidates 1 and 2 will produce the broadest measurable gains if the posting uniqueness invariant holds across mutation and persistence.
- Candidate 3 should be a small but reliable symbol improvement.
- Candidates 4 and 5 should matter primarily for high-cardinality symbol workloads.
- All percentage ranges above are engineering estimates; they require direct A/B confirmation.

## Three most load-bearing facts

1. **Every exact-word benchmark hit list longer than one is currently rehashed and recopied even though insertion already suppresses same-line duplicates.** [src/index.zig:236-269; src/index.zig:522-548]
2. **Search Tier 0 groups postings into document runs yet still allocates and probes a per-query document map; removing it is the clearest remaining uncached-search opportunity after the recent hot-path commits.** [src/explore.zig:3491-3586]
3. **Symbol lookup still performs per-result outline hash lookups and linear symbol scans to recover detail, despite already having a symbol index.** [src/explore.zig:2767-2794; src/explore.zig:2833-2843; src/explore.zig:3375-3384]

## Open question

Does the word posting representation guarantee globally—after shard merge, mmap load, file removal, and lower document-ID reuse—that each `(word,doc_id,line_num)` occurs exactly once and each document appears in only one contiguous run? Proving that invariant determines whether candidates 1 and 2 are safe behavior-preserving optimizations or require a persistence-time normalization step.
