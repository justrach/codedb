## report

## Audit result

The dirty tree does **not** contain an obvious search/startup regression in the changed production code. `src/main.zig`, `src/bootstrap.zig`, and `src/cli_args.zig` are byte-identical to clean `HEAD`; the relevant dirty diffs are concentrated in Zig-0.17 compatibility changes and index-writing correctness work. On native targets, most compatibility branches compile away, while the substantive `src/index.zig` changes affect index construction/persistence rather than the snapshot/mmap cold-search load path (`git diff --numstat HEAD`; `src/cio.zig:11-12,63-97`; `src/index.zig:1401-1412,1720-1882`).

That makes the observed **~3% process-startup** and **~1.8% cold in-process search** regressions more consistent with Zig 0.17 code generation or standard-library runtime costs amplifying existing fixed startup work, rather than a newly added source-level hot path.

## Ranked concrete changes

### 1. Avoid creating and joining a new OS thread for every ordinary CLI invocation

**Symbols:** `mainTrampoline`, `mainInner`  
**Location:** `src/main.zig:73-76`, `src/main.zig:110-115`  
**HEAD comparison:** identical at `git show HEAD:src/main.zig:73-76,110-115`

Current startup always:

1. allocates an 8 MiB stack in release builds,
2. creates an OS thread,
3. runs all real work there,
4. joins it immediately.

```zig
const thread = try std.Thread.spawn(.{ .stack_size = stack_size }, mainInner, .{});
thread.join();
```

The only invocations exempted are the no-argument/version fast paths handled before `mainTrampoline` (`src/main.zig:58-62,84-107`).

**Concrete change:** Run `mainImpl` on the initial thread for ordinary CLI/query commands. Retain the large-stack worker only for commands demonstrably needing it—likely indexing, daemon/server, MCP, or specific deeply recursive parsing paths. A conservative first version could parse only enough raw argv to choose between direct CLI execution and the large-stack path.

**Why it should measurably help:** Thread creation/join, stack reservation, TLS setup, and scheduler interaction are fixed process-startup costs. They are unusually large relative to a short cold CLI search and directly match both reported regressions. This is the strongest candidate for recovering most or all of the ~3% startup delta.

**Behavior risks:**

- The trampoline likely exists to protect against stack exhaustion in parsing/indexing. Running all commands on the initial stack without auditing stack use is not low risk.
- Command dispatch before full parsing must preserve root/command ambiguity and global-option behavior.
- Error reporting currently differs between `mainTrampoline` and `mainInner` (`src/main.zig:62-69,110-114`).

**Risk-controlled implementation shape:** Keep the worker for `index`, `snapshot`, `serve`, `mcp`, and `cli-daemon`; initially bypass it only for read-only query commands with a known snapshot-backed path. Validate with a deliberately small process stack and the largest supported files.

### 2. Stop duplicating every argv string after argv has already been materialized

**Symbols:** `bootstrapArgs`, `argsAlloc`, `main`, `mainImpl`  
**Locations:** `src/cio.zig:482-490,494-517`; `src/main.zig:58-60,148-149,156-189`  
**HEAD comparison:** identical at `git show HEAD:src/cio.zig:452-487`

Startup first obtains a process-lifetime argv vector:

```zig
const argv = cio.bootstrapArgs(init.args);
cio.setProcessArgs(argv);
```

Then `mainImpl` allocates a new argv slice and separately allocates/copies every string:

```zig
const raw_args = try cio.argsAlloc(allocator);
```

`argsAlloc` performs one allocation for the slice and one allocation plus memcpy per argument (`src/cio.zig:499-515`). The global-option filter then builds another pointer list and converts it to an owned slice (`src/main.zig:156-189`).

On Windows, `bootstrapArgs` itself already calls `args.toSlice(page_allocator)` and allocates another pointer array that intentionally lives for the process lifetime (`src/cio.zig:483-489`).

**Concrete change:** Pass the bootstrap argv slice into the real entry point and parse borrowed `[]const u8` spans directly. Allocate only the filtered pointer array when global options actually need removal—or use a small stack-backed array for normal argument counts.

**Why it should measurably help:** This removes `argc + 1` heap allocations, per-argument memcpy, corresponding frees, and one avoidable pointer-array allocation from every non-fast invocation. It is a small absolute cost but is exactly the kind of fixed allocator work that can explain a low-single-digit startup shift.

**Behavior risks:**

- Borrowed argv lifetime must remain valid until command completion. On POSIX it is runtime-owned; Windows currently intentionally leaks the bootstrap representation for process lifetime (`src/cio.zig:482-490`).
- Some downstream code may implicitly depend on writable or sentinel-terminated argument slices, even though the visible parser APIs accept `[]const []const u8` (`src/cli_args.zig:46,167`).
- macOS currently obtains argv independently through `_NSGetArgv` in `argsAlloc` (`src/cio.zig:495-510`), so the borrowed representation should be tested there.

### 3. Make config discovery avoid the executable-path lookup when no binary-local config is relevant

**Symbols:** `loadUserConfig`, `Config.loadDefault`  
**Locations:** `src/bootstrap.zig:26-34`; `src/config.zig:70-90`; call at `src/main.zig:409-415`  
**HEAD comparison:** `src/bootstrap.zig` and this call site are unchanged from HEAD.

Every cold query calls `std.process.executablePathAlloc` before config loading:

```zig
const self_exe = std.process.executablePathAlloc(io, alloc) catch null;
```

But config resolution first checks an explicit path and `$CWD/.codedbrc`; only the final fallback uses `<binary_dir>/.codedbrc` (`src/config.zig:76-88`). Thus even users with `--config-file` or a cwd config pay an unnecessary executable-path syscall/allocation.

More importantly, users with no config pay executable-path resolution plus at least two config probes on every invocation.

**Concrete change:**

- Handle an explicit config before resolving the executable path.
- Probe `$CWD/.codedbrc` before resolving the executable path.
- Resolve the executable only if both miss and the binary-directory fallback is still required.
- Longer-term, consider making the binary-local fallback opt-in or embedding whether it exists at installation time.

**Why it should measurably help:** It removes a filesystem/process lookup and allocation from configured common cases. This should show up more clearly in process-startup benchmarks than in search-engine timing.

**Behavior risks:**

- Must preserve precedence exactly: explicit, cwd, then binary directory (`src/config.zig:76-88`).
- Errors from an explicit path must not silently fall through.
- Changing or caching the binary-local fallback could alter behavior after the executable or config file is replaced.

### 4. Collapse snapshot header validation and snapshot load into one open/read or one mapping

**Symbols:** `loadSnapshotIfHeadMatches`, `loadBestSnapshot`, `loadSnapshot`  
**Locations:** `src/bootstrap.zig:37-74`; `src/snapshot.zig:528-536`; invocation at `src/bootstrap.zig:389-393`  
**HEAD comparison:** bootstrap path is unchanged from HEAD.

For each candidate snapshot, startup first calls `readSnapshotGitHead`, then—if the head matches—calls `loadSnapshot` separately (`src/bootstrap.zig:45-53`). Therefore the winning snapshot is opened/read at least twice. `loadBestSnapshot` also probes the root-local snapshot before the central per-project snapshot (`src/bootstrap.zig:65-74`), so the usual central-snapshot case includes an extra failed root-path probe.

**Concrete change:** Add a validated-load API that opens/maps once, checks the header and git head from that data, and continues loading from the same handle/mapping. Alternatively have `readSnapshotGitHead` return a validated open object consumed by `loadSnapshotValidated`.

**Why it should measurably help:** Cold in-process search explicitly pays snapshot bootstrap before trigram/word-index mmap setup (`src/bootstrap.zig:391-413`). Removing one open/read and pathname traversal from the winning snapshot is a plausible contributor at the reported ~1.8% scale, especially on macOS, Windows, networked home directories, or cold metadata caches.

**Behavior risks:**

- Must retain the legacy/non-git rule: a snapshot with no recorded head is accepted only when the current project also has no git head (`src/bootstrap.zig:45-49`).
- File replacement between validation and load currently causes a second-open view of the file. A single-handle design changes that race, generally beneficially, but tests should define the intended semantics.
- Snapshot corruption and version checks must remain centralized rather than partially duplicated.

### 5. Avoid unconditional data-directory creation on read-only cold queries

**Symbols:** `getDataDir`, `mainImpl`  
**Locations:** `src/bootstrap.zig:77-88`; `src/main.zig:397-398`  
**HEAD comparison:** unchanged from HEAD.

`getDataDir` is both a path resolver and a mutating initializer:

```zig
std.Io.Dir.cwd().createDirPath(io, dir) catch ...
```

Every cold search calls it before config/bootstrap, even if the directory tree already exists (`src/main.zig:397-412`). Depending on Zig 0.17’s `createDirPath` implementation, this can mean multiple component probes/syscalls on every process.

It also duplicates `$HOME` before formatting the result despite only needing the environment string during the format operation (`src/bootstrap.zig:79-84`).

**Concrete change:**

- Split `dataDirPath` from `ensureDataDir`.
- For snapshot-backed read-only queries, format the path without calling `createDirPath`; create it only on a path that will write, scan, spawn a daemon, or otherwise needs it.
- Remove the temporary `home` duplication and format directly from `home_env`.

**Why it should measurably help:** This removes fixed filesystem metadata work and two allocator operations from every cold search. If Zig 0.17 changed directory-creation internals, it is also a credible version-sensitive source of a small regression.

**Behavior risks:**

- Cold search with no existing data directory eventually needs directory creation if it scans and persists indexes.
- Auto-spawn and daemon-lock paths require the directory to exist before lock-file creation (`src/main.zig:382-391`; `src/cli_proxy.zig:451-468`).
- Error/warning timing may change.

### 6. Initialize heavier CLI facilities only after borrowed argument parsing and early command exits

**Symbols:** `mainImpl`  
**Location:** `src/main.zig:130-148,196-289`

Before parsing the command, `mainImpl` currently:

1. installs SIGPIPE handling,
2. initializes `std.Io.Threaded`,
3. checks stdout TTY state,
4. initializes styled output,
5. allocates/copies argv.

Some early commands such as help, update, and nuke are dispatched only after this work (`src/main.zig:196-289`). Version/no-arg already have a separate fast path (`src/main.zig:84-107`), but help does not.

**Concrete change:** Parse borrowed argv first and add raw fast paths for `--help`/`-h` analogous to version. For commands that need no filesystem I/O, delay `std.Io.Threaded.init` until after dispatch. If Zig 0.17 exposes a cheaper synchronous/native `std.Io` backend suitable for short CLI reads, benchmark that backend for read-only commands.

**Why it should measurably help:** It reduces the minimum initialized runtime surface for process-startup benchmarks. The likely payoff is smaller than removing the thread trampoline because search still needs I/O.

**Behavior risks:**

- Full help uses styled output and TTY detection, so exact color behavior must be preserved.
- `--help` in mixed MCP/global-option positions has special semantics (`src/main.zig:233-263`).
- Replacing the I/O backend is not low risk until concurrency, cancellation, and file API behavior are validated. Treat backend replacement as an experiment, not an immediate patch.

### 7. Do not optimize the dirty native compatibility diffs unless profiling implicates them

**Symbols/files:** `cio` freestanding guards, native atomic aliases, `bufPrintZ` wrapper  
**Locations:** `src/cio.zig:11-12,63-103,180-258,261-361`; `src/explore.zig:16,1354-1357`; `src/hot_cache.zig:2-4,16-24`

The dirty migration adds:

- `freestanding` guards around OS functionality,
- a `bufPrintSentinel` compatibility wrapper,
- `u32` atomics only for wasm32 and `u64` elsewhere.

On normal Linux/macOS/Windows builds, the target checks are compile-time constants. `SearchGeneration` and `AtomicCounter` remain `u64` on native targets (`src/explore.zig:16`; `src/hot_cache.zig:4`). The `bufPrintZ` changes occur in daemon/socket paths rather than cold in-process snapshot search (`src/cli_proxy.zig:156-161,451-468,557-561,701-717`).

**Recommendation:** Do not spend optimization risk here without assembly or profile evidence. These changes are unlikely to account for either reported native regression.

The substantive dirty `src/index.zig` changes primarily alter posting insertion and two-file trigram persistence, not the mmap read/search path. They may affect first-ever indexing benchmarks, but not a valid-snapshot cold in-process search (`src/index.zig:1401-1412,1720-1882`; cold load at `src/bootstrap.zig:400-416`).

## Measurement protocol

### Build matrix

Produce four release binaries with identical CPU/optimization/link settings:

1. clean `428d8df` with Zig 0.16,
2. clean `428d8df` ported only enough to build with Zig 0.17, if available,
3. current dirty Zig 0.17 tree,
4. current dirty tree plus each candidate change individually.

The clean-HEAD-on-both-compilers comparison is essential: current versus HEAD alone conflates compiler/runtime and source effects.

Record:

- exact Zig commit,
- `-Doptimize` mode,
- target and CPU flags,
- LTO/strip/PIE settings,
- binary size and dynamic dependencies.

### Startup benchmark

Use commands that isolate distinct layers:

- `codedb --version`: loader plus raw fast path;
- `codedb --help`: full CLI entry, parsing, worker thread, output setup;
- a cheap invalid or metadata-only command;
- `codedb <root> status`;
- `codedb <root> search <rare-token>` with a valid snapshot.

Run with:

```text
CODEDB_NO_CLI_DAEMON=1
CODEDB_NO_WARMUP=1
CODEDB_NO_TELEMETRY=1
CODEDB_QUIET=1
```

Pin to one CPU, use performance governor, avoid turbo-state drift, and alternate binaries in randomized ABBA order rather than running all samples of one binary first. Use at least 500 startup samples and report median, p25/p75, p95, and bootstrap confidence intervals. A 1–3% claim should require intervals excluding zero across multiple runs.

### Cold in-process search benchmark

Define “cold” precisely:

- **Cold process, warm page cache:** new process each iteration, same valid snapshot, pre-touch corpus/index files before each comparison pair.
- **Cold process, cold metadata/data cache:** only on a dedicated machine where caches can be dropped fairly; randomize binary order.
- Disable daemon proxying and auto-spawn.
- Verify identical stdout and exit status for every sample.
- Use single-token, multi-token/BM25, regex, common-token, and rare-token searches because startup-to-engine ratios differ.

Instrument phase timestamps around:

1. entry to `main`,
2. before/after worker-thread creation,
3. argv preparation/filtering,
4. `std.Io.Threaded.init`,
5. config discovery,
6. root/data-dir resolution,
7. git-head lookup,
8. snapshot header validation/load,
9. trigram mmap,
10. word-index mmap,
11. `runQuery`,
12. flush/exit.

Existing bootstrap timing only measures snapshot loading (`src/bootstrap.zig:391-393`), so it cannot attribute thread, config, argv, or data-directory overhead.

### System-level attribution

For the top candidates:

- Linux: `perf stat` for task-clock, cycles, instructions, branches, page faults, context switches; `strace -c` for clone/openat/newfstatat/mkdir/read/mmap.
- macOS: Instruments/System Trace or `dtruss` where permitted.
- Windows: WPA/ETW for thread creation, file opens, and allocator activity.

Expected signatures:

- Candidate 1: one fewer thread creation/join and fewer context switches.
- Candidate 2: fewer malloc/free calls and copied argv bytes.
- Candidate 3: fewer executable-path/config filesystem calls.
- Candidate 4: one fewer snapshot open/header read.
- Candidate 5: fewer mkdir/stat component probes.

## Verified vs inferred

### Verified

- Main startup, bootstrap, and CLI parser source are unchanged from clean HEAD.
- Every non-fast CLI invocation creates and joins an 8 MiB-stack worker thread (`src/main.zig:73-76`).
- Arguments are materialized for the fast path and then separately duplicated per argument in `mainImpl` (`src/main.zig:58-60,148-149`; `src/cio.zig:482-517`).
- Config loading resolves the executable before checking whether an explicit or cwd config makes that unnecessary (`src/bootstrap.zig:26-34`; `src/config.zig:76-88`).
- Snapshot bootstrap validates the head and then separately invokes snapshot loading (`src/bootstrap.zig:45-53`).
- Data-directory resolution unconditionally calls `createDirPath` (`src/bootstrap.zig:77-88`).
- Dirty native-relevant source changes do not add an evident new cold-search loop or copying pass.

### Inferred

- The compiler/stdlib change is likely the primary source of the measured regression because the main startup/search orchestration is unchanged.
- Thread creation is the most likely fixed-cost source capable of producing a measurable startup improvement.
- Duplicate argv allocations, executable-path resolution, directory creation, and double snapshot opens are individually smaller, but together are credible at the 1–2% cold-search scale.
- The exact ranking below the thread trampoline depends on OS and whether the benchmark uses warm filesystem caches.

## Three most load-bearing facts

1. **The startup/search orchestration is identical to HEAD**, so the regression is not explained by a new dirty-tree main/bootstrap/parser path (`src/main.zig:58-148`; `src/bootstrap.zig:372-416`; `git diff HEAD`).
2. **Every ordinary CLI search pays an OS thread create/join with an 8 MiB stack before doing useful work** (`src/main.zig:73-76`).
3. **Cold search performs several avoidable fixed operations before query execution: argv duplication, executable-path resolution, unconditional directory creation, and separate snapshot validation/load** (`src/cio.zig:494-517`; `src/bootstrap.zig:26-34,45-88`).

## Open question

The `--version` path returns before worker-thread and I/O initialization (`src/main.zig:58-62,97-105`); if that path alone regressed by ~3%, the strongest evidence would point directly to Zig 0.17 binary generation/loader behavior rather than any of the application-level changes above.
