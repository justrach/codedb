## report

## Audit result

The measured deltas—direct `initialScan` 188 ms vs 187 ms and cold CLI search 116.4 ms vs 114.3 ms—do **not** identify a credible migration-induced indexing regression. In the native runtime indexing path, nearly all changes in the four requested files are Zig 0.17 compatibility changes or affect persistence/incremental updates rather than the measured cold scan.

The best opportunities are therefore **new optimizations that apply equally to clean HEAD and current**, especially eliminating per-file setup in parsing and file I/O. These could make current materially faster than baseline, but they are not reversions of migration overhead.

# Verified findings

## 1. The measured direct `initialScan` path is effectively unchanged by this diff

`initialScan` chooses up to eight workers and delegates to `initialScanWithWorkerCount`; its only relevant dependency from `cio.zig` is environment lookup for the worker override.【src/watcher.zig:1179-1188】【src/cio.zig:394-403】

The only `watcher.zig` diff is:

- `[_]?FsEvent{null} ** CAPACITY` → `@splat(null)` in `EventQueue` initialization.【src/watcher.zig:44-49】

That queue is not part of `initialScanWithWorkerCount`. This is a Zig syntax migration, not runtime indexing overhead.

Likewise, native `cio.zig` behavior is unchanged by the newly added freestanding guards:

- `posixGetenv` only takes the new early return on freestanding targets.【src/cio.zig:394-403】
- timer/timestamp changes only add freestanding branches.【src/cio.zig:261-302】
- native mutex and rwlock implementations remain the POSIX/Windows implementations; no-op locks are selected only for freestanding builds.【src/cio.zig:171-258】

**Conclusion:** the 1 ms direct-scan difference is consistent with measurement noise or Zig 0.17 code-generation/runtime variation, not an avoidable source-level addition in the audited diff.

## 2. Most `explore.zig` changes are migration-required and native-no-op

The diff’s array repetition conversions to `@splat` are Zig 0.17 syntax migrations. They affect static/local initialization forms, not algorithmic work:

- `code_char_freq` initialization.【src/explore.zig:7535-7541】
- fuzzy presence table initialization.【src/explore.zig:8605-8612】
- fuzzy batch lane initialization.【src/explore.zig:8735-8759】

The new freestanding guards in content loading, rerank tracing, and co-change construction are compile-time target checks and do not add meaningful native-path work.【src/explore.zig:2518-2525】【src/explore.zig:4455-4462】【src/explore.zig:4676-4683】

Changing `search_gen` to a target-dependent integer is also migration/platform accommodation: native remains `u64`; only wasm32 becomes `u32`.【src/explore.zig:16-16】【src/explore.zig:1354-1358】

**Classification:** migration-required or target-specific; not plausible causes of the native A/B differences.

## 3. The changed trigram insertion is correctness work, but not on the normal cold-build hot path

The notable runtime change in `index.zig` replaces an unconditional append in `insertExtracted` with `getOrAddPosting`, preserving sorted posting lists when a freed lower document ID is reused.【src/index.zig:1390-1412】

`getOrAddPosting` performs a binary search and may insert into the middle of an array.【src/index.zig:1089-1105】 That is objectively more expensive than append, but it is required when document IDs can be reused.

However, ordinary `TrigramIndex.indexFile` already distinguishes new IDs from reused IDs:

- Brand-new, monotonically increasing IDs use append.【src/index.zig:1235-1244】【src/index.zig:1291-1297】
- Only reused IDs use sorted insertion.【src/index.zig:1298-1303】

Cold shard builders likewise use bulk-new insertion assumptions rather than the changed `insertExtracted` path. `insertBulkNew` is explicitly documented as assuming strictly increasing new IDs and uses append.【src/index.zig:1414-1431】

For the ordinary multiworker `initialScan`, `initialScanWorker` is currently called with no trigram shard, and trigram work is omitted entirely when `skip_trigram` is true.【src/watcher.zig:770-792】 Cold non-search CLI startup calls `initialScan(..., true)`, so this scan does not build trigrams inline.【src/bootstrap.zig:468-494】

**Conclusion:** do not revert this change for speed. It repairs a real ordering invariant and is not a credible explanation for the measured cold scan regression.

A safe micro-optimization would be to add an append fast path inside `insertExtracted` when the posting list is empty or its last `doc_id < doc_id`, falling back to `getOrAddPosting` otherwise. That preserves correctness and helps bulk-like callers, but likely has **negligible impact** on the two supplied benchmarks because they do not appear to use this symbol.

## 4. `TrigramIndex.writeToDisk` is changed substantially, but mostly in a favorable direction

Current `writeToDisk`:

- Builds the file table in document-ID order and directly fills `doc_to_disk`, avoiding the old intermediate `StringHashMap` and second hash lookup pass.【src/index.zig:1720-1744】
- Streams lookup entries in fixed batches instead of retaining an allocation proportional to trigram cardinality.【src/index.zig:1758-1768】【src/index.zig:1837-1883】
- Writes postings and lookup streams concurrently through separate buffered writers.【src/index.zig:1786-1807】

These changes should reduce allocations, hashing, and peak persistence memory. They are **not migration-required**, but they are optimizations rather than obvious overhead.

They also do not affect the direct `initialScan` median. They can affect a first-ever cold search because `coldLoadOrScan` may build and persist a temporary trigram index before mmap-loading it.【src/bootstrap.zig:482-490】 For non-search cold commands, trigram persistence occurs after the initial scan and is separately profiled.【src/bootstrap.zig:525-568】

### Correctness risk in the persistence rewrite

The two files are flushed before either rename, which is good, but they are still renamed separately—postings first, lookup second.【src/index.zig:1875-1886】 A crash between renames can leave a mixed pair. This was already a general two-file atomicity limitation, but opening and producing both temporaries together does not solve it.

The new document-ID ordering is important because persisted posting lists must remain sorted for mmap binary searches; the current code documents and enforces that relationship.【src/index.zig:1720-1744】

**Recommendation:** retain this rewrite unless focused persistence benchmarks show a regression. Benchmark it independently rather than attributing the 2.1 ms cold CLI delta to it.

# High-confidence optimization opportunities

## Priority 1: Stop opening and closing the repository root once per file

Every call to `parseInitialScanEntry` performs:

1. `cwd().openDir(root)`
2. file read
3. `dir.close()`

This happens for every indexed file.【src/watcher.zig:602-620】

The outer scan already opens the root directory before collecting entries.【src/watcher.zig:704-708】 Worker threads then call `parseInitialScanEntry` repeatedly from their per-entry loop.【src/watcher.zig:663-687】

### Suggested design

Open one root directory handle per scan worker, outside its file loop, and pass that handle to a variant of `parseInitialScanEntry`. The serial path can reuse the outer root handle or open one dedicated non-iterating handle.

### Estimated impact

- **Likely:** 2–10 ms on medium repositories, potentially more on macOS, Windows, network filesystems, or repositories with thousands of small files.
- This is one of the few opportunities likely large enough to move a ~188 ms scan visibly.
- The gain scales with file count, not bytes.

### Correctness risks

- Do not share a mutable directory handle across workers unless Zig’s `std.Io.Dir` contract explicitly permits concurrent use.
- Safest implementation: one handle owned by each worker.
- Preserve symlink/root-resolution behavior by opening the same `root` with the same flags as today.

### Focused benchmark

Add counters or a benchmark variant comparing:

- current per-file `openDir`/close;
- one `Dir` per worker;
- repositories of 1k, 10k, and 50k tiny files;
- worker counts 1, 2, 4, and 8.

Report collection, read/parse, commit, and total time separately using the existing `CODEDB_INDEX_PROFILE` timing framework.【src/watcher.zig:691-708】【src/watcher.zig:794-833】

## Priority 2: Reuse parser infrastructure per worker instead of constructing an `Explorer` per file

`parseContentForIndexing` creates and destroys a complete one-slot `Explorer` for every file solely to carry allocator/parser state:

- `Explorer.initFallible(allocator, 1)`
- parse outline
- clone outline
- `Explorer.deinit()`【src/explore.zig:2007-2018】

The worker loop already owns a scratch arena reset once per file.【src/watcher.zig:663-679】 Repeatedly constructing all of `Explorer`’s maps, caches, locks, indexes, and associated state is therefore avoidable in principle.

The parsed outline is then cloned again into packed libc-owned storage for publication.【src/watcher.zig:637-659】 `cloneOutlinePackedBorrowingPath` computes aggregate string size, allocates packed storage, and copies every symbol/import string.【src/explore.zig:2596-2651】

### Suggested design

Best option: factor parsing into a lightweight reusable `ParserContext` containing only the state required by `parseOutlineWithParser`. Initialize one context per worker and reset its transient state per file.

A less invasive experiment is one reusable parser `Explorer` per worker, provided all parser-mutated state can be reset safely and cheaply between files.

A more ambitious follow-up is to have parsing produce the packed persistent outline directly, eliminating the intermediate clone.

### Estimated impact

- Parser-context reuse: **likely 5–20 ms** on many-small-file repositories; lower on repositories dominated by large-file parsing.
- Direct packed-outline construction: potentially another **3–15 ms**, depending on symbol/import density.
- This is the highest-upside structural optimization in the audited path.

### Correctness risks

- **Medium to high.** Parser state leakage across files can corrupt language detection, imports, symbol locations, or ownership.
- Direct packed construction must preserve `FileOutline` ownership flags and path borrowing semantics.
- The current two-stage clone provides clean error unwinding; a replacement needs equivalent OOM safety.

### Focused benchmark and validation

Measure:

- empty/tiny files, where setup dominates;
- symbol-heavy generated source;
- mixed-language repositories;
- allocations per file and bytes copied;
- exact equality of outlines, dependency graph, and symbol index against the current path.

Run parser and indexing tests under an allocator that detects leaks and double frees.

## Priority 3: Bulk-commit parsed files under one lock, but only after profiling

Every file commit takes and releases `Explorer.mu`, bumps the search generation, and checks/invalidates derived graph state.【src/explore.zig:1514-1529】 During a cold scan there should be no concurrent readers that need per-file visibility, yet the main thread invokes this once for each ready file.【src/watcher.zig:795-803】

### Suggested design

Create a private `commitParsedFileAdoptOutlineLocked` helper and let the cold scan hold the exclusive lock across a batch—or across all currently ready files—while preserving the public locking wrapper for incremental use.

Also consider batching `search_gen` advancement once per cold-scan publication rather than once per file, if no observer can run during bootstrap.

### Estimated impact

- Lock/unlock alone: probably **under 1–3 ms**.
- Could be larger if generation bumps or repeated derived-state checks inhibit optimization.
- Lower confidence than per-worker directory/parser reuse.

### Correctness risks

- **Medium.** Holding the lock while waiting for worker results would be wrong and could block unrelated startup work.
- Commit only already-ready batches; never wait on `takeReady` while holding `Explorer.mu`.
- Error rollback semantics in `commitParsedFileAdoptOutline` must remain per-file correct.【src/explore.zig:1530-1567】

### Focused benchmark

Instrument:

- time waiting for worker publication;
- time inside `commitParsedFileAdoptOutline`;
- time acquiring the mutex;
- dependency rebuild and symbol-index rebuild separately.

Benchmark batch sizes 16, 64, 256, and “all ready.”

## Priority 4: Tune the static worker partitioning for skewed file sizes

Workers receive contiguous file-count chunks, not byte-balanced chunks.【src/watcher.zig:776-792】 Worker results are then consumed in worker order and per-worker item order.【src/watcher.zig:795-803】

A chunk containing several large or parser-heavy files can hold up publication while other workers finish. Because the consumer processes worker 0 completely before worker 1, work completed in later chunks cannot be committed early.

### Suggested design

Use size-aware greedy partitioning, or a shared atomic work queue plus a separate ordering mechanism if deterministic commit order is required. A lower-risk option is more, smaller static chunks assigned to workers while retaining an ordered result array.

### Estimated impact

- Balanced repositories: negligible.
- Skewed repositories: **5–30% of parse phase** is plausible.
- Less universally high-confidence than eliminating per-file setup.

### Correctness risks

Commit order is explicitly relied on for symbol precedence, cache eviction, dependency output, and persistence semantics.【src/watcher.zig:673-674】【src/watcher.zig:795-797】 Any dynamic scheduler must preserve discovery-order commit even if parsing is out of order.

### Focused benchmark

Construct repositories with:

- 95% 1–4 KiB files and 5% 500 KiB–1 MiB files;
- large files clustered at the start, middle, and end of discovery order;
- compare worker busy time, main-thread idle time, and total scan time.

## Priority 5: Keep a safe append fast path in `insertExtracted`

`insertExtracted` now binary-searches every posting even when the new document ID is greater than the posting list’s last ID.【src/index.zig:1390-1412】【src/index.zig:1089-1105】

A correctness-preserving implementation can:

1. append if list is empty;
2. append if `last.doc_id < doc_id`;
3. otherwise call `getOrAddPosting`.

### Estimated impact

- Potentially material for callers that feed new files through `insertExtracted`.
- **Negligible for the supplied direct scan and cold CLI search** unless profiling proves this symbol is reached.
- Primarily an incremental/bulk API cleanup.

### Correctness risk

Low if the fallback remains. Do not restore unconditional append: reused lower IDs would break sorted-list binary searches.

# What not to optimize based on this A/B

1. **Do not remove freestanding guards in `cio.zig` or `explore.zig`.** They are compile-time target accommodations and do not explain native timing.【src/cio.zig:261-302】【src/explore.zig:2518-2525】

2. **Do not revert `@splat` conversions.** They are Zig 0.17 migration syntax, with no credible per-file runtime cost.【src/watcher.zig:44-49】【src/explore.zig:7535-7541】

3. **Do not revert sorted posting insertion.** The correctness requirement is real; optimize with a guarded append fast path instead.【src/index.zig:1089-1105】【src/index.zig:1390-1412】

4. **Do not treat the current medians as proof of regression.** The observed differences are roughly 0.5% and 1.8%, and the relevant source diff does not add corresponding work to the measured native scan path.

# Recommended benchmark sequence

1. **Establish variance:** 30–50 alternating A/B runs, pinned CPU, fixed worker count, report median, p10/p90, and MAD.
2. **Profile current scan phases:** use `CODEDB_INDEX_PROFILE`; add temporary benchmark-only subdivisions for root-open/read, parser initialization, parsing, packed clone, commit, dependencies, and symbol indexing.【src/watcher.zig:691-708】【src/watcher.zig:794-833】
3. **Prototype benchmark only—one `Dir` per worker:** likely the lowest-risk measurable win.
4. **Prototype parser-context reuse:** compare allocations/file and outline equality.
5. **Benchmark persistence separately:** trigram build, postings write, lookup write, rename, and mmap load; do not fold these into `initialScan`.
6. **Run size-skew workload:** determine whether static chunks or parser setup dominate before changing scheduling.

# Inferred findings

- The supplied 1–2 ms differences are probably noise or compiler/runtime effects rather than source-level migration overhead. This follows from the lack of relevant native hot-path changes, but cannot be proven without distributions and phase profiles.
- Per-file `openDir` and full `Explorer` construction are likely the most reliable ways to beat baseline materially because both scale directly with file count and occur on every scan.
- On repositories dominated by a few large files, scheduling and parser work will dominate; on repositories with thousands of tiny files, directory opens, parser construction, allocation, and outline cloning should dominate.
