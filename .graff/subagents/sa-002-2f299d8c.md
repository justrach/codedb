## task

Use codedb to find the worker pool or thread pool used for reading files and building trigram shards. Look for thread pools, task queues, or spawn logic after the initial walk. Identify how file paths are handed off to workers and how results (shards) come back. Note any existing parallel patterns (e.g., parallel stat, parallel read).

## report

**No central thread/task pool; ad-hoc `std.Thread.spawn` on static chunks (after serial walk).** (All evidence from `src/watcher.zig` + cross-refs in `src/index.zig`, `src/bootstrap.zig`, `src/background.zig`, `src/test_*.zig`.)

### 1. Initial walk (serial, produces paths for workers)
- `collectInitialScanEntries` (watcher:509) runs a single `FilteredWalker` (watcher:275 struct; `init` + `next` loop at 294/386).
- Walk does `dir.iterate()` + `dir.statFile` + `store.recordSnapshot` + appends `InitialScanEntry{path, skip_trigram}` (filtered by `trigramFileCap`, `shouldSkipFile`, ignore patterns).
- Returns contiguous `ArrayList(InitialScanEntry)`. No parallelism here. (Called by `initialScanWithWorkerCount:639`, `initialScanWithTrigrams:987`, tests.)

Then `n_workers = max(1, min(worker_count, entries.len))` (capped at 8 or `CODEDB_SCAN_WORKERS`; see `initialScan:1115`, `initialScanWithTrigrams:994`).

### 2. Worker handoff + spawn logic (post-walk)
Static chunking (no queue):
```zig
// watcher:708 (similar at 932,1040)
const chunk_size = ...; var offset=0;
for (0..n_workers) |i| {
    const chunk = entries.items[offset .. offset+count];
    ...
    threads[i] = try std.Thread.spawn(.{}, worker_fn, .{io, ..., chunk, shard_ptr, ...});
}
```
- `initialScanWithWorkerCount` (623): spawns `initialScanWorker` (723) for outlines+words (trigram=null).
- `initialScanWithTrigrams` (975):
  - `skip_outlines`: spawns `readAndBuildTrigramShardWorker` (1055).
  - else: spawns `initialScanWorker` with `&shards[i]` as trigram_shard (1087).
- `buildTrigramsFromCache` (865): for hot `ContentCache`, collects `CachedEntry[]`, spawns `cachedTrigramBuildWorker` (944).
- Same pattern in `buildFrequencyTableFromMapParallel` (index:3272; spawns `freqCountWorker`).

Workers get **disjoint contiguous slices** of paths/entries (or cached slices). No dynamic tasks or shared queue.

### 3. Per-worker work (read + build)
- `initialScanWorker` (595): per-chunk loop → `parseInitialScanWorkerEntry` (561) → `readIndexableFile` (173; does `dir.readFileAlloc` + binary check) + `parseContentForIndexing`. Optionally `word_shard.indexFile(...)` and/or `trigram_shard.indexFile(...)`. Then `results.publish`.
- `readAndBuildTrigramShardWorker` (783): openDir + statFile + `readIndexableFile` (into c_allocator) + manual trigram loop + `shard.insertBulkMapNew` (skips >1MB).
- `cachedTrigramBuildWorker` (829): same extract+insert but on pre-cached `CachedEntry` (no disk).
- All use `c_allocator` (or worker arena) for cross-thread safety; shards are private.

(Reads/stats are **not** parallelized outside these; walker is serial. No "parallel stat" or "parallel read" helpers found.)

### 4. Results/shards back to main
- **Outlines + commit order**: `WorkerParsedResults` (104 struct) per worker: `items:[]?PersistedScanFile`, `ready: atomic.Value(usize)`, mutex+condvar.
  - Worker: `publish` (123) does `items[index]=...; ready.store(release);` (batch signal every 64 or at end).
  - Main (730): `for workers { for items { if (takeReady) commit... } }`. `takeReady` (136) waits on acquire+condvar.
  - Guarantees serial commit order (matches doc_id assignment).
- **Shards** (Word/Trigram):
  - Workers build into private `*WordIndex` or `*TrigramIndex` (arena/c_allocator).
  - After join (739/948/1058): main does `mergeShard` (index:391; for words, remaps doc_ids by base) or `mergeBulkShard` (index:1455; for trigrams, optionally transfers posting lists if same allocator).
  - Order of shards == order of chunks == serial order (see comments at watcher:605, index:389).
- Errors: `word_index_error` or `build_errors[]` checked post-join.
- Cleanup: explicit `deinit` + free after merge.
