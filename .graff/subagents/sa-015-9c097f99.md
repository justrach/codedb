# Release/PR readiness audit

**Verdict: refuted — the dirty tree is not safe to merge or release as-is.**

The intended Zig 0.17 migration and performance changes compile and the full local build graph passes, but release readiness is blocked by unignored harness/generated artifacts and by a vendor tree that currently contains **119 MB of generated Zig cache data**. The release claims also exceed what this audit could independently reproduce, and the claimed retrieval parity is weakened by net test deletions.

## Merge blockers

### 1. Harness, Graff, trace, and root cache artifacts are unignored

The dirty tree contains:

- `.graff/` — **2.9 MB**
- `.harness/`
- `harness.trace.jsonl` — **196 KB**
- `harness.trajectory.jsonl` — **132 KB**
- `.zig-global-cache/` — **48 MB**

None is covered by the root `.gitignore`. `git check-ignore` returned no match for all five classes. They are currently untracked, so they are not yet in a commit, but a broad `git add -A` or GUI “stage all” would include them.

The trajectory file contains session/prompt material. I did not find common private-key or token signatures, but traces are still internal generated/session data and should not enter the PR.

**Exact remediation**

Add root ignore rules before staging:

```gitignore
# Local agent/harness state
.graff/
.harness/
harness.trace.jsonl
harness.trajectory.jsonl

# Explicit global cache used by the Zig 0.17 migration workflow
.zig-global-cache/
```

If harness output names can vary, prefer a narrowly scoped pattern such as:

```gitignore
harness*.trace.jsonl
harness*.trajectory.jsonl
```

Then verify:

```sh
git check-ignore -v \
  .graff/sessions/example.json \
  .harness/settings.json \
  harness.trace.jsonl \
  harness.trajectory.jsonl \
  .zig-global-cache/example
```

Do not stage those paths. If they are not needed locally, remove them from the working directory after the audit; otherwise leave them ignored.

### 2. The vendor directory contains 119 MB of generated cache material

`vendor/nanoregex/` is approximately **120 MB**, of which **119 MB** is:

```text
vendor/nanoregex/.zig-cache/
```

There are 75 generated cache files, including compiler output and cache metadata.

The good news is that `vendor/nanoregex/.gitignore` ignores `.zig-cache/`, and `git add -n vendor` did not propose adding cache files. The bad news is that the PR is still relying on a nested vendor ignore rule to prevent a very large accidental artifact upload. The dirty-tree audit should not be considered clean while generated build output remains inside the vendored source.

**Exact remediation**

1. Remove only the generated vendor cache before staging:

   ```sh
   rm -rf vendor/nanoregex/.zig-cache
   ```

2. Retain `vendor/nanoregex/.gitignore`, and optionally add a root defense-in-depth rule:

   ```gitignore
   vendor/**/.zig-cache/
   ```

3. Verify no generated files would be staged:

   ```sh
   git add -n vendor | grep -E '(\.zig-cache|\.o$|compiler_rt|timestamp)'
   ```

   This must produce no output.

4. Review the final vendor file list:

   ```sh
   git add -n vendor
   ```

- immutable-corpus parity with Zig 0.16

What I directly reproduced:


However, the default Zig test output and `--summary all` did **not** print the claimed `706/710` count or four skips. I also did not reproduce the focused 180-test run, MCP E2E, cross-version corpus parity, lint command, or benchmarks during this audit.

This does not prove the numbers are false, but the release text presents them as release verification without including durable evidence or commands sufficient to reproduce every claim.

**Exact remediation**

Before merge, attach CI logs or a checked-in/reviewable verification record showing:

1. The exact command and uncached output for the 706/710 count and four skips.
2. The exact focused-index command and 180/180 result.
3. The MCP E2E command and 20/20 result.
4. The immutable corpus hash/archive procedure and old/new hit-count output.
5. Benchmark raw output supporting all medians and geometric means.
6. The exact “modified-file lint” command and output.

Run tests uncached or with isolated cache directories so the release evidence is not merely:

```text
run test cached
```

For example, use temporary local/global caches appropriate to the pinned Zig build. If these artifacts cannot be produced, soften the changelog to distinguish historical benchmark observations from verification performed on the final PR tree.

### 4. Retrieval-parity confidence is weakened by test deletions

The dirty diff removes:

- 50 lines from `src/test_parser.zig`
- 47 lines from `src/test_query.zig`
- net 51 lines from `src/test_explore.zig` despite other additions

The total dirty test changes include substantial additions elsewhere, and the suite passes, but deleting parser/query assertions is directly relevant to the broad changelog statement:

> “No scoring, ranking, tokenization, parser, filtering, or result-rendering formula changed…”

A passing suite after dropping assertions is not sufficient evidence that behavior is unchanged. This is especially concerning because the migration removes `mcp-zig` and replaces helpers locally.

**Exact remediation**

- Explain every deleted assertion in the PR description.
- Restore assertions that remain semantically valid.
- If Zig 0.17 required rewriting them, migrate them rather than deleting them.
- If coverage moved, identify the exact replacement test names and show equivalence.
- Add focused tests for `src/mcp_json.zig`, especially:
  - EOF with and without a trailing newline
  - messages at and over `MAX_LINE`
  - malformed/non-string fields
  - all JSON control-character escapes
  - allocation failure behavior if the project tests OOM paths

Until the deletions are justified or replaced, the strongest “unchanged retrieval” formulation does not survive the audit.
