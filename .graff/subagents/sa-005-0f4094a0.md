## Concrete findings

**No actionable correctness, security, framing, or memory-safety findings.**

### 1. JSON-RPC framing and CR/LF sanitization remain equivalent

**Target:** `src/mcp.zig:5283-5305`, especially `5293-5302`  
**Base:** `src/mcp.zig:5309-5328`, especially `5317-5323`

Attack performed:

- Payload with no CR/LF.
- Payload beginning or ending with CR/LF.
- Consecutive `\n`, `\r`, `\r\n`, and `\n\r`.
- Multiple separated newline runs.
- Empty payload.
- Malformed/noncanonical producer output containing raw line breaks.
- OOM at capacity reservation or payload append.
- Final JSON-RPC record delimiter interaction.

Result:

- When `result` contains neither byte, the new branch appends the entire payload. This is byte-for-byte identical to the base loop, which would append one run spanning the full payload.
- When either byte exists, the code executes the same loop as base and removes every individual `'\n'` and `'\r'` byte. CRLF therefore still loses both bytes, not only one.
- The final framing delimiter remains exactly `"}\n"` at `src/mcp.zig:5304`.
- Raw CR/LF cannot escape into line-delimited JSON-RPC framing through this change.
- Errors still cause an early return before `stdout.writeAll`; the function does not emit a partially assembled frame.
- `stdout_broken` handling is unchanged immediately after the changed range.

**Severity:** None  
**Deploy blocker:** No

One pre-existing caveat remains: stripping raw CR/LF can change the meaning of malformed JSON rather than rejecting it. The PR does not introduce or worsen that behavior; the base implementation did exactly the same sanitization.

### 2. Context source rendering is materially equivalent for normal, CRLF, and EOF inputs

**Target:** `src/mcp.zig:2627-2634`  
**Delegated implementation:** `src/explore.zig:2825-2833`, `src/explore.zig:1000-1028`  
**Base:** `src/mcp.zig:2626-2660`

Attack performed:

- First-line and non-first-line symbols.
- Single-line and 40-line capped bodies.
- `line_end <= line`.
- Requested lines beyond EOF.
- Empty files.
- Files with and without a final newline.
- CRLF files.
- Allocation failure while reading, building offsets, or appending output.
- Cache staleness and lock/ownership behavior.

Result:

- The same range is requested: `sr.line` through `min(sr.line_end, sr.line + 39)`, or only `sr.line`.
- Output format remains the same: seven-space prefix, right-aligned five-column line number, `" | "`, source bytes, and `\n`.
- Both implementations split on LF only, so CRLF source lines retain the `\r` in rendered text. This is not a newly introduced CR behavior.
- Both preserve the trailing empty logical line when a file ends in LF.
- Out-of-range requests append nothing.
- `appendLineRange` holds the Explorer shared lock while borrowing cached content and properly deinitializes an owned disk-read fallback through `content_ref.deinit()`.
- The line-offset cache is invalidated on content replacement/removal (`src/explore.zig:1952` and `2651`), defeating the stale-offset/pointer-reuse counterexample considered during review.
- On offset-cache allocation failure, the function returns `false`; `mcp.zig` intentionally ignores that result, matching the base path’s effective behavior when `getContent` fails.
- An append allocation failure can leave an abbreviated context section, but it remains text later JSON-escaped by the normal response construction. It does not create malformed JSON-RPC framing. Base also suppressed rendering allocation errors.

**Severity:** None  
**Deploy blocker:** No

## Behavior changes worth noting, but not findings

- `handleContext` now builds and uses the line-offset cache rather than allocating a full file copy and scanning from byte zero. This can change performance and allocation patterns, but I found no normal-input output difference.
- Under severe allocator failure, the exact point at which source-body rendering stops may differ from base. The enclosing MCP response remains structurally valid, and both versions already treat this optional context enrichment as best-effort.
- The no-newline `writeResult` path is purely an optimization; newline-bearing payloads continue through the original sanitizing implementation.

## Final verdict

**SURVIVES. Deploy blocker: No.**

What would have broken it:

- Treating `\r\n` as one match and leaving one byte behind.
- Bypassing sanitization based only on searching for `\n`.
- Writing response fragments before complete frame assembly.
- Different EOF/trailing-empty-line semantics in `appendLineRange`.
- Failure to invalidate cached offsets when file content changes.
- Borrowed content escaping the Explorer lock or owned fallback content leaking.

None of those counterexamples held.
