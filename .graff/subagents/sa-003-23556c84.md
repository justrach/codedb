## Findings

- **High — stale line-offset cache can return incorrect source lines after an uncached file changes on disk.**  
  **`src/explore.zig:946-950, 2827-2832, 2877-2880`**  
  `appendLineRange` passes `readContentForSearch` data into `LineOffsetCache`. On a content-cache miss, that data is a temporary disk-read allocation freed when `appendLineRange` returns. The offset cache nevertheless identifies it solely by `(content.ptr, content.len)`. Allocators commonly reuse the same address for the next same-sized read. If the file changes externally while retaining its byte length but moving newlines, the next call can accept the old offset table and slice the new content at stale boundaries. Unlike `indexFile`, an external disk change does not call `line_offsets.invalidate`. This can produce wrong line numbers/text in production context output. The new test only exercises canonical cached content, so it does not cover this counterexample.

- **Medium — tree and outline cache hits race mutations and can serve stale output after the mutation has completed.**  
  **`src/explore.zig:2683-2688`** and **`src/explore.zig:3065-3071`**  
  Both methods load `search_gen` and consult their render cache before acquiring the Explorer shared lock. Counterexample: reader loads generation N; writer acquires the exclusive lock, bumps to N+1 and completes an index/remove; reader then finds and returns the generation-N cached entry without ever taking the Explorer lock. Thus generation tagging does not guarantee freshness. The same ordering also permits rendering post-mutation state under an old generation when the mutation occurs between the generation load and shared-lock acquisition. Cache lookup and generation observation need to be synchronized with Explorer mutation state.

## Verdict

**Refuted. Blocking issue present:** the uncached disk-read path can reuse stale newline offsets and return incorrect source content. The render-cache mutation race is an additional non-blocking correctness issue.
