## High severity

### `CODEDB_BENCH_OUT` breaks the documented A/B runner when given a relative path
**Files:** `scripts/bench-ab.sh:24-27`, `scripts/bench-ab.sh:53-58`, `docs/performance-0.2.5830.md:155-158`

The script preserves `CODEDB_BENCH_OUT` verbatim, but each sample is launched after changing to a different working directory.

Concrete failure sequence:

1. Run the documented form:
   ```bash
   CODEDB_BENCH_OUT=zig-out/bench-ab scripts/bench-ab.sh HEAD~1
   ```
2. `OUT` remains the relative string `zig-out/bench-ab`.
3. A base sample changes directory to `$WT` and writes:
   ```text
   $WT/zig-out/bench-ab/base-01.json
   ```
4. A head sample changes directory to `$REPO_ROOT` and writes:
   ```text
   $REPO_ROOT/zig-out/bench-ab/head-01.json
   ```
5. The comparator runs from the caller/repository directory against `zig-out/bench-ab`, where it sees head samples but no base samples.
6. `paired_files()` rejects the run as unpaired. The advertised persistent-output invocation therefore cannot complete or produce `report.md`.

The script must resolve `OUT` to an absolute path before `run_sample` changes directories. As written, a primary documented workflow is unusable unless the caller happens to supply an absolute path.

## Medium severity

### The PR benchmark compares against a mutable branch tip rather than the reviewed PR base
**File:** `.github/workflows/bench-regression.yml:54-60`

The workflow receives the immutable base commit as `github.event.pull_request.base.sha`, but instead fetches `github.event.pull_request.base.ref` and benchmarks `FETCH_HEAD`.

Concrete failure sequence:

1. A PR is opened against release branch commit `A`; GitHub records `base.sha = A`.
2. The workflow is queued.
3. Before its base-benchmark step runs, another PR advances the release branch to `B`.
4. `git fetch origin "$BASE_REF"` fetches `B`, and the worktree is created from `B`.
5. The checked-out PR merge/head and the benchmark baseline no longer describe the same review state.
6. A performance change in `B` can either manufacture a regression attributed to this PR or hide one, producing a false fail or false pass.

This also makes reruns of the same workflow nondeterministic. The base worktree should be created from the event’s immutable base SHA.

### The new paired/parity gate is silently absent for the exact release base under review
**File:** `.github/workflows/bench-regression.yml:81-90`

`origin/release/0.2.5829` does not contain `corpus_hash` in `src/bench.zig`. Consequently, on this PR:

1. The base benchmark succeeds using the normal schema.
2. The condition at line 88 finds no `corpus_hash`.
3. The paired benchmark step exits successfully without creating any paired samples or running the parity comparator.
4. CI falls back to the old one-shot comparison at lines 125-127, which has no response-hash or corpus-parity validation.

Thus the commit that introduces substantial performance-sensitive behavior is not itself protected by the new parity gate against its declared PR base. A changed result with improved timing can pass this workflow because the fallback comparison checks latency and tool presence only. If parity-checked evidence is a merge requirement for this performance batch—as the documentation presents it—this is a deploy blocker rather than merely reduced coverage.

## Low severity

### “Require parity” still accepts complete parity opt-out
**Files:** `scripts/compare-bench-paired.py:107-126`, `scripts/test_compare_bench_paired.py:64-73`

When both revisions set a tool’s `parity` field to false, `--require-parity` reports `SKIP` and succeeds.

Concrete failure sequence:

1. A candidate changes a tool’s output and changes its benchmark case to `parity: false`.
2. The selected base also marks that tool false, or a future benchmark policy disables it on both sides.
3. Run `compare-bench-paired.py --require-parity`.
4. No response hashes are compared, and the comparator returns success for that tool.

This contradicts the intuitive CLI contract of `--require-parity`; it actually means “require parity only for tools that self-declare parity.” That may be intentional for stateful tools, but the comparator provides no external required-tool policy, so benchmark-controlled metadata can weaken the gate. The included test explicitly codifies this bypass.
