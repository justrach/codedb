This alone is minor, but confirms the dirty documentation is not yet a clean final release state.

### 2. Provenance comparator can falsely pass an arbitrary candidate commit/tree

In `validate_provenance()`, source-tree verification is performed only when `source_sha` appears in the hard-coded `PINNED_COMMIT_TREES` map. That map contains the production baseline and baseline harness, but not candidate `91ecd6e…`.

For a head sample, the comparator requires only:

- syntactically valid 40-hex `source_sha`
- syntactically valid 40-hex `source_tree_sha`
- consistency across samples
- `production_source_sha == source_sha`

It does **not** require:

- head source SHA equals the intended release candidate supplied externally
- head source SHA exists in the repository
- head tree equals `git rev-parse <head-sha>^{tree}`

Concrete counterexample: replace every head sample’s source and production SHA with the same invented 40-hex value and replace its tree with another invented 40-hex value. With the other fields unchanged, provenance can still report `PASS`.

The actual 40 samples were independently checked and do match Git, so this does not invalidate these specific values. It does invalidate the claim that the comparator itself enforces candidate commit/tree provenance.

### 3. Provenance is mutable self-reported JSON, not revalidated evidence

`run-bench-json.py` records Git and compiler details at collection time, but the comparator later accepts the JSON fields without independently consulting Git or hashing the current compiler. Apart from the two hard-coded baseline trees, provenance validation is schema and cross-sample consistency checking.

Thus edited samples can remain provenance-valid if their invented metadata is internally consistent. For final release gating, the intended candidate SHA/tree should be supplied to the comparator and checked against Git, or the evidence should be signed/attested externally.

Again, manual audit rescued the current evidence, but the implementation has a genuine false-pass path.

### 4. Duplicate tool records are silently collapsed by the comparator

`tool_map()` uses:

```python
{tool["tool"]: tool for tool in data["tools"]}
```

A sample containing duplicate records for one tool silently keeps only the last record. The comparator does not reject duplicates.

The audited samples contain no duplicates, so this is not a defect in the present data. It remains a provenance/parity gate false-pass path: a malformed or manipulated sample can include extra contradictory results that are silently discarded.
