### Counterexample: mmap assumes disk posting lists are sorted by `file_id`; the writer does not ensure that

`MmapTrigramIndex.candidates` intersects posting ranges as sorted sequences:

- `src/index.zig:2361–2380`: merge intersection advances a single cursor under the assumption `p.file_id >= id`.
- `findPostingMask` also binary-searches a posting range by `file_id` (`~2426`).

But persistence builds disk file IDs from hash-map iteration:

- `TrigramIndex.writeToDisk`, `~1728–1741`: `file_table` / `disk_path_to_id` are built from `file_trigrams.keyIterator()` when normal per-file tracking exists.
- `~1751–1753`: in-memory `doc_id` is remapped through that arbitrarily ordered `disk_path_to_id`.
- `~1825–1845`: postings are emitted in the existing posting-list order, which is sorted by **in-memory `doc_id`**, not remapped disk `file_id`.

Thus a disk posting range can be unsorted by `file_id`, while mmap search requires it sorted.

A minimal shape is:

| in-memory doc | content contribution | disk file ID after hash-map iteration |
|---|---|---|
| 0 | `abc` | 2 |
| 1 | `bcd` | 1 |
| 2 | `abcd` | 0 |

For query `abcd`:

- `abc` posting range is emitted as `[2, 0]` (docs 0, 2)
- `bcd` posting range is emitted as `[1, 0]` (docs 1, 2)

The mmap sorted merge can consume `[1, 0]` while looking for `2`, exhaust it, and reject file ID `0`—the actual `abcd` match. The heap path remains correct because its lists are sorted by its own `doc_id`.

This predates `428d8df`; the streamed writer retained the same remap-and-emit ordering. But it blocks classifying any further mmap search-path change as safe.

### Proposed optimization assessed

There *is* an obvious performance parity gap, but it is not presently safe to prioritize:

- Heap `TrigramIndex.candidates` hoists consecutive-trigram pair construction and posting-list probes once per query (`~1560–1576`).
- Mmap `candidates` repeats normalization, trigram packing, and **two `lookupTrigram` binary searches** for every surviving candidate and consecutive pair (`~2388–2410`).

After correctness is repaired, mmap can safely mirror heap’s precomputed pair table:

```zig
const Pair = struct {
    range_a: ?Range,
    range_b: ?Range,
    next_bit: u8,
};
```

Build it once per query, then retain the existing per-candidate `findPostingMask` checks. This removes approximately:

- `2 × log2(lookup-entry-count)` mmap lookup comparisons per candidate/pair,
- repeated packing/normalization per candidate/pair.

It is most valuable for long queries with broad trigram intersections. It will not materially help rare-trigram queries, because candidate intersection and the two posting-mask searches then dominate. Added memory is only `O(query length)` and is negligible relative to the existing unique-trigram map and range list.

### Coverage gaps

`428d8df` added a useful 4,097-posting batch-boundary test, but it:

- reloads via heap `TrigramIndex.readFromDisk`, not `MmapTrigramIndex`;
- queries only `abc`, a single-trigram query with no range intersection or bloom-pair verification;
- therefore cannot expose disk-file-ID ordering defects.

Existing mmap coverage is also insufficient:

- `issue-164: mmap trigram index returns same candidates as heap index` compares **length**, not exact path-set equality.
- Its query has effectively unique matching trigrams, so it does not exercise divergent multi-document posting ranges.
- Heap-only tests cover bloom and `loc_mask` adjacency behavior; there is no mmap parity coverage for them.
- The sole candidate performance regression test benchmarks heap only.

### What would have made this survive

Before the hoisting optimization, persistence needs an explicit invariant:

1. Either assign disk `file_id`s in ascending live `doc_id` order, **or**
2. sort each emitted `DiskPosting` range by remapped `file_id`.

Then add mmap round-trip parity tests that assert exact candidate sets—not counts—across:

- overlapping-but-not-identical posting lists (`abc`, `bcd`, `abcd`);
- multiple file insertion/path permutations;
- repeated trigrams and mixed case;
- bloom `next_mask` and `loc_mask` rejection cases;
- a 4,096/4,097 batch-boundary corpus loaded through mmap.

Only after that, hoisting mmap pair/range lookup is a focused, low-risk performance follow-up.
