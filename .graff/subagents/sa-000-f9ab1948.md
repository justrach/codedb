**Misleading facilities/metrics**

- `src/benchmark.zig` is an in-process microbenchmark, not the production cold CLI path: it excludes bootstrap snapshot checks, persistence, mmap, frequency/centrality, daemon behavior, and process startup.
- Its query figures are arithmetic means over repeated queries in one process; they do not represent cold CLI latency. Although search cache is disabled at `src/benchmark.zig:316`, OS cache, allocator state, branch predictors, and built indexes remain warm.
- `index_ms` truncates to whole milliseconds at `src/benchmark.zig:344`, weakening sensitivity around a ~187 ms result.
- Fresh `HOME` removes codedb state but does **not** make filesystem pages cold. Call it “fresh application state,” not “cold disk.” Real cold-cache tests require controlled cache dropping or a corpus larger than RAM and entail much higher variance.
- Hyperfine process time combines startup, bootstrap, indexing, query, formatting, and teardown; use it as an end-to-end acceptance metric, not hotspot attribution.
- Startup at 1.5–1.6 ms is below a useful single-run attribution scale; batch hundreds/thousands and inspect distribution/tail latency.
- CI is not reliable for small deltas: `.github/workflows/bench-regression.yml:18` uses shared `ubuntu-latest` and runs head before base, rather than interleaving.
- That workflow invokes `scripts/run-bench-json.py`, which runs `zig build bench`, while the inspected repository benchmark is the distinct `zig build benchmark` target. `scripts/compare-bench.py` also compares external tool `avg_latency_ns`, not `src/benchmark.zig`’s `index_ms` or per-query rows. Do not cite that CI gate as validation of initial-scan changes.
