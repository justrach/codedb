# Existing rows that could plausibly show 2–3× gains

These are plausible algorithmic targets, but the present benchmark cannot reliably distinguish a real gain from cache/order artifacts.

### `codedb_context`

**Plausible real headroom:** yes.

At roughly 121 µs locally, this row performs enough selection, graph/search, and formatting work to permit a genuine 2× improvement. It is also the only current row large enough for CI’s 50 µs absolute threshold to have reasonable sensitivity.

**Counterevidence:** the second telemetry-enabled pass was about 62 µs—roughly 2× faster despite telemetry being additional work. That strongly indicates warmed state or run-order effects, not telemetry acceleration.

**Required proof:** cold and warm strata, alternating base/head runs, result equivalence, and component timings.

### `codedb_edit`

**Plausible real headroom:** possibly, especially in parsing, filesystem writes, reindexing, and snapshot bookkeeping.

**Current flaw:** `resetBenchTarget` resets the in-memory explorer/store but does not restore the file on disk. After the first iteration, later operations may replace content already present on disk. The benchmark therefore mixes first-change and repeat/no-op-like states.

The telemetry-enabled pass was about 55% faster than telemetry-off, another clear order/state warning.

**Verdict for a claimed 2–3× win:** unsupported until every iteration starts from identical disk and index state and verifies the resulting file/index/store state.

### `codedb_read`

**Plausible real headroom:** maybe 2× for larger, uncached files or deep reads, but not convincingly for this tiny 20-line case.

The standard case reads 20 lines from a small, repeatedly accessed file. A 2–3× gain here would likely come from file/content caching or avoiding output work, not an important production improvement. `edge_read_deep` is the more meaningful target.

### `codedb_search`

**Plausible real headroom:** on cold, large, high-candidate searches, yes. On this row, doubtful.

The standard row uses a 22-file, approximately 1.1 MB corpus, fixed query, fixed result limit, and repeated calls. Search caches and hot content dominate. The pathological search rows in `bench_edge.zig`, with explicit cache busting, are much better candidates for real 2–3× improvements.

### `codedb_symbol`

Potentially 2× only if the query falls through expensive ranking or formatting. The current exact `main` query on a tiny corpus is not a convincing target. A 2× result would save only about 7 µs locally.

### `codedb_bundle`

A 2–3× **end-to-end** gain is plausible only if bundle avoids repeated JSON-RPC parsing, envelope construction, transport, and client round trips. The current benchmark does not time those savings.

For inner dispatch alone, the current three-op bundle is already only about 15.5 µs, versus approximately 20 µs for the separately measured outline/search/word rows. Another 2–3× reduction would require one of:

- shared computation across sub-ops,
- parallel execution,
- cache/state changes,
- less output,
- or omitted work.

None is demonstrated here. Parallelism would also need ordering, shared-state, error, truncation, and activity-accounting parity tests.

# Rows already near the benchmark’s lower bounds

“Lower bound” here means the lower bound of this dispatch-only fixture—not real MCP latency.

### `codedb_deps` — 70 ns

This is clearly a warmed response-cache hit. `dispatch` has a special path-only deps cache keyed by store sequence and path. It cannot plausibly improve 2–3× in a meaningful way; the timer and benchmark overhead are already comparable to the measured work.

It is not representative of a dependency traversal.

### `codedb_find` — 650 ns

The query `"main"` appears to hit an exact-file fast path. This is already effectively a hash lookup plus tiny rendering. A 2–3× claim would be numerically fragile and operationally irrelevant.

### `codedb_status` — ~2 µs

Already near fixed formatting and map/count access costs. There is little meaningful 2–3× opportunity unless output semantics or measured scope change.

### `codedb_word` — ~3.2 µs

For a warmed exact lookup on 22 files, this is near the fixture’s floor. Large posting lists or cold mmap/heap promotion are different workloads and need separate rows.

### `codedb_tree` / `codedb_hot` — ~5 µs

These may have modest allocation/formatting headroom, but a repeatable 2–3× improvement without output changes is unlikely. Output byte equality alone would not prove ordering or content parity.

### `codedb_outline` — ~6 µs

The response is already around 6.7 KB. Since the timer includes handler rendering but excludes outer MCP escaping and transport, further 2–3× reductions would be suspicious unless allocation profiling identifies a concrete source.

# Benchmark flaws that can create fake wins

## P1: The benchmark does not measure end-to-end MCP dispatch

`BenchContext.runToolCall` starts its timer immediately before `dispatch(...)` and stops immediately afterward. The following are outside the reported latency:

- JSON-RPC request parsing
- `tools/call` parameter selection and validation
- tool-name-to-enum conversion
- telemetry
- query/file-access logging
- convergence governor
- summary generation
- guidance generation
- JSON escaping
- MCP content envelope construction
- `writeResult`
- stdout write/flush
- process or IPC latency

Yet the output labels this “E2E MCP Tool Benchmarks.”

This is merge-blocking for any claim about MCP round-trip, batching, response serialization, or client-visible latency.

## P1: Bundle savings are structurally omitted

The primary reason to bundle is avoiding repeated request parsing, response envelopes, transport round trips, and client scheduling. The benchmark:

- directly calls `.codedb_bundle`,
- supplies already parsed JSON objects,
- times only inner dispatch,
- does not compare bundle against three complete standalone MCP calls,
- does not include stdin/stdout framing or JSON parsing,
- and excludes outer result serialization from timing.

It therefore cannot answer whether bundle/batch is faster for a client.

## P1: Cache and run-order contamination

Every case runs:

1. telemetry disabled,
2. then telemetry enabled,

against the same long-lived store, explorer, project cache, and process. There is no alternation or randomization.

Observed contradictions demonstrate the problem:

- Snapshot: approximately 36.9 µs first pass vs 0.15 µs second pass
- Edit: second pass roughly 55% faster
- Context: second pass roughly 49% faster
- Search and symbol also became faster with telemetry enabled

Telemetry did not accelerate these operations. The first pass populated caches or altered state.

Snapshot is the clearest counterexample: the first dispatch builds the snapshot; subsequent iterations call `SnapshotCache.appendIfFresh`. Increasing iterations or adding a warmup can manufacture an enormous “improvement” without changing production semantics.

## P1: Current working-tree optimization is not exercised by reported rows

The working-tree change optimizes trigram **construction** in `TrigramIndex.indexFile`. In `src/bench.zig`, `watcher.initialScan` occurs before per-tool timing. The trigram masks are asserted equivalent, so the resulting query index should be the same.

Consequently, a claimed 2–3× gain in `codedb_search`, `codedb_bundle`, or another timed MCP row from this patch would be implausible. Any such movement is more likely noise, cache state, or compiler/layout effects.

The relevant benchmark should time initial scan or controlled incremental reindexing. The standard MCP table does neither.

## P1: CI threshold exempts almost all current rows

`compare-bench.py` fails only when both conditions hold:

- regression exceeds 10%, and
- absolute regression exceeds 50,000 ns.

Examples using local values:

- `codedb_bundle` could regress from 15.5 µs to about 65.5 µs—over **4× slower**—without exceeding the absolute gate.
- `codedb_search` could regress by roughly **5.6×** before failing.
- `codedb_deps`, `find`, `status`, `word`, `tree`, and `outline` can regress by orders of magnitude before CI blocks them.

This contradicts the project’s stated 10% benchmark-critical threshold.

## P1: Different compilers can be compared

CI intentionally builds base using its declared Zig version and head using the current pinned Zig version. During a migration, the result is:

> old code + old compiler versus new code + new compiler

That cannot isolate a source-level performance improvement. Compiler code generation, allocator behavior, standard library implementation, and timing behavior are confounders.

A migration comparison may be useful as a release outcome test, but not as evidence that a specific code patch caused a speedup.

## P2: No statistical design

The standard suite records only one arithmetic mean:

- no distribution,
- no median,
- no percentile,
- no standard deviation/MAD,
- no confidence interval,
- no repeated process launches,
- no outlier policy,
- no base/head interleaving,
- no CPU affinity or load controls.

The edge suite records a minimum, but minimum latency is especially easy to improve accidentally through noise.

## P2: Tiny iteration counts for unstable rows

Iterations range from 10 to 100, with no explicit warmup in the standard suite. For microsecond-scale handlers on shared CI, this is inadequate. Individual cases take far less time than scheduler and runner variation.

## P2: Correctness is not validated during timing

The benchmark records only the last response size. It does not assert:

- exact response bytes or a response hash,
- result ordering,
- per-op success/error status,
- truncation behavior,
- bundle op count,
- post-edit file/index state,
- cache-hit versus cache-miss classification.

A patch can “win” by returning incomplete, reordered, cached-stale, truncated, or error output. Equal byte length is not semantic equivalence.

## P2: Stateful cases affect later cases

Cases share one store/explorer/cache, and mutation cases are interleaved with read cases. `codedb_edit`, snapshot cache population, search caches, and lazy word-index loading can change later workloads. Fixed order makes this systematic rather than random.

## P2: Corpus is too small and homogeneous

The standard corpus has only 22 selected files. This is useful for smoke testing but not representative of repositories with:

- tens of thousands of files,
- large posting lists,
- mmap indexes,
- cold page cache,
- many symbols with the same name,
- large bundle outputs,
- response-cap truncation,
- mixed project selection.

## P2: Bundle reserve policy can bias chosen fixture

`handleBundle` reserves by tool type—24 KB for outline, 4 KB for search/word/callers, and so on—and pre-reserves up to the 200 KB cap for the outer output. The fixed bundle can therefore look allocation-efficient because its output shape matches those reserve guesses. Small-output, large-output, truncating, error, and 20-op bundles need separate rows.

## P3: Reporting is misleading

- The heading says E2E despite timing inner dispatch only.
- `formatPct` takes the absolute value, hiding whether telemetry made a case faster or slower in the human table.
- Response size comes from the final iteration only.
- New benchmark rows are silently skipped by base/head comparison.
- Removed rows fail, but renamed/replaced rows can evade historical comparison.

# Acceptance gates

## Gate 1: Semantic parity

For every optimized row:

- Hash or byte-compare the complete raw handler output against baseline.
- Assert result count and ordering.
- Assert error status and truncation markers.
- For bundle, assert every op index appears exactly once and has the same success/error result.
- For edit, restore the physical file before every sample and verify disk content, explorer state, and store sequence afterward.

No performance result is accepted if output parity is absent.

## Gate 2: Separate benchmark scopes

Publish distinct metrics:

1. **Handler-only:** direct `dispatch`
2. **In-process MCP:** parsed `tools/call` through `handleCall`, including envelope and escaping
3. **Transport E2E:** subprocess stdin request to complete stdout response
4. **Client savings:** N standalone calls versus one N-op bundle, including total request and response bytes

Do not call the first category E2E.

## Gate 3: Bundle comparison

At minimum, benchmark identical operations as:

- three standalone complete MCP calls,
- one three-op bundle,
- ten standalone calls versus one ten-op bundle,
- twenty standalone calls versus one twenty-op bundle.

Include:

- all-cache-hit,
- all-cache-miss,
- mixed success/error,
- near-200 KB response,
- response-cap truncation,
- project-qualified calls,
- repeated identical sub-ops,
- operations with overlapping and non-overlapping data.

Report total latency and per-op latency. If parallelized, prove deterministic output order and equivalent shared-state behavior.

## Gate 4: Cold/warm separation

Label and independently measure:

- process cold start,
- initial index cold,
- filesystem page-cache cold where practical,
- handler cold cache,
- steady-state warm cache.

Snapshot and deps must have separate cache-hit and cache-miss rows. Never average one cache miss with 19 hits and call that one workload.

## Gate 5: Statistical robustness

For each row:

- multiple independent process launches,
- base/head alternation or randomized order,
- sufficient duration—prefer at least hundreds of milliseconds per sample group,
- median plus p90/p95,
- dispersion such as MAD or confidence interval,
- reject a claimed gain unless it exceeds run-to-run noise by a specified margin.

A 2–3× claim should reproduce across at least three independent runs.

## Gate 6: Compiler isolation

Run both:

- base and head with the same compiler, for source-change attribution;
- each revision with its declared compiler, for release-outcome validation.

Do not attribute the second comparison solely to the patch.

## Gate 7: CI thresholds appropriate to row scale

Replace the universal 50 µs floor with per-class limits. Suggested starting point:

- Rows under 10 µs: aggregate enough iterations to measure total batch time, then enforce 10–15%.
- Rows 10–100 µs: 10% and a 1–3 µs absolute floor.
- Rows over 100 µs: 10% and a 5–10 µs floor.

Bundle should be merge-blocking at a 10% regression once measured end-to-end.

## Gate 8: Current patch-specific proof

For the rolling trigram change:

- benchmark initial scan and controlled incremental `indexFile`,
- use realistic corpora at multiple sizes,
- compare exact trigram keys and `PostingMask` values,
- report throughput in bytes/sec and files/sec,
- confirm query rows remain semantically and statistically unchanged.

The added scalar mask parity test is useful correctness coverage, but the standard MCP benchmark is not evidence for this optimization.

# Merge blockers

1. **Block any “2–3× MCP/bundle/per-tool dispatch” claim based on the current table.**
2. **Block any bundle optimization without standalone-vs-bundle full-MCP comparison.**
3. **Block if response/result parity is not checked.**
4. **Block if telemetry-off and telemetry-on passes remain fixed-order and share warmed state while being compared as overhead.**
5. **Block if snapshot cache miss and hit remain averaged together.**
6. **Block if edit iterations do not restore the on-disk fixture.**
7. **Block benchmark-critical changes while the 50 µs absolute CI floor permits multi-fold regressions in bundle/search/read and effectively unlimited regressions in fast rows.**
8. **Block attribution of MCP row wins to the current trigram-construction patch; timed MCP dispatch does not include index construction.**
9. **For any MCP implementation change, require the project’s MCP E2E scenarios in addition to unit tests.**

## Bottom line

The credible optimization target in the working tree is trigram **index construction**, not MCP per-tool dispatch. `context`, pathological search/read, edit, and cold bundle workloads may have genuine 2–3× headroom. The current `deps`, exact `find`, status, word, tree, hot, and outline rows are already near fixture-specific floors.

The strongest counterexample is snapshot: merely being the second pass changes approximately 36.9 µs into roughly 0.15 µs with no semantic optimization. That demonstrates that the existing design can manufacture far more than a 2–3× “win” from cache state alone.
