## Benchmark problems and confounds

### 1. Only aggregate statistics were supplied

The decisive missing evidence is the 20 paired observations. Baseline and rolling means/medians do not reveal:

- How many of the 20 pairs favored rolling.
- Paired-difference variance or MAD.
- Confidence intervals.
- Outliers.
- Time/order drift.
- Whether the saving is concentrated in a few runs.

A paired mean saving of 5.05 ms can still result from a few favorable outliers. A paired median of 4.5 ms is better evidence that at least half the pairs favored the change, but it still does not show whether the effect is stable enough to exceed normal system noise.

For a change this small, I would require at minimum:

- All 20 raw A/B values and paired differences.
- Win count.
- Median/MAD or bootstrap confidence interval of paired savings.
- Preferably a sign test or paired permutation/bootstrap test.
- Confirmation that reversing which binary runs first does not change the result.

### 2. “Alternating A/B” does not fully remove drift

Alternation helps, but a fixed sequence such as always `baseline → rolling` allows systematic second-run advantages:

- Hot filesystem page cache.
- Warmer directory metadata and executable pages.
- CPU frequency ramp-up.
- Allocator/OS state.
- Thermal changes.
- Background load correlated with elapsed time.

The experiment should counterbalance order, for example AB/BA/BA/AB, or randomize order while preserving pairing. If “alternating” means the order was genuinely reversed each pair, that should be stated explicitly and results should be split by order.

### 3. The claimed percentage is selectively based on medians

The paired median gives:

```text
4.5 / 140.0 = 3.21%
```

But the means give:

```text
5.05 / 140.95 = 3.58%
```

Neither is wrong, but presenting only “~3.2%” obscures that the relative statistic was not defined consistently. More importantly, ratios of separately reported medians are not a substitute for the distribution of per-pair percentage changes.

### 4. `index_ms` is an end-to-end composite

The diff changes only the local trigram accumulation loop, while `index_ms` likely includes:

- Reading or unpacking files.
- Parsing/outlining.
- Word and sparse indexes.
- Hash-map allocation and growth.
- Global posting-list insertion.
- Worker scheduling and merge/commit work.

That makes the reported improvement useful as an end-to-end observation, but weak for attribution. A 5 ms movement could come from scheduler or I/O differences rather than this loop. It also masks whether the loop itself improved materially.

A loop-level benchmark or profile should confirm reduced time/instructions in `TrigramIndex.indexFile`.

### 5. The corpus is stable but narrow

A 730-file git archive controls input variation, but does not establish generality across:

- Very small files, where rolling setup may lose.
- Large generated/minified files.
- Binary-ish content.
- Whitespace-heavy files.
- Mixed-case versus already-normalized text.
- Different architectures or CPU generations.
- Worker counts other than two.
- Other allocators or debug/safe builds.

The optimization may be Zig-0.17/codegen- and target-specific. That is acceptable if this exact release target is the goal, but the evidence should not be generalized.

### 6. No benchmark artifact is present in the current diff

The only tracked modification is `src/index.zig`. I found no raw benchmark result tied to the diff, binary hashes, compiler target, CPU state, command line, or corpus hash. The reported numbers therefore cannot be independently recomputed or audited from the working tree.

The new loop appears algebraically equivalent for ordinary successful execution:

- `i & 7` is equivalent to `i % 8` for nonnegative `usize`.
- `n3 & 7` is equivalent to normalized-byte `% 8`.
- Lengths below three still do no work.
- Length three executes exactly once without using a nonexistent fourth byte.

- Raw bytes remain available for pure-whitespace filtering.

### Residual correctness risks

#### Duplicate implementations can diverge

`indexFileReuse` contains the original non-rolling loop and remains unchanged. The code search found no current callers, but it is public and independently implements the same indexing semantics. Two implementations increase maintenance risk: future normalization, whitespace, or mask changes can be applied to only one path.

The present change does not create a current output difference, but keeping both implementations without differential tests is risky.

#### Existing tests do not prove exact index equivalence

The ReleaseFast suite passing is reassuring, but ordinary search tests may miss mask differences because the final content scan can compensate for candidate-filter false positives. Stronger tests should compare baseline and rolling-produced internal data exactly:

- Trigram key set.
- Per-trigram `loc_mask`.
- Per-trigram `next_mask`.
- Boundary lengths 0–5.
- All whitespace combinations.
- ASCII case normalization.
- Arbitrary bytes, ideally randomized/property-tested.

#### Error-path behavior was not improved

The surrounding `indexFile` mutates document/path state before all allocations have succeeded. Failures during local accumulation or posting insertion can leave partial state. This predates the rolling diff and is not evidence against its output equivalence, but it means “tests pass with c allocator” does not establish robust correctness under allocation failure.

#### Comment overstates the mechanism

The new comment says rolling keeps values “in registers.” Zig source does not guarantee register allocation; that is a compiler/codegen result. It also claims the old loop “reloaded” bytes, but LLVM may already eliminate overlapping loads or normalization calls. The benchmark/profile must establish this rather than the comment.

## Should it be kept?

**Not yet on the supplied evidence.**

The diff is modest, localized, and appears semantically correct, so the bar need not be enormous. It would become reasonable to keep if the raw paired data show, for example:

- A strong majority of pairs favoring rolling.
- A paired confidence interval excluding zero.
- No meaningful AB-versus-BA order effect.
- Equivalent index contents under differential/property tests.
- A profile or microbenchmark showing the changed loop is actually responsible.

Without those, the result is a suggestive 4.5–5.05 ms movement in a 136–141 ms composite measurement, not demonstrated causation.

## Further Zig-0.17-specific ideas

**Reject additional speculative 0.17-specific micro-optimizations for now.**

The current result is already near the scale where benchmark noise and codegen accidents matter. More source-level transformations should not be stacked on top before this one is isolated. In particular, reject ideas justified only by assumptions such as:

- “0.17 will keep these in registers.”
- Replacing more `%` operations with bit masks without measured impact.
- Manual unrolling or vectorization.
- Branch-hinting the whitespace path.
- More rolling-state variables.
- Unsafe wider/unaligned loads.
- Special allocator tricks for this loop.

Such changes could increase register pressure, code size, bounds-check complexity, target sensitivity, or correctness risk while LLVM may already perform the intended optimization.

The next 0.17-specific work should be evidence-gathering rather than another patch:

1. Preserve raw paired results and environment metadata.
2. Counterbalance execution order.
3. Profile both binaries on the same corpus.
4. Inspect generated machine code for this function if the profile identifies it as material.
5. Add exact baseline-versus-rolling differential tests.
6. Only pursue another idea if profiling names a remaining bottleneck.

**Final verdict: refuted.** The counterexample to the inference is that the same aggregate means and medians can arise from order effects, high paired variance, or a few outliers; without the raw pair distribution and counterbalanced ordering, the benchmark does not demonstrate that this diff caused a repeatable improvement. The implementation itself appears correct and remains a plausible candidate pending stronger evidence.
