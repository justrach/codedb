**BLOCKER — borrowed storage can still return a stale content hash.**  
`src/explore.zig:841` returns the cached hash solely when `content_generation` matches. However, `putBorrowed` exposes externally owned storage whose bytes may change without another cache insertion; its generation then remains unchanged. The new test at `src/test_explore.zig:2743` hides this case by calling `putBorrowed` again after mutation. Fix by either hashing borrowed entries on every read (include ownership/immutability in `ValueRef`) or enforcing and documenting immutable borrowed storage, then add a test that mutates backing storage without reinsertion and validates the chosen API contract.

Also required before merge:

- `src/hot_cache.zig:169-173`: generation wraparound deliberately reuses generation `1`, allowing an old per-path hash entry to match after wrap. Handle rollover by invalidating the associated hash cache/epoch or use a non-reusable cache identity plus generation. Add a deterministic near-wrap test.
- Test coverage does not exercise hash correctness after CLOCK eviction and reinsertion, `ContentCache.clear` followed by reinsertion, or concurrent read/update/clear through `Explorer`. Add these cases; generation uniqueness currently makes eviction/clear work only until wraparound.
- `ValueRef` contains a borrowed slice whose validity depends on external synchronization. `Explorer.renderCachedRead` correctly holds its shared lock, but the public `ContentCache` API does not state that `getWithGeneration`, updates, eviction, and clear are not thread-safe. Document the synchronization contract or enforce it internally.
- Performance direction is otherwise sound: generation comparison avoids rehashing unchanged owned content, and clearing the hash map with the content cache prevents retained stale entries and unbounded keys across full clears.
