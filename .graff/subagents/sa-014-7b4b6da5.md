### 3. PR template/checklist requirements

#### No PR template is tracked

There is **no `.github/PULL_REQUEST_TEMPLATE.md` or equivalent template directory** in the current tree. The tracked `.github` files are only:

- `.github/copilot-instructions.md`
- `.github/workflows/bench-regression.yml`
- `.github/workflows/pr-base-guard.yml`
- `.github/workflows/release-binaries.yml`

A search through all reachable Git objects also found no historical `PULL_REQUEST_TEMPLATE` path. Therefore, the operative checklist is in `CONTRIBUTING.md`, not a GitHub form/template.

#### Mandatory process

The ground rules require every PR to:

- be tied to an issue;
- be rebased onto current `main`;
- remain tightly scoped;
- exclude generated artifacts;
- avoid unrelated lockfile churn (`CONTRIBUTING.md:7-15`).

The PR description should include:

- linked issue number;
- exact-change summary;
- files/subsystems touched;
- tests run;
- failing test, xfail, or exact pre-fix reproduction;
- passing rerun of that same test/reproduction;
- nearby non-regression checks;
- whether rebased onto current `main`;
- whether generated files, lockfiles, or benchmarks changed;
- explicit confirmation of compliance with `CONTRIBUTING.md` (`CONTRIBUTING.md:17-30`).

If no issue maps cleanly, open one first (`CONTRIBUTING.md:32`).

For fixes and performance regressions, evidence must be red-to-green: show failure first, make the change, rerun the same check successfully, and run neighboring checks (`CONTRIBUTING.md:34-43`). Merely saying “tests passed” is insufficient (`CONTRIBUTING.md:127-133`).

Scope should normally remain under **500 changed lines**; larger PRs require an explicit justification in the body (`CONTRIBUTING.md:73-75`).

For benchmark PRs, the description must identify:

- measured layer;
- cache state;
- cold-start versus warmed steady state;
- number of runs;
- single-run versus median;
- exact machine or CI environment (`CONTRIBUTING.md:141-155`).

#### Important policy tension

`CONTRIBUTING.md` says to rebase onto `origin/main` (`CONTRIBUTING.md:77-84`), while the PR-base guard requires the PR itself to target the active `release/*` branch (`.github/workflows/pr-base-guard.yml:9-18`, `.github/workflows/pr-base-guard.yml:35`). These are different concepts—rebase/up-to-date requirement versus GitHub PR base—but the documentation does not explain how to reconcile them when the release branch is ahead of `main`.
