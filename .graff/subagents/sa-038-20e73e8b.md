## Ranked realistic opportunities

### 1. `Explorer.renderTree` — cache the generation-stable rendered tree

**Why this is the strongest 2–3x candidate**

Every call:

1. acquires the Explorer shared lock for the entire operation;
2. copies every outline-map key into a temporary array;
3. sorts all paths;
4. allocates a `StringHashMap` for directories;
5. repeatedly scans path prefixes and recounts slash depth;
6. performs another outline hash lookup for every already-collected path.【src/explore.zig:2707-2734】【src/explore.zig:2735-2764】

This is avoidable repeated work because tree output is wholly determined by indexed outlines plus the color flag. A generation-keyed cached byte representation—or even cached sorted paths/directory structure—would turn repeated benchmark calls into one append/copy. The current direct-render path already removed one intermediate copy, and its own comment says that change merely “halves allocation churn”; it does not address the repeated sort and directory reconstruction.【src/explore.zig:2703-2706】

**Expected rows affected**

- **Primary:** `codedb_tree` normal row.【src/bench.zig:26-28】
- **Primary:** `edge_tree_many`, where file-count scaling makes the repeated `O(F log F)` sort dominant.【src/bench_edge.zig:47-50】
- Potential indirect improvement for bundles containing tree, though the pinned bundle row does not currently include it.【src/bench.zig:39-39】

**Expected magnitude:** **2–5x on repeated normal calls; potentially much larger on `edge_tree_many`.** The estimate is inference, but the repeated full sort and hash-map rebuild are verified.

### 2. `Explorer.searchSymbols` / exact `handleSymbol` — bypass global symbol-index scan for exact names

The normal `codedb_symbol` row asks for exact `"main"`, yet `handleSymbol` always constructs a general `SymbolSearchSpec` and calls `searchSymbols`.【src/bench.zig:29-30】【src/mcp.zig:1548-1637】

For non-fuzzy searches, `searchSymbols` iterates the **entire symbol-index hash map**, computes `symbolMatchScore` for every distinct symbol name, and only then processes matching locations.【src/explore.zig:3112-3137】 Exact lookup already has an indexed implementation: `findAllSymbols` directly obtains `symbol_index.get(name)`.【src/explore.zig:2825-2835】

Additional exact-result overhead includes:

- scanning the target file’s symbol list again to recover detail for every location;【src/explore.zig:2835-2843】
- duplicating path, symbol name, and detail into caller-owned results;【src/explore.zig:2845-2854】
- in the generic path, maintaining a sorted top-K list and performing linear dedup checks;【src/explore.zig:2957-2963】【src/explore.zig:3019-3061】
- cloning every final candidate again before return.【src/explore.zig:3151-3162】

A dedicated exact-name renderer from `symbol_index.get(name)` could render borrowed indexed locations directly while holding the shared lock, analogous to `renderOutline`.

**Expected rows affected**

- **Primary:** `codedb_symbol` exact `"main"`.【src/bench.zig:29-30】
- **Primary:** `edge_symbol_exact`.【src/bench_edge.zig:42-44】
- **Direct repository benchmark:** symbol rows `init`, `main`, `handleRequest`, `render`, because those call `findAllSymbols`; a borrowed/direct-render change would help, although replacing the global scan only affects MCP `searchSymbols`, not the direct benchmark’s lookup stage.【src/benchmark.zig:113-124】【src/benchmark.zig:330-331】
- **Indirect:** `codedb_context`, which invokes `findAllSymbols` once per extracted keyword.【src/mcp.zig:2544-2563】

**Expected magnitude:** **2–3x for exact MCP symbol on nontrivial symbol tables**, with higher upside on edge corpora. Fuzzy and glob rows remain full-index workloads and need different indexing.

### 3. `handleContext` — fuse repeated keyword searches and eliminate repeated whole-file copies/scans

For each extracted task candidate, context independently performs:

- one exact symbol lookup;
- one ranked content search.【src/mcp.zig:2516-2524】【src/mcp.zig:2544-2573】

For small symbol result sets it then:

- calls `getContent` separately for each symbol reference;
- copies the entire cached file because `getContent` duplicates borrowed content;
- scans from byte zero until the requested symbol body, even for a late line.【src/mcp.zig:2621-2638】【src/mcp.zig:2639-2660】【src/explore.zig:2456-2464】

It subsequently performs another scoped content search for each distinct symbol keyword to build callers, despite having already searched the same keyword for ranked hits.【src/mcp.zig:2663-2685】 The implementation has already deduplicated duplicate `sym_ref` keywords because six redundant scoped searches cost about 180 µs, confirming that this phase is benchmark-visible.【src/mcp.zig:2676-2685】

Realistic optimization: expose one per-keyword search primitive that returns ranked hits plus scope metadata, reuse it for both file ranking and callers, and render symbol ranges from borrowed cached content/line-offset spans rather than `getContent` + a scan from line 1.

**Expected rows affected**

- **Primary:** `codedb_context`, whose pinned task names several identifiers and is run 50 times.【src/bench.zig:41-42】
- **Secondary:** no existing context edge row; the normal row is the only direct benchmark coverage.
- Search internals may improve indirectly only if the fused primitive is shared; the regular `codedb_search` rows do not execute context composition.

**Expected magnitude:** **2–3x is realistic for multi-keyword tasks with ≤3 definitions**, especially where bodies occur late in large files. This is inferred from the verified repeated searches/copies rather than measured profiling.

### 4. `Explorer.fuzzyFindFiles` / `handleFind` — bounded top-K instead of materialize-and-sort-all; avoid exact pre-scan

Fuzzy find first allocates a candidate path array, then a second match array, scores every candidate, sorts **all matches**, and truncates only after sorting.【src/explore.zig:5521-5553】【src/explore.zig:5567-5582】 With `max_results=10` or 50, maintaining a bounded heap/top-K avoids `O(M log M)` sorting and the potentially large match array.

`handleFind` also performs a separate full outline-key scan for exact basename/stem matches before fuzzy search.【src/mcp.zig:4318-4322】 `renderExactFileFind` computes basename/stem and case-insensitive comparisons over every indexed path.【src/explore.zig:5585-5604】 On a miss, this means two file-table passes before output. A basename/stem index would make the first stage `O(1)` and also remove that repeated scan from exact finds.

For delimiter-stripping retries, a no-result fuzzy scan can be repeated with the broadened query, making two full scoring passes.【src/mcp.zig:4340-4358】

**Expected rows affected**

- **Primary:** `codedb_find` normal row. Its `"main"` query first scans all paths for exact basename/stem; whether it reaches fuzzy scoring depends on corpus filenames.【src/bench.zig:40-40】
- **Primary:** `edge_find_fuzzy`, guaranteed to stress full fuzzy behavior.【src/bench_edge.zig:50-53】
- Potentially fuzzy path suggestions from failed outline/read/deps operations, depending on their helper implementation.

**Expected magnitude:** **2–3x on large fuzzy-find corpora**, especially broad queries yielding many matches. Exact `"main"` may gain primarily from the basename index, not top-K.

### 5. `Explorer.renderImportedBy` / dependency graph — remove per-query all-file basename scan and result duplication

Every ordinary imported-by request scans **all outline paths** merely to count files sharing the queried basename.【src/explore.zig:5726-5739】 Only after that does it perform the reverse dependency-map lookup and render results.【src/explore.zig:5740-5765】 Maintaining a basename multiplicity map during index updates would make this test constant-time.

The normal `codedb_deps` row takes the path-only fast path to `renderImportedBy`, so this scan is exactly on the measured path.【src/bench.zig:33-34】【src/mcp.zig:2921-2925】【src/mcp.zig:3019-3033】

For forward non-transitive dependencies, the handler copies each dependency string and then allocates an owned slice solely to render and immediately free it.【src/mcp.zig:2941-2955】【src/mcp.zig:2980-3016】 This can render borrowed entries while holding one shared lock, matching the imported-by direct renderer.

Transitive BFS also duplicates every output path even though queue traversal uses stable graph strings; it maintains separate queue, visited map, output array, and per-result string allocations.【src/explore.zig:444-497】【src/explore.zig:500-536】

**Expected rows affected**

- **Primary:** `codedb_deps`.【src/bench.zig:33-34】
- **Primary:** `edge_deps_trans`; basename-indexing helps the reverse direction, while borrowed result rendering/arena BFS helps transitive allocation cost.【src/bench_edge.zig:53-55】

**Expected magnitude:** **2–3x for ordinary deps on large file sets** because it removes the only full-file scan. Edge transitive speedup is likely smaller unless the reachable graph is large.

### 6. `Explorer.renderHot` — replace per-file Store lookups and `O(F × limit)` selection

`renderHot` simultaneously holds the Explorer shared lock and Store mutex while walking every outline and calling `store.getLatestSeqUnlocked(path)` for every file.【src/explore.zig:5832-5848】 Once its bounded list is full, selection searches the current top list for the minimum for each candidate, making it `O(F × limit)` rather than `O(F log limit)`.【src/explore.zig:5849-5855】

The older `getHotFiles` path was even more allocation-heavy—duplicating every path, building a full entry array, then sorting all files—but the current handler correctly uses `renderHot`, so that older function is not the benchmark-critical path.【src/explore.zig:5780-5825】【src/mcp.zig:2907-2911】

A Store-maintained recent-file list or sequence-ordered ring would make hot close to `O(limit)`. Short of that, iterate Store’s latest records directly and use a min-heap, avoiding per-outline hash lookup and shortening dual-lock hold time.

**Expected rows affected**

- **Primary:** `codedb_hot`.【src/bench.zig:32-33】
- No dedicated hot edge row currently exists; `edge_word_hot` is a word-index row, not hot-files.【src/bench_edge.zig:53-54】

**Expected magnitude:** **2–3x on repositories with many files**, but probably less on the small normal copied corpus.

### 7. `handleRead` / `renderReadBytes` — avoid full-file hash and cwd canonicalization for every small range

Even cached ranged reads hash the **entire file** before extracting a 20-line range.【src/explore.zig:2540-2575】 The normal benchmark asks for lines 1–20 of `src/main.zig`, and the edge benchmark asks for 40 lines around line 40,000 of `huge.zig`.【src/bench.zig:34-35】【src/bench_edge.zig:47-49】

The handler also resolves `"."` to a real path on every invocation solely to normalize the requested path before attempting the in-memory cached read.【src/mcp.zig:3035-3045】 The project root is session-stable and should be retained in `BenchContext`/session state.

The cached path is otherwise good: it renders directly from borrowed content without duplicating the file.【src/explore.zig:2491-2509】 The line-offset cache can accelerate deep line selection, but the full Wyhash remains `O(file bytes)` per call.

A per-content-generation cached hash plus pre-resolved project root makes ranged read proportional to requested output rather than file size.

**Expected rows affected**

- **Primary:** `codedb_read`.【src/bench.zig:34-35】
- **Primary:** `edge_read_deep`, where full-file hashing of `huge.zig` is likely dominant.【src/bench_edge.zig:47-49】

**Expected magnitude:** **2–3x for normal cached range reads and potentially much more for `edge_read_deep`**. Whole-file reads remain output-copy bound.

### 8. `handleStatus` — consolidate locks and cache derived status snapshot

`handleStatus` takes and releases the Store mutex, calls `approxIndexSizeBytes`, then separately takes and releases the Explorer shared lock.【src/mcp.zig:3413-3430】 `approxIndexSizeBytes` is intentionally aggregate-only and O(1), so there is no hidden posting-list scan here.【src/telemetry.zig:398-420】

The main remaining opportunity is lock churn/cache-line traffic: publish file count/sequence/index counters atomically or maintain a generation-keyed status snapshot. Because output formatting and dispatch overhead are irreducible at this scale, a clean 2–3x is less certain than for tree/deps/read.

**Expected rows affected**

- **Only:** `codedb_status`.【src/bench.zig:37-38】

**Expected magnitude:** **1.3–2x likely; 2–3x only under lock contention.** This is not a top-priority 2–3x bet.

## Lower-confidence or already-optimized paths

### Outline

Normal outline rendering is already the right shape: one map lookup, no clone, one capacity reservation, and direct serialization while holding a shared lock. The source records an earlier improvement from roughly 66 µs to 35 µs by eliminating per-symbol copies.【src/explore.zig:2337-2370】 A generation-keyed rendered-outline cache could still help repeated identical calls, particularly `edge_outline_huge`, but the output itself must still be copied to the response buffer.

**Affected rows:** `codedb_outline`, `edge_outline_huge`.【src/bench.zig:28-29】【src/bench_edge.zig:47-48】  
**Assessment:** plausible ~1.5–2x, not the strongest independent 2–3x target unless response bytes are cached at a higher protocol layer.

### Word

Single-token `searchWord` is already one shared-lock acquisition plus `word_index.searchDeduped`, documented as O(1).【src/explore.zig:5368-5389】 Multi-word mode allocates an arena, lowercases each token, and aggregates via hash maps, but neither pinned word row is multi-word.【src/explore.zig:5391-5415】【src/bench.zig:31-32】【src/bench_edge.zig:53-54】

**Affected rows:** normal `codedb_word`, `edge_word_hot`, and direct word rows `request`, `response`, `config`, `error`.【src/benchmark.zig:100-110】【src/benchmark.zig:328-329】  
**Assessment:** no obvious realistic 2–3x from the audited wrapper; likely allocator/result-copy micro-optimization only.

### Search

Search already has both result and plain-render caches, but the direct repository benchmark explicitly disables the search cache for its five ordinary rows and enables it only for the representative cached row.【src/benchmark.zig:313-327】 Cached result retrieval still allocates a fresh result array and duplicates every result path and line text; cache insertion also duplicates the same fields into cache-owned storage.【src/explore.zig:1014-1032】【src/explore.zig:1059-1075】 That creates serialization/storage duplication, but ordinary MCP plain search can use a rendered-byte cache, reducing the importance of result-copy optimization.

**Affected rows:** repository `cached:error`; possibly normal `codedb_search`; edge search rows intentionally bust cache.【src/benchmark.zig:320-327】【src/bench.zig:30-31】【src/bench_edge.zig:35-41】  
**Assessment:** cache-hit result borrowing could produce 2x in the direct cached row; uncached 2–3x requires deeper search-tier profiling and is not established by this static audit.

## Verified versus inferred

### Verified

- Tree repeats a full path collection, sort, directory hash-map construction, and prefix/depth scanning on every call.【src/explore.zig:2715-2764】
- Generic exact-symbol handling scans every distinct symbol name, despite an existing direct exact-name index lookup API.【src/explore.zig:2825-2835】【src/explore.zig:3112-3137】
- Context performs exact-symbol plus ranked-content search per keyword, then additional scoped searches and whole-file body extraction work.【src/mcp.zig:2544-2573】【src/mcp.zig:2630-2660】【src/mcp.zig:2676-2685】
- Fuzzy find materializes candidates/matches and sorts all matches before truncating.【src/explore.zig:5521-5582】
- Ordinary deps scans every outline path to count basename collisions.【src/explore.zig:5726-5739】
- Ranged reads hash the whole file; hot traverses every outline while holding both major locks.【src/explore.zig:2540-2575】【src/explore.zig:5832-5848】

### Inferred

- The stated 2–3x ranges are engineering estimates based on removed asymptotic/repeated work; no profiler output was available in the audited source.
- Tree, context, deps, find, and deep read are the most likely to clear 2x because each has a verified corpus-wide scan, sort, repeated search, or whole-file operation that can be avoided.
- Status, ordinary outline, and single-token word are unlikely to sustain 2–3x because their current core paths are already short and direct.

## Three most load-bearing facts

1. **`codedb_tree` rebuilds and sorts the complete tree on every one of its 100 timed calls**, making a generation-keyed render cache the clearest repeated-work win.【src/bench.zig:27-27】【src/explore.zig:2715-2764】
2. **Exact MCP symbol lookup currently uses the general symbol-search routine that iterates the entire symbol index**, although `findAllSymbols` already supports direct exact-name lookup.【src/explore.zig:2825-2835】【src/explore.zig:3112-3137】
3. **The measured context path runs multiple search modes per keyword and copies/scans full files to render small symbol ranges**, providing several independent opportunities that can compound to 2–3x.【src/mcp.zig:2544-2573】【src/mcp.zig:2630-2660】【src/mcp.zig:2676-2685】
