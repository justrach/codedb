## Findings

### High — `codedb_callers` now drops real calls after backtick literals

**Evidence:** `src/mcp.zig:2586`, `src/mcp.zig:2691-2695`, `src/mcp.zig:2708-2719`

`lineCodePrefix` skips only single- and double-quoted literals. Backticks are intentionally not treated as strings, so a URL or comment-like text inside a JavaScript template literal or Go raw string is interpreted as a real line comment.

Exact failure sequence:

1. Index `url.js` containing:
   ```js
   const url = `https://example.test`; renderX();
   ```
2. Invoke `codedb_callers` with `{"name":"renderX"}`.
3. `lineCodePrefix` sees the `//` in `https://` and returns the prefix before it.
4. `hasWholeWordMatchOutsideStrings` receives only that prefix and never sees the real `renderX()` call.
5. The legitimate caller is omitted from the result.

This is a regression from the prior implementation, which searched the full line and would retain the call after the backtick literal.

**Missing regression tests:**

- JavaScript template literal containing `//` followed by a real call:
  ```js
  const url = `https://example.test`; renderX();
  ```
- Go raw string containing `//` followed by a real call:
  ```go
  s := `https://example.test`; renderX()
  ```
- Rust raw string containing `//` followed by a real call.

### Medium — PHP and Swift trailing comments remain false call sites

**Evidence:** `src/mcp.zig:2697-2704`; language detection at `src/explore.zig:221` and `src/explore.zig:231`

`detectLanguage` recognizes `.php` and `.swift`, and `langHasCallSites` permits them, but `lineCodePrefix` has no marker cases for either language and falls through to `return line`.

Exact failure sequence:

1. Index:
   ```php
   init(); // renderX() is documented here
   ```
   as `trail.php`.
2. Index a real call in another file:
   ```php
   renderX();
   ```
3. Invoke `codedb_callers` for `renderX`.
4. The PHP line is not a full-line comment, `lineCodePrefix` returns it unchanged, and the comment mention passes the whole-word filter.
5. The response reports the PHP comment as a call site.

The same sequence occurs for Swift with `trail.swift`.

This also contradicts the fix’s stated intent of applying the language-specific comment rules consistently.

**Missing regression tests:**

- PHP trailing `//` comment containing only the symbol, plus one real PHP call.
- PHP trailing `#` comment containing only the symbol.
- Swift trailing `//` comment containing only the symbol.

---

### Medium — Trailing block comments are still counted as calls

**Evidence:** `src/mcp.zig:2693-2695`, `src/mcp.zig:2714-2724`; existing comment classification at `src/explore.zig:8137`

The new helper deliberately leaves mid-line block comments untouched. Consequently:

```c
init(); /* renderX() is only documentation */
```

is retained as a caller for `renderX`. The existing `isCommentOrBlank` helper recognizes `/*` for C-like languages only when the comment begins the trimmed line, so it does not prevent this case.

Exact failure sequence:

1. Index `trail.c` with:
   ```c
   init(); /* renderX() is only documentation */
   ```
2. Index another file containing a real `renderX()` call.
3. Invoke `codedb_callers`.
4. The line begins with executable code, so the full-line comment filter accepts it.
5. `lineCodePrefix` does not cut at `/*`.
6. The whole-word filter finds `renderX` in the block comment and reports `trail.c` as a caller.

**Missing regression tests:**

- C, C++, Java, and Zig trailing block-comment mentions.
- A line with a real call after a block comment:
  ```c
  init(); /* comment */ renderX();
  ```
  The implementation must exclude the first case without dropping the second.

## Coverage and performance assessment

The test-first change correctly reproduces the Zig `//` case and adds a quoted-URL preservation test, but the coverage is too narrow for promotion. It does not exercise the supported-language matrix, backtick/raw literals, or block comments.

`codedb_callers` already has an edge benchmark at `src/bench_edge.zig:45`, but the corpus does not cover the new parser paths. The fix adds another full scan of every candidate line before the existing whole-word scan. There are no allocations in the new helper, so the common-case cost is bounded, but a benchmark should measure:

- 5,000 candidate lines with trailing comments;
- long JavaScript/Go lines containing backtick literals;
- latency at `max_results=50` and `max_results=10000`.

No path-handling or new security issue was found.

The test-first process is sound for the single reproduced failure, but the fix is not safe to promote until the false-negative and cross-language cases above are covered and resolved.

**Verdict: real calls after backtick/raw literals are silently omitted from `codedb_callers` results.**
