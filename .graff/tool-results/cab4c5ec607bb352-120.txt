## Findings

### [Medium] `lineCodePrefix` truncates valid callers after backtick/raw literals

**File:** `src/mcp.zig:2707-2715`

`lineCodePrefix` skips only single- and double-quoted spans. It does not skip backticks, despite `hasWholeWordMatchOutsideStrings` explicitly treating backticks as non-string syntax for Go raw strings and JavaScript template literals.

Failure sequence:

1. Index this valid Go line:
   ```go
   func caller() { s := `http://x`; renderX() }
   ```
2. `searchContentWithScope` returns the line because it contains `renderX`.
3. `lineCodePrefix` encounters the `//` inside the raw string `http://x`.
4. It returns only the prefix before that marker.
5. `hasWholeWordMatchOutsideStrings` receives a slice that no longer contains `renderX`, so `codedb_callers` omits a genuine caller.

The same failure occurs in JavaScript with a template literal such as:

```js
function caller() { const s = `http://x`; renderX(); }
```

This is a concrete false negative in a common supported-language construct.

### [Medium] PHP and Swift trailing comments are not stripped

**File:** `src/mcp.zig:2697-2704`

The language-marker switch has no cases for `.php` or `.swift`, so `lineCodePrefix` returns the entire line for both languages. However, `langHasCallSites` treats both as call-site languages at `src/mcp.zig:2746-2750`.

Failure sequences:

```php
<?php init(); // renderX()
```

```swift
func caller() { initialize() } // renderX()
```

For either file:

1. The line is not considered comment-only because it begins with code.
2. `lineCodePrefix` returns the complete line.
3. `hasWholeWordMatchOutsideStrings` finds `renderX` outside a string.
4. `codedb_callers` reports the comment mention as a call site.

### [Low] Shell comment detection rejects valid comments after shell metacharacters

**File:** `src/mcp.zig:2714-2719`

The shell-specific condition only recognizes `#` at column zero or after a space/tab. Shell comments can also begin after a word delimiter such as `;`.

Failure sequence:

1. Index this valid shell line:
   ```sh
   echo ready;# renderX()
   ```
2. At `#`, the preceding byte is `;`, so the condition breaks instead of treating it as a comment.
3. Scanning continues through `renderX()`.
4. The caller is incorrectly reported even though the symbol appears only in the comment.

## Assessment

`zig build test --summary all` passes, and the new helper is memory-safe: it returns a borrowed slice without allocation or ownership changes, and the caller keeps `line_text` alive for the duration of filtering. The remaining problems are functional coverage gaps not exercised by the added Zig-only tests.

**Verdict:** The most dangerous defect is the backtick/raw-string truncation at `src/mcp.zig:2707-2715`, which silently drops real Go and JavaScript callers; the integration is not release-ready.
